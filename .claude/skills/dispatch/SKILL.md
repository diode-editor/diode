# Тик диспатчера

Ты — одноразовая сессия: делаешь один проход по правилам ниже и завершаешься. Ты ничего не
помнишь о прошлых тиках и не должен — всё состояние в GitHub (метки, комментарии), в tmux и в
`~/.claude/agent-loop/`. Устройство лупа — [scripts/agent-loop/README.md](../../../scripts/agent-loop/README.md).

Вопросов человеку не задаёшь: его здесь нет. Код не правишь, issues не комментируешь сам —
только через скрипты ниже. Решения принимаешь по фактам из `facts.mjs`, а действуешь скриптами:
они делают всё точно и одинаково.

## 0. Свежий main

```sh
git pull --ff-only
```

Не вышло из-за доступа (`Permission denied (publickey)`: человек отключился и ssh-агент пропал) —
репа публичная, бери по https:

```sh
git pull --ff-only https://github.com/diode-editor/diode.git main   # HTTPS_ORIGIN из lib.mjs
```

Не вышло и так (сеть, не fast-forward) — тик всё равно продолжай на том, что есть, и упомяни это в
выводе. Обновлённый скилл подхватит уже следующий тик.

После pull — зависимости основного чекаута в ногу с `package-lock.json` (бамп движка иначе
оставляет старый `node_modules`, и у детей tsc красный «из-за окружения»):

```sh
node scripts/git/wt-bootstrap.mjs
```

Он сам ничего не делает, если lock не менялся; поменялся — `npm ci`, минута-две.

## 1. Факты

```sh
node scripts/agent-loop/facts.mjs
```

В JSON: `machine` (нагрузка, память, лиза), `limits`, `verdict.canStart` с причинами, `sessions`
(живые `task-<N>`), `inProgress` (issues в работе: `sessionAlive`, `managerAlive`, `ageHours`,
`expired`, статусы ролей), `queue` (кандидаты по порядку: `bug` первыми, потом старые;
`branchExists`; `sessionAlive` — на этой машине живёт её `task-<N>`), `blocked` (issues с `ready to implement`, у которых открыт хотя бы один блокер —
нативное «Blocked by» GitHub или строка `Blocked by #N` в теле; в очередь не входят, их не
трогай — освободятся сами, когда блокер закроется), `worktrees`.

## 2. Свернуть то, что умерло — обратно в очередь

Диспатчеры ходят на нескольких машинах, и у задачи другого хоста (`mine: false`, хост в `claim`
не совпадает с `machine.hostname`) сессия живёт там, а не здесь: `sessionAlive: false` про неё
ничего не значит. Чужую задачу сворачиваешь **только** по `expired: true` — её хозяин умер
насовсем, раз не свернул сам. `claim`, `mine` и `expired` считаются по claim'у после последней
передачи задачи (`returned:`/`requeued:` в issue), а не по самому первому: у возобновлённой
задачи возраст идёт с возобновления. Для своих (`mine: true`) — одно из:

| Факт                                                         | Причина для `--reason`                                                   |
| ------------------------------------------------------------ | ------------------------------------------------------------------------ |
| `sessionAlive: false`                                        | «сессия task-N не найдена — машина перезагрузилась или сессия убита»     |
| `expired: true`                                              | «задача в работе дольше `limits.taskTimeoutHours` ч — снята по таймауту» |
| `sessionAlive: true`, `managerAlive: false`, окна детей есть | «окно менеджера пропало, дети остались без присмотра»                    |

```sh
node scripts/agent-loop/return-task.mjs --task <N> --reason "<причина по-русски>" --requeue
```

Это не вопрос к человеку, а авария машины или времени, поэтому `--requeue`: скрипт комментирует
issue (причина, id сессий, хвосты панелей), возвращает метку `ready to implement`, PR не трогает и
убивает сессию. Следующий тик увидит задачу в `queue` первой (`branchExists: true`) и
`start-task.mjs` **возобновит** её, а не начнёт с нуля. Лимит — `AGENT_LOOP_MAX_RESUMES` (2)
возобновлений на задачу; дальше скрипт сам ставит `returned` человеку, флаг не поможет. Остальные
задачи — живые, их ведёт менеджер, не трогай.

## 2а. Вернуть метку живой задаче

Задача из `queue` с `sessionAlive: true` не ждёт запуска — она идёт прямо здесь (её сессия
`task-<N>` жива с `sessionSince`), а метку `ready to implement` ей вернул по ошибке чужой
диспатчер или человек. Пока метка не та, другой хост может взять её параллельно, а твой шаг 4 —
попытаться запустить второй раз. Для каждой такой:

```sh
node scripts/agent-loop/reclaim-task.mjs --issue <N>
```

Скрипт ставит свежий `claim:` временем старта сессии и возвращает `in progress`; код `3` — уже не
нужно (метка сменилась между фактами и вызовом), просто идёшь дальше. Сворачивать такую задачу
нельзя: она живая.

## 3. Уборка

```sh
node scripts/agent-loop/cleanup-worktrees.mjs
```

Сносит worktree с влитой веткой, где никто не работает, и ветки тестировщика влитых задач.
Что оставил и почему — печатает; этого достаточно, вручную ничего не досносить.

## 4. Взять одну задачу

Только если `verdict.canStart: true` и `queue` не пуста. Берёшь **первую** из `queue` без
`sessionAlive: true` (те возвращены в работу на шаге 2а) — порядок уже правильный: сначала возобновляемые (`branchExists: true` — ветка и PR уже есть, работу надо
доделать), потом `bug`, потом старые. Одна задача за тик: следующий тик увидит нагрузку уже с ней.

```sh
node scripts/agent-loop/start-task.mjs --issue <N>
```

Ветка `issue/<N>` с открытым PR на origin — скрипт сам возобновляет задачу: пишет `resume.json`
в каталог задачи (PR, причина прошлого возврата, вердикт тестировщика из его комментария в PR,
id сессий для `claude --resume`, если прошлый прогон был на этой машине), и менеджер продолжает с
нужного места. Тебе ничего решать не надо.

Коды выхода: `0` — запущена (вывод скажет, с нуля или возобновлена); `3` — отказ (ветка есть,
а открытого PR нет — скрипт сам поставил `returned` с объяснением; или issue не подходит) —
возьми **следующую** из `queue`, но не больше одной попытки сверх первой; `4` — задачу раньше
захватил другой хост, это нормально, ничего не делай; иначе — ошибка, напечатай и заверши тик.

`canStart: false` — напечатай причины и заверши тик. Пороги не обходить и не «подождать внутри
тика»: следующий тик через несколько минут.

## 5. Итог

Три-пять строк: что свернул, что снёс, что запустил (или почему нет). На этом всё.
