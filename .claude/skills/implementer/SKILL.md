# Реализатор задачи `<N>`

Ты работаешь автономно: человека нет, вопросов задать некому. Работай по AGENTS.md и докам
проекта как обычно; здесь — только то, что отличает луп. Устройство лупа —
[scripts/agent-loop/README.md](../../../scripts/agent-loop/README.md). Номер задачи — аргумент
скилла и `$AGENT_LOOP_TASK`.

## Начало

1. Прочитай issue целиком с комментариями: `gh issue view <N> --comments`. Это спека. Для бага
   она может быть короткой — воспроизведи его первым делом, воспроизведение и есть тест.
2. **Неясно, противоречиво, упирается в решение человека или в блокер** — не угадывай и не
   спрашивай: напиши статус `returned` с вопросом и остановись (ниже). Это нормальный исход.
   Если неясность мелкая и есть разумный дефолт по эталону vscode — выбери его и запиши
   решение в описание PR и в `--note` статуса `ready-for-test`: тестировщик проверит именно его.
3. Worktree: `EnterWorktree` с именем `issue-<N>`, затем `git branch -m issue/<N>` и
   `node scripts/git/wt-bootstrap.mjs`. Ветка обязана называться `issue/<N>` — по ней тебя
   находят тестировщик, менеджер и уборка.

## Продолжение

Промпт начинается с «Resumed task» — задачу уже делали (таймаут, смерть машины, человек вернул
её в очередь), ветка `issue/<N>` и PR есть. Не начинай с нуля и не переделывай сделанное:

1. Источник правды — GitHub, не память: `gh issue view <N> --comments` (последний комментарий
   `returned:`/`requeued:` — почему остановились), `gh pr view <pr> --comments` (отчёт
   тестировщика начинается строкой `verdict: approve|bugs`), `node scripts/git/pr-status.mjs <pr>`
   (`CONFLICTING` — первым делом влей `origin/main`, раздел «Конфликт с `main`»), сама ветка.
   Если это твоя же сессия, продолженная через `--resume`, всё равно сверь: что реально
   запушено и что говорит CI.
2. Worktree: есть `.claude/worktrees/issue-<N>` — работай в нём (`cd`, `git fetch origin
issue/<N>`, `git checkout issue/<N>`, `git reset --hard origin/issue/<N>`, если локальная
   ветка отстала; незакоммиченное там — твоё же, посмотри, прежде чем сбрасывать). Нет —
   `EnterWorktree` с именем `issue-<N>`, затем `git fetch origin issue/<N>` и
   `git checkout -B issue/<N> origin/issue/<N>`. В обоих случаях `node scripts/git/wt-bootstrap.mjs`.
3. Вердикта тестировщика ещё нет (`Tester verdict so far: none`) — доведи PR до состояния
   «готов к проверке» и напиши `ready-for-test` заново (шаг 3 раздела «PR и `ready-for-test`»):
   менеджер запустит тестировщика. Вердикт есть — он уже лежит в `tester.json`, иди в раздел
   «Отчёт тестировщика»; по `bugs` ветка `issue/<N>/tests` могла быть уже влита в `issue/<N>` —
   проверь `git log`, а список багов возьми из комментария тестировщика в PR.
4. Бюджет мутаций на продолжение — заново полные 20 минут.

## Тесты — заранее, не после

Мутационный гейт — дорогой и лимитированный, а значит, он проверка, а не поиск того, что
тестировать. Поэтому:

- тест на **наблюдаемый результат** пишется до кода или вместе с ним, а не после «работает»;
  видимая часть — тест доходит до кадра (AGENTS.md, «Что считать готово»);
- между правками — точечный `npx vitest run <файл>`; `claude-lease run -- npm run check:diff`
  перед сдачей шага; `npm test`, `typecheck` и всё тяжёлое — тоже под лизой
  (`claude-lease run -- npm test`): без неё тесты плавают, а три таких прогона разом роняют под по памяти;
- бенчи (`bench:*`, `test:perf*`) локально не гоняются вовсе — только CI (скилл `heavy-run`);
- медленный или упавший по таймауту тест на загруженной машине — не баг и не повод копать
  перф: повтори под лизой; баг — только то, что воспроизвелось под лизой;
- **первый мутационный прогон — не раньше зелёного `check:diff`**, и сначала
  `npm run test:mutation -- --scope-only`: у каждого файла из скоупа должен быть тест,
  иначе ты заплатишь бюджетом за то, что видно глазами.

## Бюджет мутаций — 20 минут прогонов на задачу

```sh
claude-lease run -- node scripts/agent-loop/mutation-budget.mjs -- npm run test:mutation
claude-lease run -- node scripts/agent-loop/mutation-budget.mjs -- npm run test:mutation -- --mutate src/path/file.ts
```

- Считается только время прогона под слотом; ожидание лизы — нет. Прямой
  `npm run test:mutation`/`npx stryker` без обёртки хук не пропустит.
- Проверяй мутантов **точечно** — `--mutate <файл>` там, где не уверен, вместо полного
  прогона после каждой правки. Выжившего разбираешь в порядке docs/MUTATION.md: сначала удалить
  код (недостижимый guard, проверка «для типа»), иначе тест на поведение, и только честно
  эквивалентного гасишь `// Stryker disable next-line …: причина`; не ассертом ради балла.
  Маркеры с причиной «unreachable/defensive/for the type» держит храповик `stryker-disable-check`.
- Код 76 — бюджет исчерпан: локально больше нельзя, гоняй в CI `npm run ci:run -- mutation`
  и чини по его отчёту. Бюджет — потолок и для идущего прогона: когда остаток вышел, обёртка
  убивает прогон и отдаёт тот же код 76; его вывод — не вердикт. Перепроверка мутантов за минуту
  до потолка сворачивается сама, оставшиеся — inconclusive: их проверяй точечно вживлением
  (`scripts/mutation-inject.mjs`) или смотри в CI. Код 75 — лиза не дала слот, прогон не
  запускался, повтори без `-w`.
- Храповик не опускаем: PR всё равно должен пройти mutation-job в CI.

## Упростить — после зелёного `check:diff`, до живого запуска

Прогони `/simplify` над диффом ветки и примени найденное: дубли тестов, абстракция ради одного
вызова, параметр без второго потребителя, ветка, до которой не доходит ни один путь. Критерий:
в диффе не осталось строки, которую можно убрать, не потеряв поведение и тест на него. После
правок — снова `claude-lease run -- npm run check:diff`.

## PR и `ready-for-test`

1. Перед PR — живой запуск (скилл `drive`) и взгляд на кадр, как велит AGENTS.md.
2. Push только по https: `git push https://github.com/diode-editor/diode.git issue/<N>`.
   PR по docs/PR.md: заголовок и тело по-английски, в теле `Closes #<N>`, как воспроизвести,
   принятые решения по неясностям, секция `## Removed` (что удалено или заменено, `Nothing` — явно); фича с видимой частью — сценарий-демо в `e2e/scenarios/`.
3. **Сразу после создания PR**, не дожидаясь CI:
    ```sh
    node scripts/agent-loop/status.mjs write --task <N> --role implementer --status ready-for-test \
        --pr <номер> --branch issue/<N> --note "<решения по спеке и отступления, если есть>"
    ```
4. Дальше параллельно: доводи CI до зелёного (красное чинить, флаки по docs/PR.md) и жди
   тестировщика — в фоне:
    ```sh
    node scripts/agent-loop/wait.mjs --task <N> --role tester --timeout 2h
    ```
    Пушить в `issue/<N>` можно: тестировщик работает в своей ветке `issue/<N>/tests`.

CI ждёшь **только** так, не `gh pr checks --watch`:

```sh
node scripts/git/pr-status.mjs <pr> --watch
```

Код `0` — всё зелёное, `1` — что-то красное (упавшие перечислены), `13` — PR **CONFLICTING**:
скрипт выходит сразу, не дожидаясь проверок, потому что ждать их бессмысленно (ниже).

## Конфликт с `main` — чинить сразу, не ждать

Рядом идёт вторая задача лупа, и она часто правит те же общие файлы (`docs/public/API-COVERAGE.md`,
`docs/extensions/api-matrix*`, `e2e/api-conformance/*`, `docs/arch/*.md`, трекер). Как только её PR
влит, твой становится `CONFLICTING`: GitHub не собирает merge-коммит, **новый CI на такой PR не
запускается, а идущий бежит против уже несуществующей базы** — его вердикт ничего не стоит, и
`gh pr merge` откажет. Урок 2026-10-31 (PR #931): реализатор два часа ждал проверок конфликтующего
PR, задача провисела вдвое дольше нужного.

Поэтому код `13` от `pr-status.mjs --watch`, отказ `gh pr merge` «not mergeable» или
`CONFLICTING` в любой проверке статуса — одно и то же действие, немедленно:

```sh
git fetch origin main && git merge origin/main
```

Разреши конфликты (генерируемые файлы не своди руками — перегенерируй: `npm run api-matrix` и
т. п.), `claude-lease run -- npm run check:diff`, коммит, push и снова `pr-status.mjs <pr> --watch`.
Merge, не rebase: PR вливается squash'ем, merge-коммит в ветке никому не мешает, а force-push не
нужен. И **перед финальным push** — тем, после которого ты собираешься вливать, — влей
`origin/main` заранее тем же `git fetch origin main && git merge origin/main`: конфликт дешевле
поймать до часового круга CI, чем после.

## Отчёт тестировщика

- **`approve`** — `node scripts/git/pr-status.mjs <pr> --watch` с кодом `0` (код `13` — конфликт с `main`, раздел выше) → `gh pr ready <pr>` (после возврата PR может быть в draft, а draft не вливается) → `gh pr merge <pr> --squash --delete-branch` → статус `done`: squash-коммит в `main` — от владельца gh-аккаунта, автора не подменяем (GitHub принимает в `--author-email` только подтверждённый адрес этого аккаунта).
- **`bugs`** — `git fetch origin issue/<N>/tests` и `git merge origin/issue/<N>/tests`: в
  статусе список багов с путями к падающим тестам. Чини каждый, пока его тест не станет
  зелёным; временный или дублирующий тест, который ничего не добавляет, можно убрать — но
  баг он поймал настоящий, починить его обязан. Бюджет мутаций общий на всю задачу. Потом
  `git fetch origin main && git merge origin/main`, push, `pr-status.mjs <pr> --watch` до кода `0`
  → влить → `done`:
    ```sh
    node scripts/agent-loop/status.mjs write --task <N> --role implementer --status done --pr <номер> --branch issue/<N>
    ```
- **`window-gone`, `idle`, `timeout`** тестировщика — не вливай. Останови работу: менеджер
  сворачивает задачу, человек разберётся. Без вердикта тестировщика PR в `main` не попадает.

Записал `done` — работа закончена, больше ничего не делай: сессию закроет менеджер.

## Спутники: tuidom, сайт, доки, магазин

Задача может упираться в соседний репозиторий: движок [`tuidom/tuidom`](https://github.com/tuidom/tuidom)
(пакеты `@tuidom/*`), лендинг и реестр расширений `diode-editor/diode-editor.github.io`, сайт
документации `diode-editor/docs`, веб-витрина магазина `diode-editor/marketplace`. Решение человека
2026-10-24: в лупе ты **сам** ведёшь там ветки, открываешь PR, вливаешь по зелёному CI и **сам
публикуешь tuidom** — спрашивать некого. Правила самого репозитория (его AGENTS.md) читай и соблюдай;
push везде по https (`git push https://github.com/<owner>/<repo>.git <ветка>`), ssh-ключа на машине нет.

- **Чекаут tuidom** — `$TUIDOM_DIR`, иначе `/workspaces/tuidom/tuidom`; нет ни того, ни другого —
  `git clone https://github.com/tuidom/tuidom.git` в каталог рядом с diode и дальше работай там.
  Проверить правку движка на diode до публикации — `npm run engine:link` (`--tuidom <dir>`).
- **Публикация tuidom** — релиз едет по тегу: в tuidom `npm run set-version X.Y.Z` → PR
  `release: X.Y.Z` → зелёный CI → влить → на влитом коммите `main`
  `git tag -a vX.Y.Z -m "TUIDom X.Y.Z"` и push тега по https. Дальше `release.yml` публикует
  пакеты сам (OIDC). **Дождись версии**: раз в минуту `npm view @tuidom/core@X.Y.Z version`, пока не
  ответит; обычно минуты, через 20 минут тишины — смотри `gh run list -R tuidom/tuidom`, упавший
  канал — `gh run rerun <id> --failed`, не новая версия.
- **Поднять `@tuidom/*` в diode** — в ветке своей задачи (`package.json` + `package-lock.json`,
  `npm install`), это часть той же работы; в теле PR назови версию движка. Пока версия не приехала
  в npm, diode на неё не завязывай (CI не соберётся).
- Сайт, доки, витрина — свой PR в их репозитории по их правилам, вливаешь по зелёному CI сам; Pages
  выкладывают сами. В теле PR diode — ссылки на эти PR.

## Вернуть задачу

В любой момент, когда дальше нельзя без человека:

```sh
node scripts/agent-loop/status.mjs write --task <N> --role implementer --status returned \
    --question "<что именно должен решить человек, по-русски>" [--pr <номер>] [--branch issue/<N>]
```

Незакоммиченное закоммить и запушь в `issue/<N>` до этого — ветка останется человеку. После
статуса остановись: менеджер оформит `returned` в issue и закроет сессию.
