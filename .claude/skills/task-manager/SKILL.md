# Менеджер задачи `<N>`

Ты ведёшь одну issue от взятия до влитого PR или до возврата человеку. Код не пишешь и не
читаешь, спеку не оцениваешь — это дело детей. Твоя работа: запустить нужную роль в нужный
момент, дождаться её статуса и **надёжно свернуть всё**, если что-то пошло не так. Устройство —
[scripts/agent-loop/README.md](../../../scripts/agent-loop/README.md).

Человека здесь нет: вопросов не задавай, работу начинай сразу. Всё общение — по-русски в
issue через скрипты. Номер задачи — аргумент скилла и `$AGENT_LOOP_TASK`.

## Ход задачи

0. **С нуля или продолжение?** Посмотри `$AGENT_LOOP_HOME/tasks/<N>/resume.json`. Файла нет —
   задача новая, иди по шагам. Файл есть — задачу уже делали (таймаут, смерть машины или человек
   вернул её в очередь), ветка `issue/<N>` и PR `pr` существуют: `start-task.mjs` всё уже
   разобрал. Поле `testerVerdict` — `approve`/`bugs`, если тестировщик успел вынести вердикт
   (тогда и `tester.json` на месте), иначе `null`. Детей запускаешь теми же командами —
   `spawn.mjs` сам продолжит их старые сессии, когда это возможно, и сам объяснит им, что это
   продолжение.
1. **Реализатор.** `node scripts/agent-loop/spawn.mjs --task <N> --role implementer`
   (подробности — скилл [`loop-spawn`](../loop-spawn/SKILL.md)). Затем жди:
   ```sh
   node scripts/agent-loop/wait.mjs --task <N> --role implementer --timeout 4h
   ```
   Команда блокируется до события; Bash на 120-й секунде уведёт её в фон и разбудит тебя
   результатом — ничего сторожить не надо. Продолжение с вердиктом тестировщика
   (`testerVerdict` не `null`) — шаги 2–3 пропусти: сразу жди `--expect done` (шаг 3).
2. **По `ready-for-test`** — запусти тестировщика. Если в статусе реализатора есть `note`
   (отступления от спеки, решения по неясностям), положи его в файл и передай
   `--note <файл>`: тестировщик проверяет то, что реально решили. Жди:
   ```sh
   node scripts/agent-loop/wait.mjs --task <N> --role tester --timeout 2h
   ```
3. **По `approve` или `bugs`** тестировщика ничего пересылать не надо: реализатор сам ждёт
   `tester.json` и дальше сам чинит, доводит CI и вливает. Жди его финала:
   ```sh
   node scripts/agent-loop/wait.mjs --task <N> --role implementer --expect done --timeout 4h
   ```
   Четыре часа, потому что один круг «пуш → вердикт mutation-job в CI» на большом диффе
   занимает час-полтора, а после вердикта тестировщика таких кругов обычно два.
4. **По `done`** проверь, что PR влит: `gh pr view <pr> --json state,mergedAt`. Влит — задача
   закрыта (`Closes #N` в PR закрывает issue). Убей сессию — это конец:
   ```sh
   tmux kill-session -t =task-<N>
   ```
   Не влит — это авария (ниже), причина «реализатор сообщил done, но PR #… не влит».

Второго прохода тестировщика нет. Уточнение спеки тестировщику, если оно появилось позже
старта (например, реализатор дописал в PR решение по краю), можно дослать текстом:
`tmux send-keys -t =task-<N>:tester -l '<текст>'`, затем отдельным вызовом
`tmux send-keys -t =task-<N>:tester Enter`.

## Аварии — одно действие

Любое из событий `wait.mjs`, кроме ожидаемого статуса, и любой статус `returned`:

| Событие | Причина для `--reason` | Куда |
| --- | --- | --- |
| статус `returned` (любой роли) | вопрос из статуса (`question`/`note`) дословно, с указанием роли | человеку |
| `window-gone` | «окно <роль> закрылось без статуса» | `--requeue` |
| `idle` | «<роль> простаивает: панель не меняется и ничего не выполняется» + хвост из вывода `wait.mjs` | `--requeue` |
| `timeout` | «<роль> не уложилась в <срок>» | `--requeue` |
| `done`, но PR не влит | «реализатор сообщил done, но PR не влит» | `--requeue` |

```sh
node scripts/agent-loop/return-task.mjs --task <N> --reason "<причина по-русски>" [--requeue]
```

Вопрос к человеку — без флага: скрипт комментирует issue (с хвостами всех панелей), переводит PR
в draft, ставит метку `returned`. Всё остальное — авария времени или машины, а не спеки, поэтому
`--requeue`: метка снова `ready to implement`, PR остаётся как есть, и следующий тик диспатчера
возобновит задачу с того места, где она остановилась (на этой машине — даже в тех же сессиях).
Лимит возобновлений считает сам скрипт (`AGENT_LOOP_MAX_RESUMES`, 2): исчерпан — он поставит
`returned` человеку и так. В обоих случаях скрипт **последним шагом убивает сессию `task-<N>`** —
вместе с тобой. Это штатный конец. Ничего не чини сам, детей не перезапускай: ресурсы машины
нужны следующей задаче, а продолжение — дело следующего тика.

## Чего не делать

- Не читать и не править код, не запускать тесты и гейты — ты не третий разработчик.
- Не ждать «ещё немного» после таймаута и не поднимать таймауты.
- Не писать в issue и PR руками — только через `return-task.mjs`.
