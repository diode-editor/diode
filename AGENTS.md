Diode — терминальный текстовый редактор (клон VS Code) на TypeScript/Node.js. Цели и неизменяемые ограничения — в GOAL.md, не забывай его читать.

# Карта документации
- GOAL.md — цели проекта и non-negotiable constraints
- docs/VISION.md — позиционирование: активы, ограничения реальности, направления, текущая ставка
- docs/ARCHITECTURE.md — концептуальная карта: обзор слоёв + правила зависимостей (единственный источник правды по слоям)

- docs/arch/State.md — машинное состояние UI/сессии (StateService, аналог IStorageService/Memento)
- TUIDom (движок TUI) — отдельный репозиторий [github.com/tuidom/tuidom](https://github.com/tuidom/tuidom), пакеты `@tuidom/*` (core, elements, terminal-backend, headless-backend, inspector, testing); его доки (LAYOUT.md, STYLES.md, arch/) живут там
- docs/TESTING.md — как тестировать каждый слой; скриншот-демо для визуальных фич; приёмы отладки

- docs/public/ — публичные страницы, на которые ссылается сайт (бенчмарки, матрица готовности API); правила каталога — в его README.md
- packaging/README.md — каналы дистрибуции (install.sh, apt, npm, Homebrew tap, winget): как они собираются из релиза и как проверить локально; трекер — docs/TODO/Distribution.md

# Трекер задач
Текущие задачи и планы ведём в docs/TODO/. Индекс — docs/TODO/README.md, крупные задачи — в отдельных файлах.
Когда берёшь задачу в работу, поменяй статус на `[~]`. Когда закончил — на `[x]`.

# Worktree
Любую задачу, которую мы начинаем с этапа планирования, ведём в отдельном git worktree — заходи в него через инструмент EnterWorktree до начала работы. Исключение одно: если пользователь явно сказал не использовать worktree для этой задачи.

Все worktree живут **только** в `.claude/worktrees/<имя>` (дефолтная раскладка EnterWorktree). Не создавай их где-либо ещё — ни в соседнем `../<repo>.worktrees/`, ни в произвольном каталоге. Каталог `.claude/worktrees/` в `.gitignore`, поэтому рабочее дерево репозитория не засоряется.

В **итоге по задаче всегда указывай полный путь к worktree**, где она сделана — пользователь оттуда запускает и проверяет.

# Хуки Claude Code
В `.claude/settings.json` подключены проектные хуки-предохранители (`.claude/hooks/`, описание — в [README](.claude/hooks/README.md)): отказ на `test:mutation -- <позиционный>`, `git fetch <url> …:refs/remotes/…` без `--no-prune`, push по ssh и правку мимо текущего worktree, плюс разовое Stop-напоминание по чеклисту «готово». Отказ хука — это подсказка, как сделать то же правильно, а не повод обходить его другой командой.

Если ты перемещаешь файлы, добавляешь новые каталоги или меняешь зависимости между слоями — обнови docs/ARCHITECTURE.md.

# Style
Линт, типы и слои — гейт CI (job `static` в `.github/workflows/ci.yml`): красный `npm run lint`, `npm run typecheck` или `npm run valid-layers-check` блокирует PR, поэтому перед сдачей прогоняй все три. Форматирование и сортировку импортов чинит `npm run lint:fix`, остальное — руками.

Внутренний цикл между правками — `npm run check:diff` (типы, линт и тесты только диффа ветки, десятки секунд; `--near` — только соседние тесты): быстрый, но **не** заменяет полные гейты перед сдачей → [docs/TESTING.md](docs/TESTING.md#быстрый-цикл-по-диффу-checkdiff).

На чём спотыкается линт (чтение по индексу при выключенном `noUncheckedIndexedAccess`, конфликты правил `strictTypeChecked`, формат сгенерированного кода) — [docs/STYLE.md](docs/STYLE.md).

Не забывай использовать расширения в имени файла при импорте.
Приватные переменные давай не будем писать с подчеркиванием. Используй просто название и модификатор

# Что считать «готово»
Урок #194/#195: фича может быть зелёной по тестам и по покрытию, и при этом не работать в приложении совсем. Гейты ниже — про то, чтобы тест смотрел туда же, куда смотрит пользователь.

- **Покрытие — не сигнал DoD.** Храповик 100% в `vitest.config.ts` ловит регрессии в написанном коде и по устройству слеп к ненаписанному. Пропущенный продюсер события и недостающее условие в отрисовке дают 100% покрытия и нерабочую фичу. «Добил покрытие» ≠ «фича работает».
- **Перед сдачей фичи — `npm run test:mutation`.** Вторая половина храповика: покрытие говорит «строка исполнилась», мутационный балл — «кто-то её проверил». Тест без осмысленного ассерта даёт 100% покрытия и 11% мутационного балла (замерено). Выжившего мутанта либо убиваем тестом, либо гасим `// Stryker disable next-line <мутатор>: причина` — но не ассертом ради балла. Фантомов руками **не** разоблачаем: гейт сам вживляет точный мутант каждого не убитого Stryker'ом и печатает класс. `phantom` — Stryker соврал, чинить нечего (и гасить нельзя); `real` — настоящая дыра (тест или `disable`, подсказка `возможно, эквивалентный` — повод посмотреть на `disable`); `runtime-error` — мутант роняет vitest вне тестов, чинить код; `inconclusive`/`timeout`/`stale` — вердикта нет, причина в строке (красные без мутанта тесты, зависание, протухший отчёт — перегнать). Таблица классов → [docs/TESTING.md](docs/TESTING.md#гейт-сам-перепроверяет-каждого-выжившего-вживлением), детали → [docs/TESTING.md](docs/TESTING.md#мутационное-тестирование-stryker).
- **Тестируй наблюдаемый результат, а не шов, который только что написал.** Ассерт на структуру, в которую фича пишет (`viewState.foldedRegions`), не видит бага в том, кто её читает (рендер). Если у фичи есть видимая часть — тест обязан дойти до кадра.
- **На каждое новое RPC-сообщение — тест продюсера.** «Субпроцесс умеет разобрать сообщение» покрывает половину контракта. Вторая половина — «кто и по какому событию его шлёт»; именно она отсутствовала, и `activeTextEditor.selection` навсегда залипал на `(0,0)`.
- **Фича поверх стокового расширения закрывается стоковым расширением:** настоящий `.vsix` из магазина (версию не пиним), его настоящая функциональность из пользовательского состояния, проверка результата. Наш контракт при этом закрывается ещё и герметичным тестом на своих синтетических расширениях. Конвенция → [docs/TESTING.md](docs/TESTING.md#тесты-на-стоковые-расширения--из-магазина-конвенция).
- **Настройки — как в эталоне.** Есть у фичи в vscode настройки — они приезжают в том же PR: ключи, дефолты, `scope`, `enum`, описания дословно; неподдержанный ключ назван в PR. Как искать и заводить → [docs/arch/Configuration.md](docs/arch/Configuration.md).
- **Запусти приложение.** Харнесс фейкает рендер и ввод — то есть ровно те две области, где баги и живут. Перед «готово» — реальный запуск (`npx tsx src/vs/diode/main.ts --user-data-dir=<tmp> --headless=WxH --inspect-tui=…`) и взгляд на кадр.
- **Выводы задачи — в репозиторий, а не в память агента.** Авто-память Claude Code (`~/.claude/projects/.../memory`) — только для фактов конкретной машины: ресурсы, пути соседних чекаутов, ветки, которые живут только локально. Рецепты, грабли, устройство и решения человека пишутся в репозиторий (AGENTS.md, docs/, скиллы, комментарии в коде) в том же PR, что и работа: следующая сессия на другой машине память не увидит.

# Как работать с человеком
- **Форму фичи сверяй с эталоном vscode до вопроса, а не после — и предлагай эталонный вариант дефолтом.** Исходники эталона того же тега — `node scripts/vscode-ref.mjs` (печатает путь, при нужде качает). Вариант, которого в эталоне нет, — изобретение агента: называй его отступлением и объясняй, зачем оно. Урок #352: человек согласился на «тост с кнопками забирает фокус», потом сам спросил «а как в vscode?» — в эталоне тост фокус не берёт, кражу придумал агент.
- **Решение, которое требует человека, — вопросом с вариантами и дефолтом.** У каждого варианта — цена, один помечен дефолтом, назван срок. Нет ответа к сроку — принимается дефолт, и в отчёте и PR это записано как решение человека по дедлайну, а не как самоуправство.
- **Храповики не опускаем.** Планки покрытия, мутационного балла и прочих гейтов только растут: опустить планку ради одного PR — ослабить гейт всем следующим. Если массовая правка (линт-проход, переформатирование) затянула в гейт старый долг, гейт на этом PR пропускается **разово** по решению человека, а долг уходит в трекер — прецедент [docs/TODO/MutationDebtAfterLintSweep.md](docs/TODO/MutationDebtAfterLintSweep.md).

# Правила разработки
Сквозные конвенции, которые надо держать в голове. Полные формулировки — в детальных arch-доках по ссылкам.
- **Ограничения tuidom НЕ обходим — идём и чиним движок.** Не хватает API, хука или параметра у движка или виджета — правка делается в репозитории tuidom (`/workspaces/tuidom/tuidom`): своя ветка, свой PR, вливаешь сам, человека не ждёшь. **Публикацию версии в npm запрашивай у человека** и до её выхода diode на неё не завязывай; проверить заранее — `npm run engine:link` ([docs/TESTING.md](docs/TESTING.md#неопубликованный-движок-tuidom-в-diode)). Запрещено: копировать куски движка, monkey-patching и приватные поля (`as any`, `@ts-expect-error`), дубликат виджета ради хука, пост-обработка grid'а в обход каскада. Тест-обходы — тоже обходы.
- **Цвета** — только ИМЕНА токенов темы в `style`/`styleVar`; никаких RGB-литералов и инлайн-фоллбэков. Новый цвет — определение `{ defaults: { dark, light }, description }` в `src/vs/platform/theme/common/colors/`. Детали → [docs/arch/Theme.md](docs/arch/Theme.md).
- **`vscode.d.ts` запиннен к upstream:** единственная ручная правка — снятие `// ` с дословных строк дормантной копии; поднял поверхность — в том же PR обнови [docs/public/API-COVERAGE.md](docs/public/API-COVERAGE.md) (руками, без генератора). Правишь этот файл — сначала [docs/arch/Extensions.md](docs/arch/Extensions.md).
- **Перенесённый diff-движок** (`src/vs/editor/common/diff/`, часть `editor/common/core/`, `base/common/charCode.ts`) — дословная копия upstream: руками не правится, только `scripts/import-vscode-diff.mjs`. → [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#дословный-перенос-upstream-editorcommondiff).
- **DI** — токены именуются `*DIToken`; токен объявляется рядом со своим типом (слой токена = слой типа, проверяет `valid-layers-check`); `tuidom/` токенов не объявляет и `diContainer` не импортирует. Детали → [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#di-контейнер-границы-использования).
- **Состав фичи** — всё, что фича `src/vs/workbench/contrib/<f>/` регистрирует (команды, контекст-ключи, ключи состояния, contribution'ы, конфигурацию), объявляется в её папке; набор файлов — по нужде, не по шаблону. Канон и таблица оставшегося долга → [docs/arch/Workbench.md](docs/arch/Workbench.md#состав-фичи).
- **Система команд** — ID команд, отражающих VS Code Workbench/Editor, именуются в стиле VS Code; доступность — через typed when-контексты из `ContextKeys.ts`. Детали → [docs/arch/Workbench.md](docs/arch/Workbench.md).
- **Сначала эталон, потом своя механика.** Прежде чем придумывать устройство или объявлять отличие «нашим выбором», найди ту же вещь в эталоне (`node scripts/vscode-ref.mjs`): найденные «отступления» почти всегда оказывались нормой эталона (ghost text — injected text, `--disable-extensions` — `_isDisabledInEnv`, Tab — `TabOperation`).
- **Надёжность процесса:** свой дочерний процесс — только `GuardedChildProcess`; команда возвращает промис и не роняет процесс; отказ host-обработчика RPC не бьёт по расширению; отсутствующая зависимость — null-объект, отказ — хвостом `.catch`. → [docs/arch/Common.md](docs/arch/Common.md#надёжность-процесса-что-не-должно-его-ронять).
- **Поднятый таймаут — признак непонятой причины.** Сначала выясни, почему медленно. Таймаут ассерта отличает «медленно» от «никогда» и проверку не ослабляет; таймаут, поднятый «чтобы прошло», прячет гонку.

# Файловая структура

Раскладка — vscode-канон `src/vs/*` (две оси: слои base→tui→base/browser→platform→editor→workbench→diode и окружения common/browser/node; карта — docs/ARCHITECTURE.md, проверка — `npm run valid-layers-check`). Имена файлов — **camelCase**, как у vscode: `tuiElement.ts`, `menuRegistry.ts`; файл называется по главному экспорту.

Тесты — колокацией рядом с кодом и не одним огромным файлом: `tuiElement.ts` + `tuiElement.test.ts`, а при многих кейсах — подразделы `tuiElement.events.test.ts`.
