Читается это так:
- **~300 мс над полом бинаря на файле любого размера** — цена нашей «кухни» старта, к файлу
  отношения не имеет. На странице BENCHMARKS.md обещано 26 мс воркбенча над полом Node.
- **+2.6 с на 13 МБ** — жадные проходы по всем строкам при открытии (не пьес-три и не диск:
  13 МБ читаются за миллисекунды).
- **88 с на 500 МБ** — те же проходы, помноженные на 5 М строк, плюс полная загрузка в одну
  JS-строку (у V8 потолок строки ≈ 512 МБ символов — гигабайтный файл сейчас не откроется
  в принципе).

## Разбор по коду (что именно горит)

Трасса `main.ts → runEditor → workbench.openFile → TextFileModel.openFile → new TextDocument →
EditorComponent`. Разведка 2026-09-27, ссылки на код актуальны на коммит `50b34ca3`.

### Кухня старта (не зависит от файла)
- Бандл `dist/main.js` 3.6 МБ одним ESM-файлом, `build-sea.mjs` не включает `useCodeCache` —
  V8 компилирует бандл на каждом запуске. `diode --version` = 146 мс против `node --version`
  на той же машине — это в основном и есть парс бандла.
- `createDefaultAssetAccess` копирует `diode.bundle` (`sea.getAsset`, не `getRawAsset`).
- Цикл встроенных расширений (`main.ts:484-511`) до первого кадра с файлом: `await assets.readText`
  в SEA — микротаск, рендер между итерациями не пробивается; внутри `builtinConfigInjection →
  bundledTsServerTarget → bundleSource` (`loadTsServer.ts:91-103`) — копия `ts-server.bundle`
  и **SHA-256 по всему бандлу**; `activateByEvent("*")` спаунит extension host до первого yield.
- Последовательные `await`: `loadConfiguration` → `loadUserKeybindings` → `scanExtensions`
  (52 манифеста) → … → `workbench.activate()` (внутри `explorerService.refresh()`) →
  `preloadGrammarsForFiles` (чтение `onig.wasm` + `loadWASM` + парс грамматики) → и только потом
  `openFile`. Независимые вещи ждут друг друга.
- Статически в бандле: `@xterm/headless`, chokidar, iconv-lite, vscode-textmate — платим
  парсом даже когда терминал не открывали.
- Инструментации старта нет: ни одного `performance.mark` в `src/vs/diode` и workbench.

### Жадные O(N) проходы при открытии (средние и большие файлы)
Каждый — полный проход по документу до первого кадра, где N — строки или символы:
1. **`LineWidthCache.getMaxWidth`** (`lineWidthCache.ts:84-97`) — ширина **каждой** строки
   через grapheme-`Intl.Segmenter`; дёргается первым же layout'ом (`contentWidth` для скроллбара,
   `editorElement.ts:190-203`). Главный подозреваемый на 200 К и 5 М строк.
2. **Подсветка вхождений слова под кареткой** (`editorElement.ts:967-989` → `findTextMatches`) —
   каретка в (0,0), слово `const`/`2026` есть в каждой строке фикстуры → 200 К / 5 М `IRange`,
   и `paintRangeBackground` (`:750`) обходит их все на каждом кадре.
3. **Фолдинг** (`editorComponent.ts:656-689`): `computeIndentationFolds` по всем строкам
   **дважды** (конструктор + сеттер `foldingRangeSource`), плюс `document.getText()` (полный
   join) **до** проверки, что провайдера нет или файл больше лимита.
4. **Document sync в extension host** (`documentSyncAdapter.ts:7-15`): `model.getText()` при
   открытии до проверки `rpc === null` / лимита 8 М символов; на `host.ready` join повторяется.
5. **`buildProjection`** (`editorViewState.ts:2211-2305`): проход по всем строкам с двумя
   `number[]` и `Int32Array`, при открытии строится 2–4 раза (фолдинг бампает версию дважды,
   `setWordWrap`, `ensurePrimaryCursorVisible`).
6. **`new TextDocument`**: `detectEndOfLine` — два полных `indexOf`-прохода, затем regex
   `split(/\r\n|\n/)` — третий проход и N строк-слайсов.
7. `detectIndentation` — дважды, но с капом 10 К строк (дёшево, просто лишнее).
8. После кадра, но тоже O(N): QuickDiff (`getText` + два `split` + diff с капом 1 с).

Что уже ленивое и трогать не надо: `DocumentTokenStore` (токенизирует до низа вьюпорта),
`LineBreaksCache` при выключенном wrap, `gutterWidth`.

### Гигантские файлы
- `TextFileModel.loadDocumentFromDisk` (`textFileModel.ts:560-572`): `readFileSync` целиком →
  `iconv.decode` целиком → одна JS-строка → `split`. Три копии файла в памяти, потолок строки
  V8, ни стриминга, ни размерного порога, ни large-file режима.
- **Перечитка с диска** (revert, авто-перечитка чистого буфера; E3, #468) — `setText` в тот же
  `TextDocument`: полная замена текста одним flush-событием, без минимального диффа, как у upstream
  `IModelService.updateModel`. Бенча перечитки больших файлов нет — сверить, когда этап «Гигантские
  файлы» дойдёт до стриминга (там же решать, нужен ли дифф вместо замены).

#### Исследование 2026-09-28: во что обходится загрузка бандла

Замеры на `node dist/main.js --version` (тот же путь, что пол бинаря, без SEA-обёртки; коммит
`50b34ca3`, node 25.9, 16 ядер), профиль `--cpu-prof --cpu-prof-interval=100`. Пол `node -e ""`
— 23 мс, бандл до `--version` — 133 мс, то есть **110 мс наших**:

| статья | мс | что это |
|---|--:|---|
| компиляция ESM (`compileSourceTextModule`) | 57 | ≈25 eager-компиляция IIFE-обёрток (webpack-рантаймы xterm/textmate/oniguruma), ≈32 preparse 3.4 МБ текста |
| исполнение верхнего уровня | 32 | тела 667 модулей (13.8 — сам module body), webpack-рантаймы (5), esbuild-shim'ы CJS (3), semver-регэкспы |
| загрузка undici | 9 | ESM-импорт `http` (`@tuidom/inspector` InspectorServer): фасад ESM перечисляет экспорты встроенного модуля, ленивый геттер `http` тянет undici. В CJS этого нет |
| GC | 6.5 | куча +8 МБ за загрузку (3.7 → 11.7 МБ heapUsed) |
| прочее | ~5 | |

Состав бандла (3.4 МБ, по esbuild-маркерам): iconv-lite 540 КБ, `workbench/contrib` 417,
`workbench/services` 343, `editor/common` 311, `workbench/browser` 291, `@xterm/headless` 274,
`workbench/api` 187, `@tuidom/elements` 179, `@tuidom/core` 149, vscode-textmate 97, semver 64,
yauzl 47, jsonc-parser 45, chokidar 40. Треть байт — зависимости, которые к первому кадру не
нужны (iconv только не-utf8, xterm только терминал, semver/yauzl/jsonc только магазин).

**Рычаги, замерено на том же бандле** (наших мс над полом node; сейчас 111):

| вариант | всего мс | наших |
|---|--:|--:|
| ESM как сейчас | 134 | 111 |
| тот же граф модулей в CJS (`esbuild --format=cjs --main-fields=module,main`) | 122 | 99 |
| CJS + кэш кода (`NODE_COMPILE_CACHE`; в SEA — `useCodeCache`) | 92 | 69 |
| ESM + `NODE_COMPILE_CACHE` | 108 | 85 |
| **CJS в V8-снапшоте** (`--build-snapshot`, блоб 16.8 МБ) | **68** | **45** |
| `--jitless` (контроль) | 165 | — |

Кэш кода снимает только eager-компиляцию (preparse и исполнение остаются) — потолок для него
≈69. Снапшот снимает и компиляцию, и исполнение: на старте куча восстанавливается, ничего не
парсится. Это и есть «предкомпилированный JS» в node; в SEA включается `useSnapshot: true`,
скрипт обязан вызвать `v8.startupSnapshot.setDeserializeMainFunction()`.

**Цена снапшота** (синтетика с кучей регулируемого размера): пустой пользовательский снапшот
стартует за 33 мс против 23 у `node -e ""` — **≈11 мс фиксированных** (сборка идёт
`BuildSnapshotWithoutCodeCache`: внутренние модули node компилируются заново; в SEA блоб вшит
в бинарь — перепроверить, не меньше ли там фиксированная часть); дальше **≈3 мс на МБ блоба**
(на нашем графе: 68 − 33 = 35 мс за 11 МБ сверх базового блоба). Отсюда потолок: ниже ~11 мс
наших не опуститься в принципе, 25–30 достижимо, если ужать кучу ядра вдвое.

**Что не сериализуется** (бисекция по 60 импортам main.ts, `CheckGlobalAndEternalHandles
failed`, «global handle not serialized: [Foreign]»):
- `Intl.Segmenter`, созданный на уровне модуля и живой через замыкание —
  `@tuidom/core/dist/common/measureTextWidth.js:2` и `displayLine.js:2`. Ленивое создание при
  первом вызове проходит (проверено на синтетике и на полном графе с патчем в node_modules).
  Правило общее: любой `Intl.*` на уровне модуля — нет.
- `HTTPParser` от импорта `http` (`@tuidom/inspector` InspectorServer). Ленивая заглушка
  `createServer` проходит; заодно уходят 9 мс undici. NB: Proxy-заглушка не годится —
  `__toESM` esbuild перечисляет ключи и будит модуль.
- Всё остальное из графа (xterm, textmate, oniguruma, chokidar, iconv, semver, yauzl,
  `child_process`, `perf_hooks`, `module`, `TextDecoder`, `Buffer`, `WeakRef`) — легло без
  вопросов; для `http`/`module`/`child_process`/`perf_hooks` node пишет «not yet fully
  verified», работоспособность после десериализации проверять e2e.

**Что снапшот меняет в правилах.** Верхний уровень модулей исполняется при сборке, не при
запуске. Значит, на уровне модуля нельзя: читать окружение в константы (`process.env`, `cwd`,
`homedir`, `platform`, размеры терминала, `isSeaBinary()` в кэш), держать нативные объекты
(`Intl.*`, парсеры, сокеты, таймеры, watcher'ы), делать top-level await (у нас один —
`await runEditor()` в `main.ts`). Дисциплина закрепляется гейтом: сборка снапшота в CI падает
на первом нарушении. `performance.timeOrigin` в лестнице старта — сверить после
десериализации.

**Распил бандла.** Без снапшота даёт ≈10 мс на вынесенный МБ (preparse) — почти не
окупается. Со снапшотом каждый МБ кучи ядра — ≈3 мс, и сумма стремится к 11 мс фиксированных.
Схема: ядро до первого кадра — в снапшоте; терминал (xterm), магазин (semver/yauzl/jsonc),
iconv, роли процесса (extension host, watcher; в исследовании — «LSP-клиент») — отдельными скриптами в ассетах SEA, компилируются по требованию с готовым
code cache (`vm.Script` + `cachedData`). Решение человека 2026-10-13: распил идёт **первым** —
сначала механика на маленьком пилоте, потом части по одной, каждая своим PR со своим e2e (см.
«План этапа»); всё равно делать всё, а риск гонок на новых асинхронных швах дешевле ловить по
одному шву.

**Как повторить** (всё — на `dist/main.js`, без SEA; пробник генерируется из импортов
`main.ts`, чтобы граф модулей совпадал):

```bash
# разбивка: пол, бандл, кэш кода
node -e ""; node dist/main.js --version; NODE_COMPILE_CACHE=/tmp/cc node dist/main.js --version
node --cpu-prof --cpu-prof-interval=100 dist/main.js --version   # self-time по url: esm/utils = компиляция
# CJS-пробник: те же импорты, что у main.ts (без type), имена удержать в массиве,
# + setDeserializeMainFunction под isBuildingSnapshot(); http → ленивая заглушка createServer
npx esbuild src/vs/diode/snapshotProbe.ts --bundle --platform=node --format=cjs --target=es2024 \
  --main-fields=module,main --define:import.meta.url=import_meta_url --inject:import-meta-url.js \
  --external:node-pty --external:@vscode/ripgrep --external:ws --external:vscode-languageclient \
  --alias:http=./http-stub.cjs --outfile=probe.cjs
# в node_modules/@tuidom/core/dist/common/{measureTextWidth,displayLine}.js — segmenter лениво
node --snapshot-blob probe.blob --build-snapshot probe.cjs && node --snapshot-blob probe.blob ver
```

#### План этапа

Порядок — решение человека 2026-10-13: сначала механика распила и маленький пилот, потом
части по одной, потом кухня, tuidom, CJS, снапшот, и последним — зажать гейт. Главный риск —
гонки на новых асинхронных швах (терминал открыли до загрузки xterm), поэтому каждая часть —
отдельный PR с e2e своей фичи и замером, а не один большой PR.

1. - [x] **Механика распила + пилот yauzl.** Куски — самостоятельные CJS-файлы `lazy/<id>.cjs`
     (esbuild вторым проходом, `scripts/build-lazy-chunks.mjs`, список `LAZY_CHUNKS`); в
     `tsup.config.ts` они `external`, в `main.js` от них остаётся голый `import()` — запасной
     путь dev. SEA вшивает куски ассетами, self-extract кладёт файлами рядом с `main.js`.
     Загрузчик `loadLazyModule` (`src/vs/base/node/lazyModule.ts`): кусок есть — компилирует
     его `vm.compileFunction` в CJS-обёртке с `require` от `createRequire`, нет — `importer`.
     Гейт-храповик на граф первого кадра (`npm run lazy-chunks-check`, CI job `static`, и та же

#### Открытые вопросы

- **Каждый процесс бинаря парсит весь `main.js`** (поднят в #612). run-as-node платит ≈170 мс
  CPU и +50 МБ RSS поверх пустого SEA. На сессию с TS-файлом — три спавна run-as-node
  (typescript-language-server и два tsserver), ≈0.85 с CPU и ≈250 МБ. Варианты:
  - (a) тонкий `main.js`-диспетчер ролей, редактор — кусок `roles/editor`. Спавн run-as-node
    стоит как пустой SEA, но ядро редактора уходит из `main.js`, и снапшот (шаг 6) его не
    покроет;
  - (b) решать на шаге снапшота: SEA-снапшот один на бинарь, каждый спавн десериализует кучу
    редактора (≈45 мс) вместо парса и исполнения;
  - (c) не трогать.

  **Решение отложено человеком до шага снапшота** (2026-10-14). Дефолт (a) по сроку 2026-10-16
  **не применяется**. Позиция сессии #612 для протокола — склоняется к (b): снапшот один на
  бинарь, а (a) лишает ядро редактора снапшота.

### Этап 2 — жадные проходы: файл до десятков МБ открывается как маленький
Каждый пункт измеряется на `xlarge` (13 МБ / 200 К строк) до и после:
- [ ] **Ширина контента лениво.** `getMaxWidth` не по всем строкам: быстрый путь для ASCII
  (ширина = длина, без `Intl.Segmenter`), максимум считать по видимым/уже измеренным строкам
  и дотягивать фоном по idle-чанкам (как VS Code: горизонтальный скролл растёт по мере измерения).
- [ ] **Подсветка вхождений** — окно ±N строк вокруг вьюпорта либо кап по числу совпадений
  (VS Code ограничивает), рисовать только пересекающиеся с видимой областью.
- [ ] **Фолдинг один раз и лениво**: без `getText()` пока провайдер не подтверждён и лимит не
  проверен; indentation-фолдинг — по требованию (первый рендер gutter'а) и с капом регионов.
- [ ] **Document sync без `getText()` вперёд**: снапшот строится только при живом `rpc` и
  после проверки лимита; лимит 8 М символов — сравнить с VS Code (50 МБ) и сделать настройкой.
- [ ] `buildProjection` один раз за открытие (версия фолдинга не бампается дважды),
  `detectIndentation` один раз.
- [ ] `TextDocument`: один проход вместо трёх (`indexOf`-скан со сбором стартов строк и
  подсчётом CR/LF за раз). Это временная мера — этап 3 заменит конструктор целиком.
- [ ] QuickDiff — после кадра он уже, но `split` по всему тексту убрать вместе с этапом 3
  (диффу нужны строки, они есть в буфере).
- [ ] Цель: `xlarge` ≤ `small` + 100 мс.

### Этап 3 — Piece Tree (средне-большие файлы, правки)
По [PieceTree.md](PieceTree.md), с одной поправкой к его плану: **исходный буфер сразу
чанкованный** (список чанков ≤ 64 КБ со своими стартами строк, как `PieceTreeTextBufferBuilder`
в VS Code), а не одна строка — иначе этап 4 переделает его заново.
- [ ] `ITextBuffer` + `ArrayLineBuffer` (текущая логика), тесты зелёные.
- [ ] `PieceTreeBuffer`: RB-дерево, `subtree.length` + `subtree.lfCount`, O(log n)
  `getLineContent`/`offsetAt`/`positionAt`, `applyEdits` с теми же `onDidChangeContent`.
- [ ] `getText()` наружу — только для потребителей с лимитом (sync, провайдеры); внутренние
  (`serialize`, QuickDiff) — через итератор чанков / строк.
- [ ] Undo — оставить inverse-edits (работает), снапшоты дерева — опционально позже.
- [ ] Метрика — латентность клавиши из этапа 0 на `xlarge`: вставка/Enter/undo не зависят от
  размера файла.

### Этап 4 — гигантские файлы: стриминг без полной загрузки
- [ ] **Стриминговое чтение**: `fs.createReadStream` чанками, инкрементальный декодер
  (`iconv.getDecoder`), BOM и EOL — по первому чанку; первые чанки — синхронно ровно на вьюпорт,
  кадр показывается, остальное дочитывается в фоне, `lineCount` растёт, статусбар показывает
  прогресс. Заготовка есть: буфер этапа 3 принимает чанки по одному.
- [ ] **Large-file режим** (аналог `editor.largeFileOptimizations`: порог по размеру/строкам,
  VS Code — 20 МБ / 300 К строк): выключить токенизацию, wrap, фолдинг, подсветку вхождений,
  QuickDiff, sync в extension host; порог — настройка.
- [ ] **Память**: цель — RSS ≈ размер файла + константа (одна копия декодированных чанков, не
  три); проверить открытие 2 ГБ файла (сейчас невозможно из-за потолка строки V8).
- [ ] **Сохранение** гигантского файла — стриминговая запись из буфера, без `serialize()` в
  строку.
- [ ] Цель: `log500m` до текста ≤ 1 с и в бенч добавляется `log2g`. `log500m` из матрицы бенча
  убран до этого этапа: на CI (2026-09-27) он открылся за 88 с, а на первой же правке (Go to Line в

  строку неделями показывал бы одинаково; генератор `kind: "log"` остался, вернуть — одна строка в
