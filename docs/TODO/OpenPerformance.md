## Откуда идём

Первый отчёт — PR #318 (CI, 4 ядра, 2026-09-27): `small` до текста 446 мс при поле бинаря 146 мс
(~300 мс «кухни» на файле любого размера), `xlarge` (13 МБ) — 3.1 с (жадные проходы по всем строкам),
`log500m` (497 МБ) — 88 с и OOM на первой правке (полная загрузка в одну JS-строку; у V8 потолок
строки ≈ 512 МБ символов).

## План

Порядок важен: сначала честная линейка, потом самое дешёвое с самым большим эффектом, пьес-три и
стриминг — когда жадные проходы сняты, иначе их выигрыш не будет виден.

### Этап 0 — линейка `[x]`

Бенч считает «наших мс» от пола `node -e ""` (не `node --version`: тот отвечает до подъёма V8) и
печатает лестницу вех из процесса (`DIODE_STARTUP_TRACE`); рабочая нагрузка после открытия (Go to
Line, вставка, Enter, undo, `Ctrl+End`, поиск), peak RSS, медиана и IQR. Чёрный и белый ящик сошлись
до миллисекунды.

### Этап 2 — жадные проходы: файл до десятков МБ открывается как маленький `[~]`

Цель: `xlarge` (13 МБ / 200 К строк) до текста ≤ `small` + 100 мс, клавиша (вставка, Enter, undo,
save) ≤ 16 мс и не зависит от размера файла. Каждый PR меряется `bench:open --sizes=small,xlarge`
до и после, цифры — в описании PR.

Исходная точка (CI 2026-10-22, `bench-data` `436e1bb`): документ собран к 196 мс, кадр с текстом —
1306 мс; клавиши — вставка 240, Enter 386, undo 308–315, save 387 мс; `Ctrl+End` уже 8 мс.

Профиль (живой редактор из исходников, 2026-10-22; абсолютные числа раздуты tsx, доли — нет):

| что | открытие | клавиши (10+10+10) | почему |
|---|--:|--:|---|
| раскраска вхождений `paintRangeBackground` | ~750 мс | ~12 с из ~15 с рендера | курсор на `const`/`export` — 200 К совпадений, каждое обходит все видимые строки: O(совпадений × строк экрана) |
| `computeWordOccurrences` | — | 1.8 с | синхронно в рендере, на каждой правке, по всему файлу |
| `LineWidthCache.getMaxWidth` | ~1.8 с | 1.5 с | первый кадр меряет все строки `measureTextWidth`; после правки — максимум по всем |
| `buildProjection` | ~220 мс | 4.3 с | пересобирается целиком на каждой правке (`ensureCursorVisible`, рендер) |
| `recomputeFoldingRegions` | ~95 мс | 0.6 с | indentation-фолдинг синхронно на каждой правке |
| `pushInitialState` | 140 мс | — | после кадра, но держит поток |

Эталон: вхождения — асинхронно с задержкой `occurrencesHighlightDelay`, рисуются декорациями,
которые спрашиваются по диапазону вьюпорта; ширина контента растёт по мере отрисованных строк;
проекция строк правится по месту (префиксные суммы); indentation-фолдинг — асинхронно с капом
5000 регионов (`MAX_FOLDING_REGIONS_FOR_INDENT_DEFAULT`); sync с extension host — до 50 МБ
(`_MODEL_SYNC_LIMIT`).

PR по порядку (последовательно в одном worktree: 1, 2, 4 правят `editorElement.ts` и
`editorViewState.ts`):

- [x] **1. Вхождения и совпадения поиска — только видимая область** (#780). Двоичный поиск по
  отсортированным диапазонам, строки экрана разрешаются раз за кадр; вхождения ищутся после кадра, с
  задержкой эталона (50 мс), а правка их снимает (`_stopAll` эталона, не сдвиг) до следующего явного
  движения каретки. Тот же путь у Find. Метки на полосе прокрутки (#776) показывают все вхождения
  (решение человека 2026-10-22: «хочется видеть их все в маркерах»), но считаются раз на изменение
  источника, а не на кадр. Локально (4 ядра, медианы) до → после: `xlarge` до текста 2521 → 2138 мс
  (`small` 230 → 212); вставка 419 → 77, Enter 548 → 55, undo 461–511 → 39–46, save 426 → 152 мс.
  Остаток клавиши — пункты 2–5 (`buildProjection`, ширина, фолдинг, sync).
- [ ] **1a. tuidom: раскладка меток скроллбара — раз на массив.** `getScrollBarMarkerCells` строит
  клетки заново каждый кадр: на 200 тыс. меток (курсор на `export` в xlarge) — 60–110 мс на кадр
  прокрутки или движения каретки. diode после PR 1 отдаёт тот же массив, пока источники не
  менялись, — движку хватит мемоизации по `(markers, trackHeight, contentHeight)`. PR в tuidom,
  публикация — по разрешению человека. На клавиши не влияет: правка снимает вхождения.
- [x] **2. `buildProjection` без пересборки на правку** (#786). `IViewProjection`
  (`viewModel/viewProjection.ts`): без свёрнутых фолдов, wrap и зон — тождественная проекция без
  массивов; иначе правки сливаются в один диапазон строк и накатываются на месте, как
  `onModelLinesInserted/Deleted` эталона; пересчёт фолдинга, не изменивший свёрнутые диапазоны, кэш не
  трогает. `detectIndentation` — один раз за открытие (панель строится с базой `editor.*`). Локально
  (4 ядра, медианы, два чередующихся прохода до/после): `xlarge` до текста 2159/2269 → 2021/2068 мс
  (`small` 230 → 226–244); вставка 108/242 → 97/100, Enter 71/98 → 47/66, undo (char) 43/32 → 23/25,
  undo (Enter) 64/56 → 64/62, save 167/136 → 176/151 мс. В процессе на 200 К строк: правка 0,2 мс без
  фолдов, 0,8 мс со свёрнутым регионом, 1–1,8 мс с wrap (полная сборка — 23 мс; первое включение wrap
  на 200 К строк считает все переносы — 3,6 с, отдельный хвост `LineBreaksCache`). Остаток клавиши —
  пункты 3–5.
- [~] **3. Ширина контента лениво.** Видимые строки сразу, остальное — фоном idle-чанками,
  горизонтальный скролл растёт по мере измерения; на правке — только тронутые строки. ASCII-фастпас в
  `measureTextWidth` — PR в tuidom.
- [x] **4. Фолдинг лениво** (#787). Как `FoldingController.updateScheduler` эталона: открытие, правка
  и смена реестра провайдеров взводят `RunOnceScheduler` с адаптивной задержкой `FeatureDebounce`
  (`{ min: 200 }`: 300 мс до первого замера, дальше среднее время пересчёта с ответом провайдера);
  правка отменяет запрос в полёте, проход по отступам с провайдером — только после его ответа;
  перезагрузка (`isFlush`) — сразу. Кап — `editor.foldingMaximumRegions` (ключ, дефолт 5000 и описание
  эталона), режет объединённый список по уровню вложенности. Локально (4 ядра, медианы, два
  чередующихся прохода до/после): `xlarge` до текста 2073/2215 → 2104/1980 мс (шум, IQR до 400 мс —
  кадр держит ширина, пункт 3); вставка 67/38 → 71/61, Enter 57/44 → 28/30, undo (Enter) 32/30 →
  17/22, undo (char) 24/28 → 19/19, save 138/134 → 149/143 мс. Профиль живого бинаря: «вставка» и
  первые два Enter после Go to Line упираются в фоновую токенизацию, догоняющую вьюпорт (~3 с главного
  потока по 1 мс на `setImmediate`, сама клавиша ~15 мс) — это к бенчу (пункт 6: дать токенизации
  осесть или не гейтить `insert`) и к этапу 3 (токенизация от вьюпорта, воркер B3); один undo —
  245 мс паузы GC. Фолдинг в серии из 30 правок — два пересчёта по 60 мс вместо 30 синхронных по 16–45.
  Остаток клавиши — пункты 3 и 5.
- [ ] **5. Document sync.** Снапшот — только при живом `rpc`, строками; лимит — по эталону (50 МБ,
  константа). Часть может уехать в этап 4.
- [ ] **6. Гейт.** Бюджет `xlarge` до текста и бюджет клавиши на `xlarge` — в перф-гейт CI.

### Этап 4 — гигантские файлы: отдельный режим «только чтение» со стримингом `[ ]`

Решение человека 2026-10-22: до поста; гигантский файл — **отдельный режим**: открывается только
для чтения сразу и стримингом, редактирование — по кнопке в тосте; follow (`tail -f`) для логов — в
первой версии. Прецедент эталона — уведомление большого файла «tokenization, wrapping, folding … turned
off» с кнопкой «Forcefully Enable Features»; режим «на диске без лимита размера» — отступление: эталон
читает файл в память целиком.

- [ ] **Порог и режим.** Аналог `editor.largeFileOptimizations` (эталон — 20 МБ / 300 К строк, порог —
  настройка): файл выше порога открывается read-only, выключены токенизация, wrap, фолдинг, вхождения,
  QuickDiff, sync в extension host.
- [ ] **Документ на диске.** Свой `ITextDocument` поверх файла: разреженный индекс строк строится
  потоково, страницы читаются по требованию (`fs.read`) с LRU-кэшем; первый экран — синхронно,
  `lineCount` растёт, статус-бар показывает прогресс. Память — константа + индекс, размер файла не
  ограничен потолком строки V8. Кодировки: UTF-8/ASCII напрямую; iconv-кодировки — вопрос (iconv-lite
  0.7.3 теряет символы gb18030 на границе куска).
- [ ] **Тост «Enable editing».** Переход в обычную модель: стриминговое чтение в PieceTree (заготовка
  A4 — куски и потоковый декодер `encodingStream.ts`) с прогрессом; отказ, если файл не влезает в кучу.
  Сюда же — асинхронная загрузка модели (FileService PR 5).
- [ ] **Follow.** Дописанное в конец подхватывается (watcher → дочитать хвост, дорастить индекс);
  курсор на последней строке — экран едет за хвостом. Усечение/ротация файла — перечитка.
- [ ] **Поиск** по файлу на диске — фоном порциями, с капом совпадений (эталон — 19 999).
- [ ] **Сохранение** гигантского файла в режиме правки — стриминговая запись из буфера (снимок →
  `encodeChunks`, A4); остался один буфер байтов на `IFileService.writeFile`.
- [ ] **Перечитка с диска** (revert, авто-перечитка чистого буфера) — `setText` полной заменой одним
  flush-событием, как `IModelService.updateModel` эталона; решить, нужен ли дифф вместо замены.
- [ ] Цель: `log500m` до текста ≤ 100 мс над `small`, в бенч возвращается `log500m` и добавляется
  `log2g`/`log20g`; follow — латентность дописанной строки до кадра. `log500m` из матрицы бенча убран
  до этого этапа (CI 2026-09-27: 88 с на открытие, OOM на первой правке); генератор `kind: "log"`
  остался, вернуть — одна строка в `SIZES`.
