# Полный прогон гейтов стоит час: где время и что с этим делать

Статус: `[~]` в работе — ходы 1 и 2 (`--ignoreStatic` локально, `--incremental` локально и в
CI, перепроверка всех выживших) сделаны в ветке `worktree-mutation-incremental`; остальное открыто.

Замеры сделаны 2026-09-26 на скоупе влитого PR #297 (редактор кейбиндов: 18 файлов,
850 мутантов, 43 записи в `--mutate`) на машине 16 ядер / 62 ГБ. Чтобы числа переносились
на слабую машину, кроме wall-time мерялись **CPU-минуты** (user+sys всего дерева процессов)
и **пиковый RSS** дерева. Скрипты и сырые логи прогонов — в сеансе, повторить можно по
командам ниже.

## Из чего складывается час

Один полный локальный проход «как требует AGENTS.md» перед сдачей фичи:

| Гейт | 16 ядер, wall | CPU-мин | Пик RSS | На 4 ядрах (замер/оценка) |
|---|--:|--:|--:|--:|
| `npm run typecheck` | 14 с | — | — | ~0,5 мин |
| `npm run lint` | 47 с | — | — | ~1,5 мин |
| `npm test` (694 файла, 7667 тестов) | 41 с | 4,5 | 5,3 ГБ (16 форков) | **2 мин 10 с** (замер, 2,1 ГБ) |
| `npm run test:mutation` как есть (со статикой) | 9 мин 57 с | **115** | 18,8 ГБ (8 воркеров) | **~35–40 мин** |
| … то же с `--ignoreStatic` (как в CI) | 4 мин 39 с | 45,6 | 16,4 ГБ | ~12–15 мин (CI на 2 ядрах: 15 мин) |
| `npm run test:e2e` (51 файл, 8 воркеров) | 3 мин 29 с | 6,2 | 4,1 ГБ | **6 мин 51 с** (замер, 2 воркера, 2,3 ГБ) |

Итого без единой красной итерации: на 4 ядрах ≈ 45–60 минут, и почти всё это —
мутационный гейт. Любая красная итерация (выживший, флак) повторяет круг.

CI на PR сегодня: 17–20 минут wall на пуш (самый долгий job — `mutation`, 15–17 мин на
2-ядерном раннере). На PR #342 гейт мутаций был красным пять прогонов подряд (2,5 часа),
PR влит `--admin`.

## Куда уходит CPU в мутационном гейте

- **Статические мутанты.** 98 из 850 (12%), но на каждого гоняется весь related-набор
  (~850 тестов, ~45 CPU-с на мутанта) — **≈70 из 115 CPU-минут**. Из 16 выживших в
  прогоне со статикой 15 — статические, почти все `StringLiteral` в UI-строках
  (`keybindingRecorderComponent.ts:31` ×7 и т.п.), то есть эквивалентные по смыслу.
  Локальный `npm run test:mutation` статику **не** пропускает — только CI (`--ignoreStatic`).
- **Накладные на каждый прогон мутанта.** В среднем 9,3 теста на мутанта, тело
  теста ≈ 35 мс (268 с тестов / 7667) — то есть ≈0,3 с полезной работы на мутанта при
  ≈2,8 с фактических. Остальное — цикл Stryker ↔ vitest (`ctx.start()` на мутанта);
  изоляция модулей тут ни при чём — проверено ниже.
- **Dry run.** 36 с на 2223 related-теста (одним воркером, `maxWorkers: 1` — так
  устроен `vitest-runner`) — плюс перепроверка потерянных по bail (ещё ~25 с).

## Что проверено экспериментально

### `--incremental` (Stryker) — работает, экономия на порядок

| Прогон | wall | CPU-мин | Переиспользовано |
|---|--:|--:|--:|
| первый (`--ignoreStatic --incremental`) | 4 мин 09 с | 42,7 | — |
| повтор без изменений | **45 с** | 2,7 | 699 из 850 |
| после добавленного теста в `keybindingPortability.test.ts` | 43 с | 3,3 | 677 из 850 |
| после правки исходника `keybindingPortability.ts` | 43 с | 3,2 | — |

Переиспользуется результат мутанта, если код в его месте не менялся и (для убитого)
не менялся убивший тест, (для выжившего) не добавились тесты. Это ровно цикл
«выживший → добавил тест → перегнал»: он становится минутой вместо пяти (на 4 ядрах —
минутой вместо пятнадцати).

Нюанс, который надо закрыть при внедрении: «выжившие» из потерянных по bail прогонов
(`testsCompleted: 0`, см. TESTING.md) тоже переиспользуются как Survived, поэтому
перепроверку из `scripts/mutation-diff.mjs` надо оставить (теперь это вживление
точного мутанта, `scripts/verify-mutants.mjs`).
Файл `reports/stryker-incremental.json` — 3,9 МБ, в CI его можно класть в
`actions/cache` по ключу ветки.

### `--ignoreStatic` локально — бесплатные 70 CPU-минут

Локально статику гоняет каждый, а по смыслу её уже отдали ночному прогону
(`mutation.yml`). Паритет с CI = `--ignoreStatic` в `package.json` (или в
`stryker.config.json`), ночной прогон без него.

### `isolate: false` для прогонов Stryker — проверено, выигрыша нет

Гипотеза была: 2,8 с на мутанта при 0,3 с полезной работы — это переимпорт графа
модулей на каждый прогон, и `isolate: false` его уберёт. Замер на подмножестве
(4 файла, 227 мутантов, `vitest.configFile` с `isolate: false`, применение флага
проверено по `--logLevel debug`):

| | wall | CPU-мин |
|---|--:|--:|
| `isolate: true` (как сейчас) | 49 с | 7,5 |
| `isolate: false` | 48 с | 6,6 |

Разницы нет: накладные на мутанта сидят в самом цикле Stryker ↔ vitest
(`ctx.start()` на каждого мутанта: сбор, RPC воркеру, сброс состояния), а не в
изоляции модулей. Побочно: `npx vitest run --no-isolate` роняет 29 тестов в 10 файлах
(утечка `vi.mock` на `child_process` из `extensions/git/lib/gitShow.test.ts`,
состояние `extensionHost.*`) — гигиена сама по себе полезная, но за скоростью
мутаций сюда идти не надо.

Вывод для стратегии: **удешевить один прогон мутанта нечем — сокращать надо число
прогонов** (статика, incremental, шардинг по машинам).

### `vitest.related: false` (лечит фантомных выживших из MutationGateFlake.md) — упёрлось

С `related: false` dry run гоняет все 694 файла и падает на 7-й секунде:
`diffing fixtures (upstream corpus) difficult-move` — вне Stryker этот тест зелёный
(59/59). Значит, в песочнице Stryker'а весь набор целиком пока не живёт; прежде чем
мерить цену, надо понять, что именно ломает этот тест (копирование в sandbox или
порядок в одном потоке).

**Причина найдена (2026-10):** `disableTypeChecks` Stryker'а по умолчанию
дописывает `// @ts-nocheck` в начало каждого `.js/.ts` под `src/` в песочнице —
в том числе в фикстуры diff-корпуса `difficult-move/1.js`/`2.js`, и номера строк
ожидаемого diff'а съезжают на одну (воспроизводится вне Stryker'а той же
вставкой). В `stryker.config.json` теперь `"disableTypeChecks": false`: vitest
транспилирует esbuild'ом и типы не проверяет, так что директива не нужна вовсе.
Падал от этого не только `related: false`, но и обычный PR-гейт, если связанный
набор мутируемого файла доходил до diff-корпуса.

### Флаки

- **Юнит-набор сам по себе не флейкает под нагрузкой**: 3 из 3 прогонов на 4 ядрах
  (`taskset -c 0-3`) зелёные, 2 из 2 на 16 — тоже.
- **Dry run Stryker'а флейкает**: 2 из 4 dry run'ов на одном коммите упали на
  `workbench.preferences.test.ts › рекордер пишет комбинацию` (`vi.waitFor` с дефолтным
  таймаутом 1 с, ждёт файл на диске). Отдельно файл 3/3 зелёный. В dry run все
  related-тесты идут **одним воркером с `bail: 1`**, и падение одного теста = весь
  гейт с нуля (на 4 ядрах — минус 15 минут). Дефолтный `vi.waitFor` без таймаута
  встречается в 36 местах (editorGroups ×10, терминал ×18).
- **Параллельный e2e ломает сам себя.** `selfextract.test.ts` и `lspBundled.test.ts`
  зовут `build:selfextract`, тот — общий `buildDistArtifacts` с `tsup clean: true`,
  который **сносит `dist/`** вместе с уже собранным `dist/diode`. Соседние воркеры
  видят, что бинаря нет, и пересобирают его (`npm run build:sea` ×2 в середине
  прогона, `Couldn't write output executable: dist/diode: text file is busy`), а их
  тесты падают каскадом: `ws connect to ws://127.0.0.1:… timed out`. На main с 8
  воркерами — 14 упавших в 10 файлах, при этом три лишние сборки (tsup + `--build-sea`
  150 МБ) съедают и память, и CPU. В CI не видно: там `DIODE_E2E_WORKERS: '1'`.
  Это и есть «e2e память поедает» на слабой машине: воркеров там `cpus/2`, и каждый
  может уйти в пересборку.

### e2e: цена инстанса

Один инстанс редактора в e2e ≈ 330 МБ RSS; LSP-сьюты сверху держат сервер
(basedpyright 385 МБ, tsserver 356 МБ) — ≈1 ГБ на LSP-тест. При `cpus/2` воркерах на
4-ядерной машине это 2 инстанса ≈ 2 ГБ плюс сборка; сама сборка бинаря (tsup + SEA)
— ещё ~0,7 ГБ. На 4 ядрах / 2 воркерах (`taskset -c 0-3`, `DIODE_E2E_WORKERS=2`): 6 мин 51 с,
6,1 CPU-мин, пик 2,3 ГБ — и снова три сборки бинаря и два падения по той же гонке
(`ws connect … timed out`, `waitUntil(undercurl squiggle от tsserver) timed out after 120000ms`).
Wall e2e почти не зависит от ядер: это ожидания (settle, LSP-сервера), а не CPU.

Без уступок в качестве (тот же набор проверок, тот же порог):

   в ночном. 115 → 46 CPU-мин на прогон.
2. ~~**`--incremental` в `mutation-diff.mjs`**~~ — сделано: локальный дефолт и кэш по ветке в
   `ci.yml`; перепроверка расширена на всех выживших и идёт с `--force`, чтобы
   переиспользованный «выживший» не залипал. Описание — TESTING.md, «Цена прогона и
   инкрементальный режим».
3. ~~**Починить гонку сборки в e2e**~~ — затычка сделана: `globalSetup` собирает SEA и
   self-extract последовательно до воркеров (self-extract — `--reuse-dist`, без второго
   tsup и его `clean`), пути едут в `DIODE_E2E_BINARY`/`DIODE_E2E_SELFEXTRACT`, воркер
   не собирает никогда (пропавший файл — понятная ошибка, а не пересборка);
   `HeadlessSession.start` гонит подключение наперегонки со смертью процесса и добивает
   его при неудаче. Дальше (волна 2): неизменяемая сборка по хешу в
   `~/.cache/diode-e2e/<hash>`, параллельность по памяти, автоповтор упавших файлов,
   добивание LSP-внуков в своей группе процессов при `dispose`.
4. **Флак dry run'а** — таймауты `vi.waitFor` там, где ждут диск/субпроцесс, поднять
   явно (5 с не делают тест медленнее, когда он зелёный); один dry run = весь гейт.
5. **Шардинг мутаций в CI** — матрица из N job'ов по файлам скоупа (`--mutate`
   подмножество). Wall делится на N бесплатно; отчёт склеивается из N JSON.
6. **Тяжёлое — не на слабой машине.** Политику «перед сдачей — `test:mutation` и
   `test:e2e`» выполнять там, где есть ядра: CI уже гоняет оба; локально на слабой
   машине — юниты + lint + typecheck + инкрементальные мутации по тронутым файлам.
   Вариант — удалённый прогон на сильной машине под той же лизой (`claude-lease`).
7. ~~`isolate: false` для Stryker~~ — проверено, не даёт ничего (см. выше).

С явной уступкой (записать в правила, если пойдём):

8. **Ограничить e2e локально** списком сценариев по области фичи, полный набор — в CI.
9. **Мутировать только новые файлы, диапазоны в старых — не мутировать.** Сейчас
   диапазоны дают меньшую часть мутантов, экономия небольшая — скорее нет.

## Как повторить

```bash
git worktree add --detach .claude/worktrees/mutation-spike 74d6e76d   # head PR #297
node scripts/mutation-diff.mjs ea695a59 --scope-only
node scripts/mutation-diff.mjs ea695a59 --ignoreStatic --reporters json,clear-text,progress
npx stryker run --mutate "<скоуп>" --ignoreStatic --incremental      # дважды
npx vitest run --no-isolate
taskset -c 0-3 npx vitest run                                        # «4 ядра»
DIODE_E2E_WORKERS=2 taskset -c 0-3 npm run test:e2e
```
