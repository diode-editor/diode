# ExtensionUpdates — обновление и откат расширений из UI

Статус: `[~]` — план согласован 2026-10-22; этапы 0, 1, 2 и 3 сделаны (спеки ниже).

Цель: в Extensions view появляются действия для работы с версиями — ручное обновление, автообновление
и откат на нужную версию. Устройство магазина — [arch/workbench/ExtensionsView.md](../arch/workbench/ExtensionsView.md),
установка — [arch/Extensions.md](../arch/Extensions.md), формат реестра —
[arch/Marketplace.md](../arch/Marketplace.md).

## Что уже есть

- `meta/<id>.json` реестра содержит **все** версии (`engines`, `publishedAt`, `sha256`); `index.json` —
  только `latest`.
- `installFromRegistry` умеет точную версию (`options.version`: `engines` обходит, платформу — нет); с этапа 1
  её прокидывают `IExtensionsWorkbenchService.install(id, { version })` (пикер версий) и CLI
  `--install-extension id@1.2.3`, выбранная версия закрепляется (`metadata.pinned`).
- Кнопки страницы — чистая `describeExtensionButtons` (`extensionPageButtons.ts`); quick pick —
  `QuickInputService`; есть реестр настроек и `IStateService`.
- Откатиться можно кнопкой `Install Specific Version...` (этап 1); кнопка `Update to …` и `Update All`
  (этап 2) откат отменят — закрепление блокирует только автообновление (этап 3), как у эталона.

## Блокер: замена версии под живым host'ом

`installVsix` **сразу удаляет каталог прежней версии**, а extension host работает с ней до reload окна.
Всё, что подгружается лениво (`require`, грамматики, бандленные бинари LSP), ломается. Для ручного
обновления это терпимо, для фонового автообновления — нет.

## Спека этапа 0 — безопасная замена версии

Статус: реализована 2026-10-22; расхождения реализации со стартовым черновиком — в «Уточнениях при реализации» ниже. Эталон — vscode 1.127:
`platform/extensionManagement/node/extensionManagementService.ts` (`.obsolete`, `setExtensionsForRemoval`,
`deleteExtensionsMarkedForRemoval`, `cleanUp`), `extensionsWatcher.ts` (`deleteExtensionsNotInProfiles`, ключ
`id@version`), `common/extensionsProfileScannerService.ts` (`relativeLocation`).

### Проблема сегодня (по коду)

- `installVsix` (`extensionInstaller.ts`) после `rename` нового каталога **сразу** `rmSync` всех прочих
  каталогов того же id. Живой host держит путь к старому каталогу → ленивые `require`, грамматики, бинари
  LSP падают с `ENOENT`. То же — при переустановке той же версии (`rmSync(targetDir)` перед `rename`).
- `ProfileExtensions.remove` → `deleteUnusedExtensions` → `uninstallExtension` тоже удаляет каталог сразу:
  удаление расширения под живым host'ом ломает его так же.
- Профиль сопоставляется с диском **по id** (`profileKeys`, `list()`), `version`/`relativeLocation` в
  `extensions.json` — справочные. `main.ts` сканирует **все** каталоги `extensions/` и фильтрует по id;
  `mergeExtensions` при двух версиях берёт первую по порядку `readdir` — недетерминированно.
- `installPrepared` при откате зовёт `uninstallExtension(id)` — снесёт **все** версии id, а не только
  что поставил.

### Модель (как у эталона)

- На диске в `extensions/` может лежать **несколько версий** одного id: `<id>-<version>/`.
- Какая версия у профиля — решает запись `extensions.json` (`relativeLocation`, запасной путь —
  `<id>-<version>`). Каталог, на который не ссылается ни один профиль, — **кандидат на удаление**.
- Кандидат не удаляется сразу, а помечается в `extensions/.obsolete` — JSON-объект
  `{ "<id>-<version>": true }`, формат эталона (ключ = имя каталога). Каталог удаляется на **старте
  редактора** (cleanup) до сканирования расширений.
- Версия опознаётся по **имени каталога** (`<id>-<version>`, ключ `.obsolete` и `relativeLocation`):
  профили сравниваются с диском по каталогу, в который разрешилась их запись, — это и есть
  `id@version` эталона (`getKey` в `extensionsWatcher.ts`), но без отдельной нормализации регистра.

### Поведение (пользовательские истории — по ним тесты)

- **US-0.1 Обновление под живым host'ом.** Окно работает с `acme.demo@1.0.0`; обновляем до `1.1.0`
  (кнопка `Update to 1.1.0` или CLI `--install-extension acme.demo` из другого терминала). Каталог
  `acme.demo-1.0.0/` остаётся нетронутым, команда расширения, которая лениво подгружает модуль, продолжает
  работать до reload. `extensions.json` профиля указывает на `1.1.0`, в `.obsolete` — `acme.demo-1.0.0`.
- **US-0.2 Reload подхватывает новую версию.** После reload (или нового запуска) host грузит `1.1.0`,
  каталог `1.0.0` удалён, ключ убран из `.obsolete`; если записей не осталось — файла `.obsolete` нет.
  На диске одна версия.
- **US-0.3 Детерминированный выбор.** На диске `1.0.0` и `1.1.0`, профиль ссылается на `1.0.0` → грузится
  `1.0.0`, независимо от порядка `readdir`. Профиль сильнее пометки: каталог из `.obsolete`, на который
  ссылается профиль, установлен и для `--list-extensions`, и для окна; ключ снимает ближайшая запись
  (cleanup, `add`, `remove`).
- **US-0.4 Удаление под живым host'ом.** `Uninstall` (UI или `--uninstall-extension`): запись уходит из
  профиля, каталог — в `.obsolete`, а не `rmSync`; удаляется на следующем старте. Если каталог нужен
  другому профилю — не помечается (как сегодня «kept on disk»).
- **US-0.5 Возврат помеченной версии.** Поставили `1.1.0` поверх `1.0.0` и тут же снова ставим `1.0.0`
  (основа отката этапа 1, а сейчас — `--install-extension ./acme.demo-1.0.0.vsix`): ключ `1.0.0` снимается
  с `.obsolete`, в `.obsolete` уходит `1.1.0`. Из реестра каталог той же версии, не помеченный и целый
  (`package.json` читается, id/версия совпадают), **переиспользуется** без распаковки (эталон:
  `extractUserExtension(removeIfExists=false)`); `.vsix` той же версии всегда заменяет каталог
  (эталон: «Installing a VSIX extension shall replace the existing extension always»). То же для
  зависимости: каталог из `.obsolete`, который новая установка взяла как уже стоящую зависимость, получает
  запись в профиле и снимается с `.obsolete`.
- **US-0.6 Профили независимы.** Обновление в профиле A не трогает запись профиля B: B остаётся на `1.0.0`,
  оба каталога живут, пока на них кто-то ссылается (решение В2 ниже).
- **US-0.7 Откат при ошибке установки корня.** Если установка корня падает после установки зависимостей
  (битый архив, `EACCES`/`ENOSPC` при распаковке), откат удаляет **ровно те каталоги** `<id>-<version>`, что
  создал этот вызов, и свой временный каталог распаковки; прежние версии не трогает. CLI завершается
  сообщением об ошибке и кодом 1, а не падением процесса со стеком Node.
- **US-0.8 Удаление профиля.** Как сегодня, только через `.obsolete`: версии, на которые больше не
  ссылается ни один профиль, помечаются, удаляются на старте.
- **US-0.9 Старые `extensions.json`.** Запись без `relativeLocation` → каталог `<id>-<version>`; нет и его →
  единственный непомеченный каталог с этим id на диске, при нескольких — наибольшая semver среди
  непомеченных, с `warn` в лог. Файл при
  этом не переписывается (ровно как сегодня: чужое содержимое не трогаем).
- **US-0.10 Cleanup безопасен.** Битый
  `.obsolete` (не JSON-объект) → `error` в лог, ничего не удаляется, старт продолжается. Ошибка удаления
  одного каталога → `warn`, ключ остаётся в `.obsolete` до следующего старта, остальные удаляются.
  Каталог из `.obsolete`, на который снова ссылается профиль, не удаляется, ключ снимается. Каталог, на
  который не ссылается ни один профиль и которого нет в `.obsolete` (сирота упавшей установки, положенный
  руками), помечается и удаляется на следующем старте, как `deleteExtensionsNotInProfiles` эталона.
  Сломанная распаковка (файл и каталог на одном пути, `EACCES`, `ENOSPC`) — отказ с сообщением и откат,
  а не падение процесса.
- **US-0.11 CLI.** `--list-extensions` показывает версию профиля, а не «какую-то с диска». CLI сам
  ничего не удаляет из `.obsolete` (cleanup — только старт редактора, решение В1). Сообщение
  `Removed previous version(s): …` меняется на `Previous version(s) will be removed on next start: …`.
- **US-0.12 Несколько окон (решение В1).** Окно A работает на `1.0.0`, обновление до `1.1.0`, стартует окно B:
  B грузит `1.1.0`, каталог `1.0.0` остаётся (его держит аренда A), команда в A по-прежнему отвечает `1.0.0`.
  Когда A вышло (или убито — аренда мёртвого pid не в счёт), следующий старт удаляет `1.0.0`. Reload окна —
  тоже выход: супервизор снимает аренду до перезапуска.

### Устройство (что меняется)

- `extensionInstaller.ts`
  - `installVsix` не удаляет прочие версии; той же версии — замена через переименование старого каталога в
    `<name>.<hex>.vsctmp` (эталон: `DELETED_FOLDER_POSTFIX = '.vsctmp'`) и удаление сразу, как эталон;
    неудалённый помечается в `.obsolete` и уходит на cleanup. Возвращает `{ id, version, dir }`.
  - `uninstallExtension(id)` → `deleteExtensionDir(dir)` по конкретному каталогу (для отката и cleanup).
  - `readInstalled` пропускает служебное: всё, что начинается с точки (`.obsolete`, `.inuse`,
    `.vsix-install-<pid>-*`), и `*.vsctmp`. Временный каталог распаковки несёт pid установщика: cleanup
    удаляет только брошенные мёртвыми процессами.
- Новый модуль `obsoleteExtensions.ts` (рядом, `node/`): `readObsolete`, `markObsolete(keys)`,
  `unmarkObsolete(keys)`, аренды `writeExtensionLease`/`releaseExtensionLease`,
  `cleanUpExtensions(extensionsDir, { referencedDirs, logger })` — профили читаются лениво
  (`referencedExtensionDirs` из `profileExtensions.ts`), только если `.obsolete` есть. Запись — через temp +
  `rename`, как `writeProfileExtensions`. Межпроцессной блокировки нет, как и у `extensions.json`
  сегодня (гонка CLI и окна — вне этапа, записать в трекер).
- `profileExtensions.ts`
  - `list()` разрешает каждую запись в каталог (`relativeLocation` → `<id>-<version>` → US-0.9) и
    отбрасывает помеченные в `.obsolete`.
  - `add([{ id, dir }])` пишет запись с **версией и каталогом только что установленной** версии;
    зависимость, уже записанная в профиле, сохраняет запись. После записи — `markUnusedExtensions` по
    затронутым id; возвращает `{ obsolete }` — для сообщения CLI.
  - `deleteUnusedExtensions` → `markUnusedExtensions`: сравнение по каталогу, а не по id; версии
    затронутых id, на которые снова ссылается профиль, снимаются с `.obsolete` (US-0.5).
  - Комментарий-«Deviation from upstream: one version serves all profiles» убирается.
- `main.ts`: сканирует пользовательские расширения и оставляет только каталоги из
  `ProfileExtensions.list()` (по `dir`, а не по id). `cleanUpExtensions` — в `openProfiles` только для
  редактора, до `scanExtensions`, под try/catch с логом (старт не падает).
- `installFromRegistry.ts`: `installPrepared` откатывает по `dir`; `prepareDependencies` по-прежнему
  считает зависимость установленной при любой версии **в этом профиле или на диске** (как сейчас).
- Доки: [arch/Extensions.md](../arch/Extensions.md) — раздел про каталог расширений и `.obsolete`;
  [TODO/Profiles.md](Profiles.md) — «версия на диске одна на все профили» больше не верно.

### Решения человека (дефолт принимается, если нет ответа до старта кода)

**Приняты дефолты В1а, В2а, В3 — решение по дедлайну** (2026-10-22: «запускай» без выбора альтернатив).

- **В1. Несколько окон diode = несколько процессов.** У эталона cleanup идёт на старте shared process —
  когда других окон нет. У нас второе окно, стартуя, удалит каталог, на котором работает первое.
  - **(дефолт) а) Аренды:** каждый процесс редактора пишет `extensions/.inuse/<pid>.json` со списком
    загруженных каталогов (и удаляет на выходе); cleanup не трогает каталоги живых pid
    (`process.kill(pid, 0)`), файлы мёртвых pid чистит. Цена — +1 модуль и ~1 день; отступление от
    эталона, оправдано моделью процессов.
  - б) Как эталон, без защиты; риск — поломка соседнего окна до его reload. Цена — 0.
- **В2. Версия по профилю.** (дефолт) а) как эталон: у каждого профиля своя версия, обновление касается
  текущего профиля (US-0.6). Цена — профиль B не получит обновление, пока его не обновят в B; меняет
  предпосылку открытого вопроса про `pinned` ниже (снимается: `pinned` естественно по профилю).
  б) обновление переписывает запись во всех профилях с этим id — сохраняется «одна версия на диске»,
  но откат этапа 1 тогда тоже глобальный.
- **В3. `.vsix` той же версии под живым host'ом** — (дефолт) замена, как эталон (US-0.5); старый каталог
  переименовывается в `*.vsctmp` перед удалением, так что работающий host с уже открытыми файлами
  живёт, но ленивые `require` по старому пути сломаются. Альтернатива — отказ «Reload the window before
  reinstalling the same version» (эталон так делает, когда удаление не удалось).

### Уточнения при реализации

- Постфикс удаляемого каталога — эталонный `.vsctmp`, а не придуманный `.deleted`; и удаляется он сразу
  (как эталон), cleanup — только запасной путь.
- Cleanup на каждом старте редактора читает листинг `extensions/` и профили (после решения 2 ниже —
  иначе сирот не найти): сметает `*.vsctmp` и `.vsix-install-<pid>-*` мёртвых pid, помечает сирот. Нет
  каталога `extensions/` — не читает и профили.
- Нечитаемый профиль: `list` — пусто и `error` (как было), пометка и cleanup — ничего не делают
  (`warn`/`error`): неизвестно, что профиль держит.
- Каталог с нестандартным именем (фикстура `tab-setter`) находится по манифесту: запись без
  `relativeLocation` сопоставляется с каталогом этого id и той же версии.
- Первый reload превращает процесс в супервизора — он снимает свою аренду до перезапуска, иначе
  его pid навсегда держал бы старые каталоги.
- `migrateProfileExtensions` при нескольких версиях на диске пишет одну — наибольшую непомеченную.

### Решения по отчёту приёмки (2026-10-23, дефолты родительской сессии — решение по дедлайну)

Человек сказал «чини и вливай»; каждое решение можно переиграть.

1. **US-0.3 ↔ US-0.10: профиль сильнее пометки.** `list()` (а с ним `--list-extensions`) показывает

## Спека этапа 1 — конкретная версия и откат

Статус: реализована 2026-10-23; решения Д1–Д4 приняты по умолчанию (по дедлайну). Эталон — vscode 1.127:

`extensionsWorkbenchService.ts` (`pinned`, `outdated`), `platform/extensionManagement/common/
abstractExtensionManagementService.ts` и `node/extensionManagementService.ts` (`installGivenVersion` →

### Что есть после этапа 0 (по коду)

  каталог той же версии переиспользуется, помеченный в `.obsolete` — снимается с пометки. Откат на
  старую версию на уровне диска уже безопасен (этап 0, US-0.5).
- `IExtensionsWorkbenchService.install(id)` версию не принимает; `IExtensionListEntry` про `pinned` не знает.
- `ProfileExtensions.add` переписывает запись расширения заново (`toStoredExtension`): посторонние поля
  записи, в том числе `metadata`, при обновлении **теряются** (сохраняются только у нетронутых записей).
- CLI `--install-extension id@1.2.3` ищет в реестре id `id@1.2.3` → «not found».
- На странице — только кнопки `describeExtensionButtons` (`install`/`update`/`uninstall`/`reload`);

- Quick pick — `QuickInputServiceDIToken`, `quickPick({...})` (пример — `encodingActions.ts`).
- `meta/<id>.json` содержит все версии с `engines`, `targetPlatform`, необязательным `publishedAt`.

### Модель

- **Установка заданной версии** = установка из реестра с `version` (как `installGivenVersion` у эталона).
  Она **закрепляет** версию: `metadata.pinned: true` в записи `extensions.json` текущего профиля
  (по профилю — решение В2 этапа 0).
- Правило `pinned` при записи (эталон: `pinned: installGivenVersion ? true : (options.pinned ?? existing.pinned)`):
  - заданная версия (пикер, CLI `id@version`, CLI `.vsix`) → `true`;
  - обычная установка/обновление → сохраняется прежнее значение записи (нет записи → не закреплено);
  - зависимости → никогда не закрепляются (эталон: `pinned: false` для dep-задач): зависимость, которую
    приносит установка, пишется без `pinned`; запись зависимости, которая уже была в профиле, и её `pinned`
    не трогаются (`ProfileExtensions.add(roots, { pinned, dependencies })`; найдено тестировщиком, отчёт в #785);
  - удаление из профиля стирает запись вместе с `pinned`.
- Прочие поля `metadata` записи при перезаписи сохраняются (эталон хранит там больше, чем мы знаем).
- Закрепление **не меняет** вычисление `outdated` и кнопку `Update to X` (эталон: `outdated` не смотрит на
  `pinned`; см. Д1). Его потребители — этапы 2 (`Update All`) и 3 (автообновление, переключатель).

## Спека этапа 2 — ручное обновление

Статус: сделано 2026-10-23 (уточнения — [ниже](#уточнения-при-реализации-этапа-2)). Эталон — vscode 1.127:
`workbench/contrib/extensions/browser/extensions.contribution.ts` (`workbench.extensions.action.checkForUpdates`,

`extensionsViews.ts` (запрос `@outdated`), `extensionsViewlet.ts` (бейдж числа обновлений).

### Что есть после этапа 1 (по коду)

- `availabilityOf` (`node/extensionsWorkbenchService.ts`) считает всё по `index.latest`: `latest.engines`
  несовместимы → `incompatible`, даже если в `meta` есть более новая, чем установленная, **совместимая** версия.
  Обновление на неё не предлагается, а у неустановленного кнопка `Install` выключена, хотя
  `installFromRegistry` без `version` сам выбрал бы максимальную совместимую (`resolveCompatibleVersion`).
- `latestVersion` карточки = `index.latest.version`; бейдж строки `Update X` и кнопка `Update to X` берут его.
- Строка списка уже показывает бейджи `Update X` / `Incompatible` / `Reload` (`extensionRows.ts`).
- Обновить можно только по одному, со страницы. `extensions.refresh` перечитывает индекс, но кэш `meta`
  (`metaCache`) живёт всю сессию.
- `pinned` есть в карточке (`IExtensionListEntry.pinned`), но ни на что не влияет (этап 1, Д1).
- В заголовке секции есть меню `...` для групп, отличных от `navigation` (так делает SCM); бейджей на
  контейнерах (у эталона это число на activity bar) нет.

### Модель

- **Целевая версия** расширения = максимальная **совместимая** версия реестра (`resolveCompatibleVersion` по
  `meta.versions`: платформа и `engines`). `index.latest` — целевая, только если совместима **и есть запись под
  платформу хоста или universal**; иначе — из `meta` (одна загрузка на id, тот же кэш, что у страницы). Платформ
  индекс не знает, поэтому `meta` грузится для записей с несовместимым `latest` **и** для установленных, у которых
  `latest` выше установленной (кандидат в обновление). Запросов немного, на старте сети по-прежнему нет.
  *(Поправка по отчёту приёмки PR #792, решение по дедлайну.)*
- Карточка: `latestVersion` → целевая версия (нет совместимых → `index.latest`, как сейчас, для текста
  причины); `availability`: `incompatible` только когда совместимых нет вовсе; `outdated` — когда установленная
  `<` целевой по semver. Сейчас стоит `!==`, и откат на старую закреплённую версию показывал бы «обновление» на
  более старую версию. Эталон сравнивает `semver.gt(latest, version)`.
- **Устаревшие** = установленные в профиле, известные реестру, `outdated`. Закреплённые тоже (Е1).

### Поведение (пользовательские истории — по ним тесты)

- **US-2.1 Обновление на совместимую.** Установлен `1.0.0`; в реестре `1.1.0` (совместима) и `latest` `2.0.0`
  (`engines` не подходят). Строка — `Update 1.1.0`, страница — `Update to 1.1.0`; нажатие ставит `1.1.0`. Раньше
  было `Incompatible` и ни одной кнопки.
- **US-2.2 Неустановленное с несовместимым `latest`.** Есть совместимая старшая `1.1.0` → строка без бейджа,
  страница — включённый `Install`, ставится `1.1.0`. Совместимых нет → как сейчас: `Incompatible`, выключенный
  `Install` с причиной.
- **US-2.3 Откат не выглядит обновлением.** После отката на `1.0.0` (закреплён), целевая `1.1.0` → бейдж
  `Update 1.1.0` и кнопка `Update to 1.1.0` (Д1, Е1). Установлена версия **новее** целевой (ставили `.vsix` или реестр откатил `latest`) → ни
  бейджа, ни кнопки `Update`.
- **US-2.4 Check for Updates.** Команда `workbench.extensions.action.checkForUpdates`, заголовок
  `Extensions: Check for Extension Updates`. Есть в палитре и в меню `...` заголовка секции `EXTENSIONS`, группа
  `1_updates`, порядок 1. Перечитывает индекс и **обновляет кэш `meta` после успешного чтения индекса**: целевые
  версии считаются заново, прогресс в секции, как у Refresh; при недоступном реестре список остаётся прежним
  *(поправка по отчёту приёмки PR #792)*. Итог:
  - есть устаревшие → в поиск вьюлета ставится `@outdated ` и список показывает только их (эталон
    `openSearch('@outdated ')`, Е2);
  - нет → модальное `All extensions are up to date.` (эталон `dialogService.info`);
  - реестр недоступен → его ошибка: строка `Retry — <причина>`, как у Refresh, и уведомление об ошибке, а не
    «всё актуально».
- **US-2.5 Фильтр `@outdated`.** Запрос с `@outdated` (регистр не важен, как `/@outdated/i` у эталона) оставляет
  только устаревшие. Остаток запроса фильтрует как обычно. Без каталога — пусто, а не все установленные.
- **US-2.6 Update All.** Команда `workbench.extensions.action.updateAllExtensions`, заголовок
  `Extensions: Update All Extensions`. Есть в палитре и в меню `...` секции, `1_updates`, порядок 2. Доступна по
  typed when-контексту `hasOutdatedExtensions` (имя эталона), он истинен, когда устаревших ≥ 1 по последнему
  загруженному каталогу. Устаревшие считаются **без устанавливаемых в данный момент** (эталон: `state ===
  Installed`; два `Update All` разом не ставят дважды — поправка по отчёту приёмки PR #792). Обновляет **все**
  устаревшие (Е1) обычной установкой без `version`, то есть закрепление
  сохраняется (правило этапа 1). Прогресс в окне — `Updating extensions`. Отказ одного не останавливает
  остальные.
- **US-2.7 Итог Update All.** Одно уведомление на всю пачку, а не по одному на расширение:
  - всё прошло → `Updated N extension(s). Reload the window to apply.` с кнопкой `Reload Window` (команда
    `workbench.action.reloadWindow`);
  - часть упала → `Updated N of M extensions. Failed: <id> — <причина>; …` с той же кнопкой, если обновилось хоть
    одно;
  - у обновлённых строк бейдж `Reload` (`needsReload`).
- **US-2.8 Один Reload.** После пачки, а также после нескольких обновлений по одному, кнопка `Reload Window` на
  страницах и в уведомлении одна и та же команда. Перезагрузка применяет всё разом, после неё бейджей нет.
- **US-2.9 Без каталога.** До первого показа вьюлета `hasOutdatedExtensions` ложен и `Update All` недоступна (на
  старте в сеть не ходим). `Check for Updates` доступна всегда: она сама загружает каталог.
- **US-2.10 Боковые и встроенные** в устаревшие не попадают: не известны реестру или не в профиле.
- **US-2.11 Зависимости.** Обновление корня не обновляет его зависимости, как и сейчас. Устаревшая зависимость —
  отдельная строка, `Update All` обновляет её как отдельное расширение.

### Уточнения при реализации этапа 2

Отличия от текста спеки выше (в спеке оставлены как были, здесь — как сделано):

- **Итог `Update All`** — с правильным числом: `Updated 1 extension.` / `Updated 2 extensions.`; `extension(s)` в

- **`Check for Updates` при недоступном реестре** показывает вьюлет (иначе строки `Retry —` не видно), поиск не
  трогает; уведомление — `Could not check for extension updates: <причина>`.
- **Под `@outdated` секции `MARKETPLACE` нет**: устаревшие установлены по определению, иначе каждая строка
  была бы дважды. После `Update All` под `@outdated` — `No extensions found` (как у эталона: обновлённые уже не
  устаревшие); бейдж `Reload` видно без фильтра.
- **Меню** — `ViewTitle` секции (`viewMenuVisible`), а не `ViewContainerTitle` эталона: у контейнера одна
  секция, `⋯` — то же место. `Update All` — `enablement` (`precondition` эталона): пункт виден, но выключен.
- **Бейдж `Reload` важнее `Update`** (с этапа 0): расширение, поставленное в этой сессии и ставшее устаревшим,
  в списке `@outdated` показывает `Reload`.
- **Найденный баг модальных сообщений**: `focusOnOpen` ставил фокус на контейнер диалога, и Enter не нажимал
  `[ OK ]` — `All extensions are up to date.` (и `This extension has no other versions.` этапа 1) закрывались
  только Escape. Исправлено в `notificationsComponent.ts`: при первом открытии фокус на первой кнопке, как у
  эталона.
- **`meta`** догружается до публикации нового каталога: список не мигает `incompatible` → `outdated`.
- **Отчёт приёмки PR #792** (`e2e/extensionUpdates.stage2.functional.test.ts`) нашёл два бага и мелочь, исправлены
  в том же PR, спека поправлена выше (решения по дедлайну, родительская сессия):
  1. `Check for Updates` чистил кэш `meta` **до** чтения индекса; офлайн старый индекс оставался, а цели
     пересчитывались без `meta` — устаревшая с несовместимым `latest` становилась `Incompatible`. Теперь `meta`,
     нужные целям, перечитываются после каждого успешного индекса (Refresh тоже — иначе цель бралась бы из `meta`,
     закэшированной пикером до релиза; это поймал приёмочный тест этапа 1 «после Refresh пикер видит новую
     версию»); сбой отдельной `meta` оставляет прежний ответ; `Check for Updates` вдобавок сбрасывает остальной кэш
     (страницы, пикер). `meta`, не знающая текущий `latest`, для цели не используется.
  2. Платформенная запись: новая версия только под чужую платформу выглядела обновлением, `Update All` ставил ту
     же версию и бейдж оставался — петля. Теперь `meta` грузится для каждого кандидата в обновление, и цель
     берётся из неё. У **неустановленных** записей с совместимым `latest` `meta` не грузится: карточка показывает
     `latest`, а `Install` сам выберет версию под платформу.
  3. Устанавливаемые сейчас не считаются устаревшими; `Update All` помечает всю пачку сразу.
  - В тесте приёмки «реестр пропал» последний шаг ждал `Updated 1 extension.`, хотя ставить не из чего; теперь
    ждёт `Updated 0 of 1 extensions. Failed:` — проверяет то же (команда доступна по последнему каталогу).

  посередине сдвигают следующую.
- **US-3.4 Автообновление.** `autoUpdate: on`, установлены `a` `1.0.0` и `b` `1.0.0`, в реестре по `1.1.0`
  (опубликованы давно). После фоновой проверки оба на `1.1.0` в `extensions.json` профиля, одно уведомление
  `Updated 2 extensions. Reload the window to apply.` с `Reload Window`; бейджи строк — `Reload`. Окно не
  перезагружено, старые каталоги на месте (этап 0: `.obsolete`, живой host не задет).
- **US-3.5 Закреплённые пропускаются.** Закреплённое (`pinned`) не обновляется автоматически; бейдж `Update X` и
  `Update All` для него работают, как на этапе 2 (Е1).
- **US-3.6 Задержка публикации.** Версия опубликована 30 мин назад, `autoUpdateDelay: 2` → не ставится, строка
  `Update 1.1.0`; через 1,5 ч (подменённое время) — повторная проверка и обновление. `autoUpdateDelay: 0` → сразу.
- **US-3.7 Автообновление после ручных действий.** `autoUpdate: on`, `autoCheckUpdates: false`: первый показ
  вьюлета / Refresh / `Check` с найденными обновлениями → они ставятся сами (как эталон). `Check` при этом
  всё равно ставит в поиск `@outdated ` (строки покажут `Reload`).
- **US-3.8 Переключатель на странице.** См. Ж2. По дефолту: у установленного из реестра расширения на странице
  кнопка-флажок `Auto Update` (`[x]`/`[ ]`, id команды эталона `workbench.extensions.action.toggleAutoUpdateForExtension`);
  отмечено = не закреплено. Снять → запись закрепляется на текущей версии (`pinned: true`); отметить → `pinned`
  снимается, и если расширение устаревшее и `autoUpdate: on` — обновление ставится сразу (эталон: после
  `updateAutoUpdateEnablementFor` — `eventuallyAutoUpdateExtensions`). При `autoUpdate: off` флажок выключен
  (виден, но недоступен) с подсказкой про настройку. Нет у боковых, встроенных и не установленных.
- **US-3.9 Выключили на ходу.** `autoUpdate: on` → `off` во время ожидания задержки или до следующей проверки —
  ничего не ставится, таймер задержки снят; `off` → `on` — сразу автообновление по текущему каталогу.
- **US-3.10 Офлайн.** Фоновая проверка при недоступном реестре: ни уведомлений, ни модальных окон, строки
  `Retry —` во вьюлете не появляется, если список уже был; `warn` в лог `Extensions`; следующая попытка — по
  расписанию.
- **US-3.11 Гонка с ручным.** Автообновление и `Update All`/`Update to X` не ставят одно расширение дважды
  (правило «устанавливаемые не устаревшие» этапа 2); уведомления — по одному на каждую пачку.
- **US-3.12 Два окна.** Окна проверяют независимо (у эталона один shared process — у нас нет). Перед установкой
  каждого кандидата профиль перечитывается: если запись уже на целевой версии (обновило другое окно или CLI) —
  пропуск, в итог не идёт. Итог в `extensions.json` — одна запись на id, без потерь (см. Ж4).

### Устройство (что меняется)

- `extensionsConfiguration.ts`: три настройки выше.
- `ProfileExtensions.setPinned(id, pinned)` (или `updateMetadata`, как у эталона) — меняет только `metadata`
  записи, через тот же атомарный `rename`; в контракт `IExtensionsWorkbenchService` — `setAutoUpdate(id, enabled)`
  (или `setPinned`) и признак на карточке для флажка.
- Планировщик — отдельный класс в `common/` (чистый: часы и таймеры инъецируются, никаких `Date.now`/`setTimeout`
  на уровне модуля — V8-снапшот), вклад фазы `eventually` его запускает. Кандидаты автообновления — чистая функция
  (`getOutdated` × `pinned` × задержка × сейчас) — юниты.
- Подписка на изменения настроек (`autoCheckUpdates`, `autoUpdate`, `autoUpdateDelay`).
- Итоговое уведомление — переиспользовать текст из `extensionUpdateActions.ts`.
- `describeExtensionButtons` — флажок `Auto Update`.
- Тестовый хук времени для e2e (подменённые часы/таймеры планировщика) — способ на усмотрение реализатора, без
  влияния на релизную сборку (по образцу существующих тестовых хуков инспектора).
- Доки: [arch/workbench/ExtensionsView.md](../arch/workbench/ExtensionsView.md) — расписание, настройки, флажок;
  убрать «авто-обновление» из «Чего сознательно не делаем» (пункт этапа 4 частично делается здесь).

### Уточнения при реализации этапа 3

Отличия от текста спеки выше (в спеке оставлены как были, здесь — как сделано):

- **US-3.7: после автообновления под `@outdated` строк нет**, а не «строки покажут `Reload`»: обновлённое уже не
  устаревшее (то же правило, что после `Update All` на этапе 2) — список `No extensions found`, бейдж `Reload`
  видно без фильтра. `Check` при этом ставит `@outdated ` и видит строки: автообновление идёт через секунду после
  чтения (`autoUpdateDelayer` эталона), а не синхронно.
- **Схема `extensions.autoUpdate`** перечисляет `true`/`false` рядом с `on`/`off` (`type: ["string","boolean"]`):
  у эталона схема их не отвергает, а наша валидация заменила бы `false` дефолтом `on` — вопреки Ж1. Описания —
  эталона, «a Microsoft online service» → «the extension registry».
- **Флажок при `autoUpdate: off`** — `[ ] Auto Update (extensions.autoUpdate is off)`, выключенный: подсказок
  (tooltip) у кнопок tuidom нет, причина — в подписи. Фокус после нажатия остаётся на флажке (шапка страницы при
  пересборке кнопок возвращает фокус кнопке того же вида — раньше фокус терялся).
- **Таймер задержки без фоновых проверок** (`autoCheckUpdates: false`): у эталона он зовёт проверку, которая при
  выключенной настройке ничего не делает — отложенное обновление не ставилось бы никогда. У нас — проход
  автообновления по текущему каталогу, без сети.
- **Фоновая проверка не удалась до первого списка** — ошибки нет и во вьюлете; первый показ читает каталог сам
  (иначе пустой список без причины).
- **US-3.12 шире спеки:** пропускается и запись, которую другое окно **удалило** из профиля — иначе автообновление
  ставило бы удалённое обратно. Пропущенная строка в этом окне получает `Reload` (его host работает со старой версией).
- **Отчёт приёмки PR #796** (`e2e/extensionUpdates.stage3.functional.test.ts`, реестр по HTTP) нашёл два бага, исправлены
  в том же PR; поправки спеки — решения по дедлайну (родительская сессия, предложения тестировщика):
  1. **`meta` не прочиталась — дата неизвестна**: кандидат не ставится и ждёт следующего удачного чтения (отличается
     от «нет `publishedAt` в прочитанной `meta` — задержки нет»). Раньше один ответ 500 на `meta/<id>.json` давал цель
     из индекса без даты, и свежая версия ставилась сразу, мимо задержки. `latestPublishedAt` строки: `null` — даты в
     `meta` нет, не задано — неизвестно.
  2. **Таймер задержки — не длиннее 12 ч** (дальше — обычный перерасчёт по расписанию), и никакой таймер планировщика
     не превышает 2³¹−1 мс: `AdjustableClock` взводит длинный срок частями. Раньше `autoUpdateDelay` от ~597 ч давал
     таймер больше предела `setTimeout`, Node срабатывал через 1 мс — фоновые проверки шли по кругу (с
     `TimeoutOverflowWarning` поверх TUI). У эталона тот же неограниченный `disposableTimeout`.
- **Контракт** `IExtensionsWorkbenchService`: `checkForUpdates({ background: true })`, `onDidReadCatalog(ok)`,
  `updateExtensions(ids)` (`updateAll` = он же по всем устаревшим; оба перечитывают профиль перед каждой
  установкой — US-3.12), `setPinned(id, pinned)`, `latestPublishedAt` у строки. Профиль — `ProfileExtensions.setPinned`.
- **Команда** `workbench.extensions.action.toggleAutoUpdateForExtension` (аргумент — id, без заголовка)
  регистрируется в фазе `eventually` вместе со стартом расписания; кнопка страницы идёт в
  `ExtensionPageActions.setAutoUpdate` напрямую.
- **Время в e2e** — сервис `IClock` (`platform/clock`, `AdjustableClock`) и метод инспектора `Diode.advanceClock`;
  без инспектора часы — `Date.now`/`setTimeout`.

### Вне этапа

- Бейдж с числом обновлений на контейнере — нет механики бейджей (строка этапа 2).
- Перезапуск extension host без reload окна (`extensions.autoRestart` эталона).
- Согласие на обновление, которое добавляет исполняемый код (`shouldRequireConsentToUpdate` эталона), доверенные
  издатели без задержки, лимитные подключения (`meteredConnection`).
- Автообновление встроенных расширений, пре-релизы.
- Межпроцессная блокировка — если Ж4 а).
