# ExtensionUpdates — обновление и откат расширений из UI

Статус: `[~]` — план согласован 2026-10-22; этап 0 — спека ниже, работа не начата.

Цель: в Extensions view появляются действия для работы с версиями — ручное обновление, автообновление
и откат на нужную версию. Устройство магазина — [arch/workbench/ExtensionsView.md](../arch/workbench/ExtensionsView.md),
установка — [arch/Extensions.md](../arch/Extensions.md), формат реестра —
[arch/Marketplace.md](../arch/Marketplace.md).

## Что уже есть

- `meta/<id>.json` реестра содержит **все** версии (`engines`, `publishedAt`, `sha256`); `index.json` —
  только `latest`.
- `installFromRegistry` умеет точную версию (`options.version`: `engines` обходит, платформу — нет), но
  `IExtensionsWorkbenchService.install(id)` её не прокидывает, CLI тоже (`--install-extension id@1.2.3`
  ответит «not found»).
- Кнопки страницы — чистая `describeExtensionButtons` (`extensionPageButtons.ts`); quick pick —
  `QuickInputService`; есть реестр настроек и `IStateService`.
- Сегодня откатиться можно только руками: `diode --install-extension ./publisher.name-1.2.3.vsix`, и
  первая же кнопка `Update to …` откат отменит.

## Блокер: замена версии под живым host'ом

`installVsix` **сразу удаляет каталог прежней версии**, а extension host работает с ней до reload окна.
Всё, что подгружается лениво (`require`, грамматики, бандленные бинари LSP), ломается. Для ручного
обновления это терпимо, для фонового автообновления — нет.

## Этапы (по PR на каждый)

- [~] **0. Безопасная замена версии.** Спека — [ниже](#спека-этапа-0--безопасная-замена-версии). Новая версия ставится рядом, старая помечается устаревшей (как
  `.obsolete` у эталона в `extensions/`) и удаляется на следующем старте. `ExtensionScanner` и
  `profileExtensions` берут версию из записи `extensions.json`, а не «единственный каталог с этим id».
  Тест: обновление при работающем host'е не трогает его каталог; после reload на диске одна версия.
- [ ] **1. Конкретная версия и откат.**
  - `install(id, { version? })` в контракте `IExtensionsWorkbenchService`.
  - Команда `extensions.installSpecificVersion` («Install Specific Version…») — quick pick по версиям из
    `meta`: версия, дата, `current`; несовместимые показаны с причиной (точная версия обходит `engines`,
    платформа проверяется).
  - Кнопка `Install Another Version…` на странице расширения, та же команда — в палитре.
  - **Выбранная руками версия закрепляется** (`metadata.pinned` в записи `extensions.json`, как у
    эталона): у закреплённого нет `Update to X`, есть `Unpin`. Иначе автообновление отменит откат.
  - `--install-extension id@1.2.3` в CLI (`main.ts`, прокинуть `version` в `options`).
- [ ] **2. Ручное обновление.**
  - «Последняя» — **максимальная совместимая** по `meta` (`resolveCompatibleVersion`), а не `latest`
    индекса: сейчас при несовместимом `latest` обновление на более новую совместимую не предлагается.
  - В заголовке вьюлета — `Check for Updates` и `Update All` (кроме закреплённых).
  - Бейдж `↑ X.Y.Z` на устаревших строках списка; после обновлений — один `Reload Window`.
- [ ] **3. Автообновление.**
  - Настройки как у эталона: `extensions.autoCheckUpdates` (bool), `extensions.autoUpdate` (bool;
    `onlyEnabledExtensions` не нужен — выключения расширений нет).
  - Правило «на старте в сеть не ходим» сохраняется: первая проверка — фоном после первого кадра с
    задержкой, дальше раз в 12 часов (как у эталона).
  - Пропускаем закреплённые и установленные не из магазина.
  - Итог — уведомление «Updated N extensions — Reload Window»; сами окно не перезагружаем.
  - Отключение автообновления для одного расширения — переключатель на странице, тот же `pinned`.
- [ ] **4. Доки и тесты.**
  - `ExtensionsView.md` (убрать «пикер версий» и «авто-обновление» из «сознательно не делаем»),
    `Extensions.md`, [TODO/Extensions.md](Extensions.md).
  - Герметичные e2e на файловом реестре-фикстуре с несколькими версиями одного `.vsix`: откат,
    закрепление, `Update All`, автообновление с подменённым таймером; сценарий-демо в `e2e/scenarios/`.
  - Юниты: выбор кандидатов на обновление, `describeExtensionButtons`.

Зависимости: 0 и 1 независимы; 2 — после 1 (`pinned`); 3 — после 0 и 2.

## Спека этапа 0 — безопасная замена версии

Статус: черновик 2026-10-22, по нему пишем тесты, потом код. Эталон — vscode 1.127:
`platform/extensionManagement/node/extensionManagementService.ts` (`.obsolete`, `setExtensionsForRemoval`,
`deleteExtensionsMarkedForRemoval`, `cleanUp`), `extensionsWatcher.ts` (`deleteExtensionsNotInProfiles`, ключ
`id@version`), `common/extensionsProfileScannerService.ts` (`relativeLocation`).

### Проблема сегодня (по коду)

- `installVsix` (`extensionInstaller.ts`) после `rename` нового каталога **сразу** `rmSync` всех прочих
  каталогов того же id. Живой host держит путь к старому каталогу → ленивые `require`, грамматики, бинари
  LSP падают с `ENOENT`. То же — при переустановке той же версии (`rmSync(targetDir)` перед `rename`).
- `ProfileExtensions.remove` → `deleteUnusedExtensions` → `uninstallExtension` тоже удаляет каталог сразу:
  удаление расширения под живым host'ом ломает его так же.
- Профиль сопоставляется с диском **по id** (`profileKeys`, `list()`), `version`/`relativeLocation` в
  `extensions.json` — справочные. `main.ts` сканирует **все** каталоги `extensions/` и фильтрует по id;
  `mergeExtensions` при двух версиях берёт первую по порядку `readdir` — недетерминированно.
- `installPrepared` при откате зовёт `uninstallExtension(id)` — снесёт **все** версии id, а не только
  что поставил.

### Модель (как у эталона)

- На диске в `extensions/` может лежать **несколько версий** одного id: `<id>-<version>/`.
- Какая версия у профиля — решает запись `extensions.json` (`relativeLocation`, запасной путь —
  `<id>-<version>`). Каталог, на который не ссылается ни один профиль, — **кандидат на удаление**.
- Кандидат не удаляется сразу, а помечается в `extensions/.obsolete` — JSON-объект
  `{ "<id>-<version>": true }`, формат эталона (ключ = имя каталога). Каталог удаляется на **старте
  редактора** (cleanup) до сканирования расширений.
- Ключ версии — `extensionKey(id) + "@" + version` (как `getKey` в `extensionsWatcher.ts`), регистр id
  не важен, версия — строкой.

### Поведение (пользовательские истории — по ним тесты)

- **US-0.1 Обновление под живым host'ом.** Окно работает с `acme.demo@1.0.0`; обновляем до `1.1.0`
  (кнопка `Update to 1.1.0` или CLI `--install-extension acme.demo` из другого терминала). Каталог
  `acme.demo-1.0.0/` остаётся нетронутым, команда расширения, которая лениво подгружает модуль, продолжает
  работать до reload. `extensions.json` профиля указывает на `1.1.0`, в `.obsolete` — `acme.demo-1.0.0`.
- **US-0.2 Reload подхватывает новую версию.** После reload (или нового запуска) host грузит `1.1.0`,
  каталог `1.0.0` удалён, ключ убран из `.obsolete`; если записей не осталось — файла `.obsolete` нет.
  На диске одна версия.
- **US-0.3 Детерминированный выбор.** На диске `1.0.0` и `1.1.0`, профиль ссылается на `1.0.0` → грузится
  `1.0.0`, независимо от порядка `readdir`. Каталог из `.obsolete` не грузится никогда, даже если
  на него ссылается профиль (запись битая → лог `warn`, расширение пропущено).
- **US-0.4 Удаление под живым host'ом.** `Uninstall` (UI или `--uninstall-extension`): запись уходит из
  профиля, каталог — в `.obsolete`, а не `rmSync`; удаляется на следующем старте. Если каталог нужен
  другому профилю — не помечается (как сегодня «kept on disk»).
- **US-0.5 Возврат помеченной версии.** Поставили `1.1.0` поверх `1.0.0` и тут же снова ставим `1.0.0`
  (основа отката этапа 1, а сейчас — `--install-extension ./acme.demo-1.0.0.vsix`): ключ `1.0.0` снимается
  с `.obsolete`, в `.obsolete` уходит `1.1.0`. Из реестра каталог той же версии, не помеченный и целый
  (`package.json` читается, id/версия совпадают), **переиспользуется** без распаковки (эталон:
  `extractUserExtension(removeIfExists=false)`); `.vsix` той же версии всегда заменяет каталог
  (эталон: «Installing a VSIX extension shall replace the existing extension always»).
- **US-0.6 Профили независимы.** Обновление в профиле A не трогает запись профиля B: B остаётся на `1.0.0`,
  оба каталога живут, пока на них кто-то ссылается (решение В2 ниже).
- **US-0.7 Откат при ошибке зависимости.** Если установка корня падает после установки зависимостей,
  откат удаляет **ровно те каталоги** `<id>-<version>`, что создал этот вызов; прежние версии не трогает.
- **US-0.8 Удаление профиля.** Как сегодня, только через `.obsolete`: версии, на которые больше не
  ссылается ни один профиль, помечаются, удаляются на старте.
- **US-0.9 Старые `extensions.json`.** Запись без `relativeLocation` → каталог `<id>-<version>`; нет и его →
  единственный каталог с этим id на диске, при нескольких — наибольшая semver, с `warn` в лог. Файл при
  этом не переписывается (ровно как сегодня: чужое содержимое не трогаем).
- **US-0.10 Cleanup безопасен.** Нет `.obsolete` — cleanup не читает `extensions/` целиком. Битый
  `.obsolete` (не JSON-объект) → `error` в лог, ничего не удаляется, старт продолжается. Ошибка удаления
  одного каталога → `warn`, ключ остаётся в `.obsolete` до следующего старта, остальные удаляются.
  Каталог из `.obsolete`, на который снова ссылается профиль, не удаляется, ключ снимается.
- **US-0.11 CLI.** `--list-extensions` показывает версию профиля, а не «какую-то с диска». CLI сам
  ничего не удаляет из `.obsolete` (cleanup — только старт редактора, решение В1). Сообщение
  `Removed previous version(s): …` меняется на `Previous version(s) will be removed on next start: …`.

### Устройство (что меняется)

- `extensionInstaller.ts`
  - `installVsix` не удаляет прочие версии; той же версии — замена через переименование старого каталога в
    `.<name>.<random>.deleted` и удаление его на cleanup (эталон: `DELETED_FOLDER_POSTFIX`), чтобы
    неудачный `rename` не оставил пустоты. Возвращает `{ id, version, dir, previous }`.
  - `uninstallExtension(id)` → `deleteExtensionDir(dir)` по конкретному каталогу (для отката и cleanup).
  - `readInstalled` пропускает служебное: `.obsolete`, `.vsix-install-*`, `*.deleted`.
- Новый модуль `obsoleteExtensions.ts` (рядом, `node/`): `readObsolete`, `markObsolete(keys)`,
  `unmarkObsolete(keys)`, `cleanUpExtensions(extensionsDir, profileFiles, logger)`. Запись — через temp +
  `rename`, как `writeProfileExtensions`. Межпроцессной блокировки нет, как и у `extensions.json`
  сегодня (гонка CLI и окна — вне этапа, записать в трекер).
- `profileExtensions.ts`
  - `list()` разрешает каждую запись в каталог (`relativeLocation` → `<id>-<version>` → US-0.9) и
    отбрасывает помеченные в `.obsolete`.
  - `add(ids)` пишет запись с **версией и каталогом только что установленной** версии (сейчас берёт
    «единственную с диска»); после записи — пересчёт неиспользуемых версий → `markObsolete`.
  - `deleteUnusedExtensions` → `markUnusedExtensions`: сравнение по ключу `id@version`, а не по id.
  - Комментарий-«Deviation from upstream: one version serves all profiles» убирается.
- `main.ts`: сканирует пользовательские расширения и оставляет только каталоги из
  `ProfileExtensions.list()` (по `dir`, а не по id). `cleanUpExtensions` — в `openProfiles` только для
  редактора, до `scanExtensions`, под try/catch с логом (старт не падает).
- `installFromRegistry.ts`: `installPrepared` откатывает по `dir`; `prepareDependencies` по-прежнему
  считает зависимость установленной при любой версии **в этом профиле или на диске** (как сейчас).
- Доки: [arch/Extensions.md](../arch/Extensions.md) — раздел про каталог расширений и `.obsolete`;
  [TODO/Profiles.md](Profiles.md) — «версия на диске одна на все профили» больше не верно.

- Юниты `profileExtensions.test.ts`: US-0.3, US-0.4, US-0.6, US-0.8, US-0.9; `add` пишет версию
  установленной.
- Юниты `installFromRegistry*.test.ts`: US-0.5 (переиспользование каталога из реестра), US-0.7.
- e2e `registry-install.test.ts` (CLI, реестр-фикстура с двумя версиями): обновление → обе версии на

  Перезапуск → ответ `1.1.0`, на диске один каталог.
- Мутационный гейт по новым модулям, живой запуск (`drive`) сценария US-0.1 перед сдачей.

### Решения человека (дефолт принимается, если нет ответа до старта кода)

- **В1. Несколько окон diode = несколько процессов.** У эталона cleanup идёт на старте shared process —
  когда других окон нет. У нас второе окно, стартуя, удалит каталог, на котором работает первое.
  - **(дефолт) а) Аренды:** каждый процесс редактора пишет `extensions/.inuse/<pid>.json` со списком
    загруженных каталогов (и удаляет на выходе); cleanup не трогает каталоги живых pid
    (`process.kill(pid, 0)`), файлы мёртвых pid чистит. Цена — +1 модуль и ~1 день; отступление от
    эталона, оправдано моделью процессов.
  - б) Как эталон, без защиты; риск — поломка соседнего окна до его reload. Цена — 0.
- **В2. Версия по профилю.** (дефолт) а) как эталон: у каждого профиля своя версия, обновление касается
  текущего профиля (US-0.6). Цена — профиль B не получит обновление, пока его не обновят в B; меняет
  предпосылку открытого вопроса про `pinned` ниже (снимается: `pinned` естественно по профилю).
  б) обновление переписывает запись во всех профилях с этим id — сохраняется «одна версия на диске»,
  но откат этапа 1 тогда тоже глобальный.
- **В3. `.vsix` той же версии под живым host'ом** — (дефолт) замена, как эталон (US-0.5); старый каталог
  переименовывается в `*.deleted`, а не удаляется, так что работающий host с уже открытыми файлами
  живёт, но ленивые `require` по старому пути сломаются. Альтернатива — отказ «Reload the window before
  reinstalling the same version» (эталон так делает, когда удаление не удалось).

### Вне этапа

- Межпроцессная блокировка `extensions.json` и `.obsolete` (гонка CLI и окна).
- Уведомление «нужен reload» после обновления — этап 2.

## Открытые вопросы (решает человек)

- [ ] Автообновление по умолчанию включено или выключено? Предложение: включено, как у эталона, но
  только после этапа 0.
- [ ] `pinned` — по профилю или глобально? Версия на диске одна на все профили
  ([Profiles.md](Profiles.md)), но у эталона `pinned` живёт в `extensions.json` профиля. Предложение:
  по профилю, как у эталона; при расхождении закреплено, если закреплено хоть в одном профиле.
