# [~] EnvironmentTuning — подсказки пользователю по тюнингу окружения

Трекер требований/рекомендаций к окружению (терминал, мультиплексор, SSH), от которых
зависит корректная работа редактора. Цель — научиться **детектировать** такие
ситуации и **подсказывать** пользователю, что подкрутить, а не «молча чинить» за него
(тем более не ценой регрессий вроде утечки кодировки в соседние панели tmux).

Статусы: `[ ]` — открыта, `[~]` — в работе, `[x]` — сделана.

---

## Мотивация

Часть функций редактора работает корректно только при определённых настройках
окружения, которые пользователь не обязан знать. Пример — Ctrl+Tab в tmux (см. ниже):
модификатор физически теряется на стыке kitty→tmux ещё до приложения, и никакой
конфиг diode это не чинит. Мы намеренно не подкручиваем чужой tmux из кода, поэтому
нужен механизм, который честно объяснит пользователю причину и даст рецепт.

---

## Открытый вопрос: как доносить до пользователя

Способ подачи ещё **не выбран**. Кандидаты (идеи, без обязательств):

- намёк/индикатор в статусбаре, когда обнаружено «недонастроенное» окружение;
- one-shot нотификация при старте (с возможностью «больше не показывать»);
- команда-«doctor» — отчёт по окружению со списком рекомендаций;
- запись рекомендаций в лог.

Источник сигналов у нас уже есть: `TerminalEnvironmentService`
(`src/vs/workbench/services/terminalEnvironment/node/terminalEnvironmentService.ts`) детектит
окружение и capability `extended-keys` (env-хинты + fire-and-forget проба
клавиатурного протокола). Его естественно переиспользовать как вход для подсказок.

## Список рекомендаций

Формат пункта: симптом → причина → что подкрутить.

### [ ] Linux: исчерпан лимит inotify (ENOSPC/EMFILE) — сказать это пользователю, как VS Code

- **Симптом.** На старте (или при раскрытии дерева) файловые watcher'ы отваливаются:
  ОС отказывает в новом watch'е с `ENOSPC: System limit for number of file watchers reached`
  (реже `EMFILE`). Раньше это **роняло весь редактор**: chokidar делал `emit('error')`,
  слушателя не было, EventEmitter бросал исключение из async-потрохов → процесс умирал.

- **Что уже сделано.** Watcher'ы больше не роняют процесс и пишут warn с подсказкой:
  - `ChokidarFileWatcher` и `ChokidarTreeWatcher` (`src/vs/platform/files/node/`) — канал `files.watcher`
    (обход дерева с недавних пор живёт в отдельном процессе, и его записи доезжают в тот же
    канал через протокол `treeWatcherProtocol.ts` — сообщение `log`);
  - `FileTreeDataProvider` → `ExplorerService` (`onWatchError`) — канал `filetree.watcher`;
  - общий разбор ошибки и текст подсказки — `describeFileWatchError` (`src/vs/platform/files/common/fileWatchErrors.ts`).
  Редактор при этом работает, теряется только live-reload (settings.json/keybindings.json,
  внешние изменения открытых файлов, авто-обновление ветки дерева).
  Заодно ужаты дефолты `files.watcherExclude`
  (`src/vs/workbench/common/configuration/filesConfiguration.ts`): рекурсивный watcher больше
  не заходит в `node_modules`, `.git`, каталоги сборки и кеши, и на типовом дереве в лимит
  не упирается вовсе (замер на репозитории diode: 94 176 watch'ей → 2 447). Это снижает
  вероятность ENOSPC, но не убирает его — на большом дереве или низком лимите он остаётся,
  и пункт ниже по-прежнему открыт.

- **Что осталось (главное).** Пользователь ничего не видит — только строчка в логе. VS Code
  в этой ситуации показывает **уведомление** вида «Unable to watch for file changes… ENOSPC»
  со ссылкой на инструкцию, как поднять лимит. Нам нужно то же самое, как только появится
  механизм уведомлений (см. раздел «как доносить до пользователя» выше):
  - одно уведомление на сессию (не спамить на каждый упавший watcher — их десятки);
  - текст с рецептом: `sysctl fs.inotify.max_user_watches` → поднять и записать в
    `/etc/sysctl.d/*.conf` (`fs.inotify.max_user_watches=524288`);
  - деградацию сформулировать честно: «внешние изменения файлов не отслеживаются».

- **Заодно.** Это первый кандидат на общий паттерн «редактор жив, фича деградировала» —
  такие вещи должны становиться уведомлением, а не молчаливой строкой в логе.

- **Ставка выросла.** С появлением `SharedTreeWatcher` (`src/vs/platform/files/node/`)
  на одном обходе едет несколько подписчиков, поэтому упавший по ENOSPC обход теперь
  разом лишает слежения всех, кто на нём сидел, — а `ITreeFileWatcher` такого события
  наружу не отдаёт вовсе. Уведомление станет нужнее, и вместе с ним понадобится
  канал «обход умер» до подписчиков.

- **Переезд обхода в свой процесс ничего здесь не изменил** (и не должен был):
  лимит inotify — общий для процессов пользователя, а не для одного. Что изменилось —
  цена отказа для пользователя: раньше растущее число подписок душило главный цикл
  редактора и ENOSPC приходил как «редактор отвис», теперь отклик не меняется вовсе,
  и молчание стало **единственным** признаком отказа. Замер на дереве с ~55k
  каталогов (по три прогона на сборку): отклик главного цикла до переезда —
  worst 779–901 мс и 12–13 просадок >100 мс за первые 10 с, после — worst
  46–177 мс и 0–1 просадка; обход в обоих случаях умирает по ENOSPC примерно на
  9-й секунде.

### [~] tmux + kitty: Ctrl+Tab / Ctrl+Shift+<key> не доходят (приходит голый Tab/легаси)

Расследование закрыто бисекцией по слоям (демо — `src/demos/keyDiagnosticsDemo.ts`,
оно включает те же режимы, что бэкенд, и печатает сырые байты → токены → событие →
биндинг → tier). Ниже — итог, что уже сделано в коде, и что осталось.

- **Симптом.** Внутри tmux Ctrl+Tab не переключает вкладку (приходит голый `0x09`),
  Ctrl+Shift+<буква> не приходит вовсе. Индикатор tier при этом может врать — см. ловушку ниже.

- **Где теряется (доказано бисекцией).**
  - **kitty + ssh, без tmux** → всё идеально: Ctrl+Tab = `\x1b[9;5u`, tier=kitty, полный
    протокол (release-события, репорты модификаторов). ssh байт-прозрачен, не виноват.
  - **+ tmux 3.4** (локально И по ssh) → Ctrl+Tab деградирует в `0x09`. Модификатор гибнет
    на стыке **kitty→tmux**: tmux просит расширенные клавиши у внешнего терминала через
    xterm-`modifyOtherKeys`, а **kitty его принципиально не поддерживает** (позиция автора
    kitty — только свой протокол). Запрос игнорируется, kitty остаётся в legacy, и tmux
    физически не получает Ctrl у Tab — добавить его на выходе он не может.
  - Подтверждение источником: tmux PR
    [#4038](https://github.com/tmux/tmux/pull/4038) «Improve support for extended key
    reporting modes» — переработка ровно этого; из него выросла опция `extended-keys-format`
    (csi-u/xterm). Работа **доехала в tmux 3.5**; в **3.4** опции нет (`invalid option`).
  - Вывод по версиям: **tmux 3.4 — не дожать**; **tmux 3.5+** — фикс (`extended-keys always`
    + при необходимости `set -g extended-keys-format csi-u`). См. также kitty #5508 → #4075.

- **Ловушка: индикатор tier ≠ доставка клавиш.** `extended-keys` поднимается ещё и по
  env-хинту (`KITTY_WINDOW_ID` и т.п.). Локально (без ssh) хинт на месте → tier показывает
  `csi-u`, хотя реальные расширенные клавиши tmux 3.4 НЕ доставляет. По ssh хинт срезается
  → `legacy`. Поэтому «индикатор csi-u» не равно «Ctrl+Tab работает».

- **Что уже сделано в diode (коммиты `chore:`).**
  - Бэкенд шлёт ещё и xterm-`modifyOtherKeys` (`\x1b[>4;2m`) рядом с kitty-enable
    (`tuidom/backend/nodeTerminalBackend.ts`) — это помогает терминалам/мультиплексорам, которые
    его понимают; на чистом kitty работает kitty-протокол. С tmux 3.4+kitty не спасает (см. выше).
  - Runtime-детект tier из фактически пришедшей CSI-u клавиши
    (`TerminalEnvironmentService.noteExtendedKeysObserved()` + хук в `WorkbenchComponent`) — индикатор
    и tier-gated биндинги поднимаются по реальному вводу, а не только по пробе/хинту.
  - Диагностический демо `src/demos/keyDiagnosticsDemo.ts`.

- **Что подкрутить (пользователю).**
  - **tmux 3.5+** для самого Ctrl+Tab. В `~/.tmux.conf`:
    ```tmux
    set -s extended-keys always
    set -g extended-keys-format csi-u   # только tmux ≥ 3.5
    set -as terminal-features ',*:extkeys'
    ```
  - **Фолбэк уже сейчас (любой tmux):** `Ctrl+PageDown`/`Ctrl+PageUp` (и `Alt+PageUp/Down`)
    переключают вкладки и **без** extended-keys — модификаторы на спец-клавишах кодируются
    стандартным `;mod`-параметром, который tmux пропускает всегда
    (`src/vs/workbench/Actions/TabActions.ts`).

- **Дальнейшие шаги (detect & advise — суть трекера).**
  - Детектить ситуацию «внутри tmux, но расширенные клавиши фактически не приходят» (например:
    `mode_tmux` активен, а `noteExtendedKeysObserved` так и не сработал спустя N вводов) и
    подсказать пользователю: «жми Ctrl+PageDown, либо tmux ≥ 3.5 для Ctrl+Tab».
  - Способ подачи — из раздела «как доносить» выше (статусбар/нотификация/doctor).

- **Почему не чиним кодом.** Авто-`tmux set` мутирует серверную опцию чужого tmux — отвергнуто.
  Возврат DCS passthrough для input-режимов — прошлый баг (утечка кодировки во все панели,
  ломался Ctrl+S-префикс; коммит `3d20e6f`). И главное — на tmux 3.4 проблема в самом tmux,
  кодом diode не решается в принципе.

### [ ] Мак: Cmd, Option и tmux — что подсказывать маководу

Мак-раскладка и Keyboard Doctor — [MacKeybindings](MacKeybindings.md). Доктор уже
отдаёт рецепты под опознанный эмулятор (`emulatorRecipes`), но пока только в
отчёте. Здесь — то, что надо довести до «детектим и подсказываем».

- **iTerm2 и `CSI >4;2m`.** Бэкенд шлёт modifyOtherKeys после kitty-push, а iTerm2
  трактует любой `CSI >4;n m` как сброс kitty-стека. Итог: откат в legacy, и Cmd
  уходит в меню-бар. Фикс в движке — tuidom PR
  [#13](https://github.com/tuidom/tuidom/pull/13). Живьём на iTerm2 не проверено.
- **tmux и Cmd.** У tmux три модификатора: Cmd и Option пишутся в один бит, и Cmd+S
  приезжает байт в байт как Option+S. Cmd под tmux не доезжает никогда, поэтому
  мак-рунг под tmux не выше `extended`. Подсказка пользователю: Cmd-раскладка
  только без tmux; внутри tmux — Ctrl-подслой. Для Ctrl+Shift/Ctrl+Tab нужен
  `extended-keys always` + `extended-keys-format csi-u` (tmux ≥ 3.5), см. пункт выше.
- **tmux и `LC_DIODE_PLATFORM`.** Свой env под tmux застывает на момент создания
  сессии, поэтому diode спрашивает `tmux show-environment`. Туда переменная попадает
  только с `set -ag update-environment LC_DIODE_PLATFORM`. Подсказать, если под tmux
  ОС осталась «default», а клиент — маковский терминал.
- **Рецепты эмуляторов** (не проверено, из документации):
  - iTerm2 — Left/Right Command = Super, «Apps can change how keys are reported»,
    Left Option = Esc+;
  - kitty — `macos_option_as_alt left`, снять Cmd-шорткаты, нужные редактору;
  - ghostty — `macos-option-as-alt = left`, `alt+arrow_left/right=unbind`
    (иначе шлёт legacy `ESC b`);
  - WezTerm — `enable_kitty_keyboard`,
    `send_composed_key_when_left_alt_is_pressed = false`;
  - Terminal.app — Cmd невозможен, Option — галка «Use Option as Meta key».
- **Дальше:** показывать рецепт не только в отчёте доктора, а подсказкой, когда
  окружение опознано как мак, а рунг ниже возможного для эмулятора. Например,
  iTerm2 без tmux, а super так и не пришёл.
