# Diff Viewer — side-by-side и семейство команд сравнения

Цель: довести дифф до полноценной **смотрелки изменений** — второй режим отображения
(side-by-side) плюс набор команд, которые открывают дифф не только для пары «файл ↔ HEAD».
Git остаётся главным поставщиком левой стороны, но сама вкладка перестаёт быть
git-специфичной: сравнить можно два произвольных файла, буфер с диском, файл с содержимым
буфера обмена, файл с произвольной ревизией — как в VS Code.

Это продолжение [Diff.md](Diff.md) (его этап 7 и хвост «Осталось по смотрелке»); там —
история этапов 1–6 и решения по движку, здесь — приёмочный чек-лист и фазировка.

Документ — одновременно **спека** (номенклатура команд), **приёмочный чек-лист** (user
stories US-1…US-36: каждая закрывается тестом при реализации, по ним же ручное
тестирование после релиза) и **трекер фазировки**.

---

## Что уже есть (точка старта)

- Вкладка `vexx-diff:<path>?HEAD` с **inline**-диффом: два номера строки в гуттере,
  маркеры `-`/`+`, подсветка синтаксиса, свёрнутые неизменённые куски.
- Дифф — **снимок** на момент открытия; правки исходного буфера её не двигают.
- Дифф — настоящая текстовая поверхность: каретка, выделение, копирование,
  горизонтальная прокрутка, мышь (`DiffViewElement` поверх `EditorViewState`,
  `readOnly = true`, синтетический документ из `createDiffViewState`).
- Единственный вход — «Git: Compare Active File with HEAD» и активация строки в Changes.
- Раскрытие свёрнутого куска жестом — модель умеет (`DiffViewModel.expandRegion`),
  элемент нет.

---

## Рамка: из чего состоит сравнение

Не дизайн реализации (он будет отдельно), а словарь, без которого сценарии не читаются.

Дифф — это **пара сторон** `{original, modified}`. Каждая сторона — это `{uri, label,
текст}`, а вот **откуда взялся текст**, вкладке знать не нужно. Сегодня левую сторону даёт
git (`vexx-diff:` + `IOriginalResourceProvider`), правую — открытый буфер или диск.
Всё семейство команд ниже — это ровно варианты того, чем заполнить две стороны:

| Источник | Пример команды | Чем читается |
|---|---|---|
| файл на диске | Compare Active File With… | `file:`-провайдер ФС (уже есть) |
| открытый буфер | Compare with Saved | `TextEditorPane.getText()` (уже есть) |
| ревизия git | Compare with HEAD / with Revision… | `git:`-провайдер (уже есть) |
| буфер обмена | Compare Active File with Clipboard | `IClipboard.readText()` |
| пусто | дифф удалённого файла | пустая строка (уже есть) |

Отсюда два следствия, влияющие на сценарии: (1) идентичность вкладки перестаёт быть
«путь + ревизия» и становится парой источников; (2) «сравнить с пустым» и «сравнить с
буфером обмена» — не спецслучаи, а обычная пара, где одна сторона не имеет файла на диске.

Отдельная ось — **режим отображения**: inline (что есть сейчас) и side-by-side (что
делаем). Режим — свойство вкладки, а не пары; переключается на лету и не пересчитывает
дифф.

## Пользовательские сценарии

Формат: **Дано** → *Действие* → **Ожидаемо**. Сценарии, помеченные ★, покрываются e2e
на SEA-бинаре (видимая часть); остальные — юнитами.

### A. Откуда открывается дифф

- **US-1. ★ Активный файл ↔ HEAD в side-by-side.** Репо, файл с правками открыт. →
  «Git: Compare Active File with HEAD». → Вкладка `<файл> ↔ HEAD`, две колонки: слева
  версия HEAD, справа рабочая; изменённые строки подсвечены с обеих сторон.
- **US-2. ★ Активация строки в Changes.** Вьюлет Source Control, строка modified-файла. →
  Enter / двойной клик. → Тот же side-by-side, одна вкладка (не открывается сначала файл).
- **US-3. ★ Сравнить с другим файлом.** Открыт `a.ts`. → «File: Compare Active File
  With…» → пикер (сверху открытые вкладки, ниже файлы workspace, фильтрация по мере
  ввода — механика Quick Open) → выбрать `b.ts`. → Вкладка `a.ts ↔ b.ts`; слева `a.ts`
  (активный — original, как VS Code), справа выбранный; несохранённые правки обеих
  сторон видны (открытый буфер побеждает диск). Esc в пикере — ничего не открылось.
- **US-4. ★ Select for Compare / Compare with Selected.** Explorer, файл `a.ts`. →
  контекстное меню → «Select for Compare»; затем на `b.ts` → «Compare with Selected». →
  Вкладка `a.ts ↔ b.ts` (выбранный ПЕРВЫМ — слева). Пункт «Compare with Selected» до
  первого выбора не показывается (when-ключ); повторный «Select for Compare» просто
  заменяет отложенный файл; выбор не переживает рестарт (как VS Code).
- **US-5. Сравнить с буфером обмена.** В буфере обмена Vexx — текст (скопирован
  Ctrl+C). Открыт файл. → «File: Compare Active File with Clipboard». → Вкладка
  `Clipboard ↔ <файл>`; слева содержимое буфера обмена, справа файл.
  *Ограничение (осознанное):* читается внутренний регистр Vexx, не системный буфер —
  `OscClipboard.readText()` намеренно не спрашивает терминал (см. его док-комментарий).
  Текст, скопированный в другом приложении, сюда не попадёт; в сценарии это должно быть
  видно как «сравнили с пустым», а не как ошибка. Повторный вызов с новым содержимым
  буфера обновляет ту же вкладку (идентичность пары не зависит от текста).
- **US-6. ★ Сравнить с сохранённой версией.** Файл открыт, есть несохранённые правки. →
  «File: Compare Active File with Saved». → Слева версия с диска, справа живой буфер;
  метка `<файл> (on disk) ↔ <файл>`. Файл без правок (буфер = диск) — вкладка честно
  показывает «no changes» (US-11), это не ошибка. Untitled-буфер — команда недоступна
  (файла на диске нет).
- **US-7. Сравнить с произвольной ревизией.** Репо с ветками/тегами. → «Git: Compare
  Active File with Revision…» → пикер ref'ов (переиспользует `vexx.git.query refs`:
  ветки, теги; текущая помечена) → выбрать ветку. → Вкладка `<файл> (<ref>) ↔ <файл>`;
  левая сторона — содержимое файла на этом ref (читается тем же `git:`-провайдером ФС,
  что и HEAD, — меняется только ref в query). Файла на ref нет → левая сторона пуста,
  всё справа добавлено (не ошибка). Вне репозитория — команда недоступна.
- **US-8. Дифф файла из коммита (GRAPH).** Панель GRAPH, коммит. → активация коммита →
  список файлов коммита → активация файла. → Вкладка `<файл> ↔ <shortSha>~`, дифф
  `commit^ ↔ commit`. *(Follow-up SourceControlGraph — сценарий фиксируем здесь, чтобы
  форма вкладки совпала.)*
- **US-9. Untitled-буфер как сторона.** Открыт untitled-буфер с текстом. → «Compare Active
  File With…» → выбрать файл. → Дифф открывается; сторона untitled берётся из памяти,
  метка — имя untitled-вкладки. Untitled доступен и в пикере US-3 (в группе открытых
  вкладок) — тогда он правая сторона.
- **US-10. Сравнение, где одна сторона пуста.** Файл удалён в рабочем дереве (status D) →
  активация в Changes даёт «HEAD ↔ пусто»: слева весь файл как удалённый, справа только
  филлеры. Симметрично untracked-файл (нет в HEAD) при явном сравнении с HEAD даёт
  «пусто ↔ файл».
- **US-11. Два пустых файла / идентичные стороны.** Сравнить файл сам с собой (или два
  пустых). → Вместо пустого экрана — сообщение по центру вкладки в духе VS Code:
  «The files are identical». Вкладка при этом нормально закрывается и не ломает навигацию.
- **US-12. Дифф из расширения.** Расширение зовёт `vscode.diff(left, right, title?)` —
  тот же id и контракт, что в VS Code, поэтому стоковые расширения работают без адаптации.
  → Открывается та же вкладка, что и у пользовательских команд: uri сторон резолвятся
  реестром провайдеров ФС (`file:`, `git:`, …), title — метка вкладки (без него —
  `<лево> ↔ <право>`). Проверяет, что API-путь не отличается от пользовательского.

#### Спека команд сравнения (детализация A)

Все команды дают **снимок** (живой пересчёт — фаза 5) и открывают **одну** вкладку на
пару источников: та же пара → обновление снимка на месте + активация (US-32), другая
пара того же файла → отдельная вкладка (US-33). Пара упорядочена: `(лево, право)` ≠
`(право, лево)`. Ошибка чтения любой стороны — нотис в статус-баре (образец —
«No changes to compare»), вкладка не открывается.

| id | title (палитра) | Доступность (when) | Поведение |
|---|---|---|---|
| `workbench.files.action.compareFileWith` | File: Compare Active File With… | активная вкладка с ресурсом | пикер Quick Open: открытые вкладки, затем файлы workspace; выбранный — правая сторона, активный файл — левая |
| `workbench.files.action.compareWithSaved` | File: Compare Active File with Saved | активный **текстовый** редактор файла с диска | `(on disk) ↔ буфер` |
| `workbench.files.action.compareWithClipboard` | File: Compare Active File with Clipboard | активная вкладка с ресурсом | `Clipboard ↔ файл`; левая сторона без uri — текст из `IClipboard` |
| `selectForCompare` | Select for Compare | строка файла в Explorer (контекст-меню, группа сравнения) | запоминает uri + взводит when-ключ `resourceSelectedForCompare` |
| `compareFiles` | Compare with Selected | Explorer + `resourceSelectedForCompare` | `выбранный ранее ↔ текущий` |
| `vexx.scm.compareWithRevision` | Git: Compare Active File with Revision… | `gitHasRepo` + активная вкладка | пикер ref'ов → `(ref) ↔ файл` |
| `vscode.diff` | — (программная) | всегда | `(leftUri, rightUri, title?)` — вход для расширений и внутренних потребителей |

Общее ядро — «открыть дифф пары источников»: сторона задаётся либо uri (текст
резолвится реестром ФС / открытым буфером — буфер побеждает диск, несохранённые правки
видны), либо готовым текстом с меткой (Clipboard). `vexx.scm.compareWithHead` (US-1)
переезжает на то же ядро без изменения поведения. Кейбинды VS Code — chord-пары
`Ctrl+K D` (Saved) и `Ctrl+K C` (Clipboard) — добавляются, только если chord-механика
уже есть; иначе палитры достаточно (отметить в доке фактическое состояние).

### B. Раскладка side-by-side

- **US-13. ★ Две колонки и разделитель.** Дифф открыт. → Экран поделён пополам:
  колонка original | вертикальный разделитель | колонка modified. У каждой стороны —
  свой гуттер с номерами строк своей стороны (не два номера в одном гуттере, как в inline).
- **US-14. ★ Подписи сторон.** Над колонками — строка с метками: слева `HEAD`
  (или `b.ts`, `Clipboard`, `Saved`), справа `<файл>`. Пользователь должен понимать, что
  где, не глядя на заголовок вкладки.
- **US-15. ★ Филлеры и выравнивание.** Файл с добавленными и удалёнными строками. →
  Против добавленной строки справа слева стоит пустая строка-филлер (визуально отличимая
  от пустой строки файла), и наоборот; строки, соответствующие друг другу, всегда на одной
  высоте.
- **US-16. ★ Синхронная вертикальная прокрутка.** Колесо мыши / стрелки / PageDown в любой
  из сторон. → Обе колонки едут вместе, выравнивание не рвётся; полоса прокрутки одна на
  дифф, а не по одной на сторону.
- **US-17. Синхронная горизонтальная прокрутка.** Длинная строка. → Горизонтальный скролл
  двигает обе стороны на одно и то же смещение (как VS Code).
- **US-18. ★ Intra-line подсветка.** Строка изменена частично. → Внутри строки выделен
  только изменённый фрагмент (движок уже даёт `innerChanges`), фон всей строки — более
  тусклый оттенок; в обеих колонках.
- **US-19. ★ Свёрнутые неизменённые куски.** Файл, где изменения далеко друг от друга. →
  Неизменённые куски свёрнуты в строку-плейсхолдер «⋯ N unchanged lines» **на всю ширину
  обеих колонок** (одна плашка, а не две независимые).
- **US-20. ★ Раскрытие куска жестом.** Каретка/указатель на плейсхолдере. → Enter или
  клик → кусок раскрывается; обе стороны раскрываются согласованно, выравнивание
  сохраняется, скролл не прыгает. Повторное раскрытие большого куска — порциями
  (upstream `revealLineCount: 20`), полное — отдельным жестом/командой «Expand All».
- **US-21. ★ Узкий терминал → авто-inline.** Ширина окна меньше порога (у VS Code это
  `renderSideBySideInlineBreakpoint`, у нас — в колонках). → Вкладка сама рисуется
  inline; при расширении обратно возвращается side-by-side. Никакого «две колонки по
  15 колонок каждая».
- **US-22. Ручное переключение режима.** «Diff: Toggle Inline View» (палитра/кейбинд). →
  Режим меняется мгновенно, дифф не пересчитывается, позиция скролла сохраняется. Выбор
  персистится (как режим list/tree у Changes) и применяется к следующим диффам.
- **US-23. Ресайз окна.** `resize` до узкого и обратно, дифф открыт. → Ничего не падает,
  колонки пересчитываются, каретка остаётся на своей строке.

### C. Взаимодействие внутри диффа

- **US-24. ★ Каретка в активной стороне.** Клик в правой колонке. → Каретка там; стрелки
  ходят по строкам этой стороны, филлеры каретка проскакивает (на «нет такой строки»
  курсор не стоит).
- **US-25. ★ Переключение сторон.** Команда «Diff: Switch Side» (и клик мышью в другой
  колонке). → Активной становится другая сторона, каретка встаёт на **соответствующую**
  строку, а не в начало файла.
- **US-26. ★ Выделение и копирование.** Выделить несколько строк в одной колонке →
  Ctrl+C. → В буфере — текст только этой стороны: без номеров строк, без маркеров
  `-`/`+`, без строк-плейсхолдеров. Выделение не «перетекает» во вторую колонку.
- **US-27. ★ Навигация по изменениям.** F7 / Shift+F7 («Go to Next/Previous Difference»).
  → Каретка прыгает к следующему/предыдущему изменению; если оно внутри свёрнутого
  куска — кусок раскрывается; строка попадает в видимую область.
- **US-28. Правка запрещена, текст живёт.** Ввод символа, Delete, Ctrl+V, Ctrl+X. →
  Ничего не меняется, вкладка носит метку-замок; при этом Ctrl+C, движение каретки,
  выделение, Home/End/PageUp/PageDown работают (уже так в inline — не должно сломаться).
- **US-29. Закрытие и переключение вкладок.** Ctrl+W, Ctrl+Tab, Ctrl+6 на дифф-вкладке. →
  Работают как на обычной вкладке, диалога сохранения нет.

### D. Живость и идентичность вкладки

- **US-30. ★ Живой дифф вместо снимка.** Дифф `<файл> ↔ HEAD` открыт; в соседней вкладке
  правим тот же файл. → Дифф пересчитывается по debounce (механика `QuickDiffService`),
  скролл и каретка не сбрасываются в начало.
- **US-31. Сдвиг HEAD.** Дифф открыт → в терминале `git commit`. → Левая сторона
  обновляется (как это уже делает гуттер), вкладка не показывает исчезнувшие изменения.
- **US-32. Дедуп вкладок.** Дважды вызвать сравнение одной и той же пары. → Одна вкладка;
  вторая активация обновляет содержимое и активирует существующую.
- **US-33. Разные пары — разные вкладки.** `a.ts ↔ HEAD` и `a.ts ↔ b.ts` открыты
  одновременно. → Две вкладки с различимыми метками, друг друга не затирают.

### E. Краевые случаи

- **US-34. Большой файл и таймаут.** Сравнить файлы на десятки тысяч строк. → Результат
  появляется; при упоре в `MAX_DIFF_COMPUTATION_MS` показывается грубый дифф, приложение
  не замирает и пользователь понимает, что результат приблизительный.
- **US-35. Бинарный / нечитаемый файл.** Сравнить с картинкой или бинарником. →
  Сообщение вместо мусора на экране; вкладка закрывается нормально.
- **US-36. EOL и пробелы.** Файл с CRLF; правка только в конце строк / только в отступах.
  → EOL сам по себе не даёт изменений (уже починено при разборе сторон); для пробелов —
  тумблер «Toggle Ignore Trim Whitespace» с наблюдаемым эффектом.

**Осознанные non-goals этого документа** (чтобы не выглядели недоделками): `Ctrl+F` внутри
диффа (`FindService` типизирован `TextEditorPane` — отдельная задача), `Ln, Col` в
статус-баре для диффа, staging по диапазонам (`git.stageSelectedRanges`), три колонки для
merge-конфликтов, word wrap внутри диффа.

## Решённые вопросы (зафиксировано с пользователем, 2026-08-10)

1. **Дефолтный режим** — side-by-side, авто-фолбэк в inline на узком окне. Порог —
   `SIDE_BY_SIDE_MIN_COLS = 100` колонок **ширины самого элемента** (не терминала):
   сайдбар и скроллбар съедают ~20 колонок, так что это терминал от ~120. Урок
   реального запуска: порог 120 по элементу оставлял inline даже на 140-колоночном
   терминале.
2. **Свёртка по умолчанию** — остаётся включённой и в side-by-side (отклонение от
   upstream, оправданное высотой терминала); раскрытие жестом — фаза 2.
3. **Кто original в «сравнить два файла»** — как VS Code: первый выбранный слева.
4. **Скоуп первого захода** — side-by-side на существующем входе (US-1, US-2);
   семейство команд (US-3…US-9) — следующей фазой на развязанной паре источников.
