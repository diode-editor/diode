# Marketplace — курируемый магазин расширений

Цель: дать пользователю Diode способ находить и ставить рабочие расширения, а нам —
контролируемый канал их публикации. Магазин курируемый: мы отвечаем за то, что всё
в реестре работает в Diode.

Этот документ — замена старой модели Phase 10 из [Extensions.md](Extensions.md)
(краулер по GitHub-топику `diode-extension`). Что изменилось: **дистрибуция через
курируемый реестр** вместо самоподписки топиком — наполнение идёт PR-ами/коммитами
в один репозиторий (им стал репозиторий сайта), а не кравлингом чужих. Что сохранено из старого
дизайна: артефакт/версия-ориентированная схема, `sha256` на каждый артефакт,
матчинг `engines`, install-флоу поверх `installVsix`, миграция на openvsx как
возможное будущее (смена источника, не формата).

Связанные документы: [Extensions.md](Extensions.md) (рантайм расширений; Phase 8b —
views, Phase 9 — внешние расширения), [docs/arch/Extensions.md](../arch/Extensions.md).

## Принципы

- **Курируемость.** В реестр попадает только то, что мы протестировали в Diode.
  Зелёный прогон системы тестирования расширений (`e2e/marketplace/`) — условие
  добавления/обновления записи.
- **Чужие байты не хостим.** Запись реестра пинит конкретную версию артефакта по URL +
  `sha256`; чужие `.vsix` живут у авторов (openvsx, GitHub Releases). Свои расширения
  раздаём сами — из `artifacts/` репозитория сайта. Перехостить чужое конкретное
  расширение можно без смены схемы (другой тип artifact-источника).
- **Иммутабельность версий.** Опубликованная версия не переписывается — изменения
  только добавлением новой версии. Подмену артефакта на том же URL ловит `sha256`.
- **Формат переживает транспорт.** Файловый source, HTTP-source и CI registry-репо
  читают/пишут один формат; код — source of truth
  (`src/vs/platform/extensionManagement/common/registryFormat.ts`).

## Формат данных (schemaVersion 1)

Публикуемый вид registry-репозитория = то, что читает клиентский источник:

```
<registry-root>/
  index.json                 — компактный список для поиска и Extensions view
  meta/<publisher>.<name>.json — полная мета расширения, читается лениво
  artifacts/**               — .vsix для path-артефактов (файловый source/тесты)
```

- `index.json`: `{ schemaVersion, generatedAt?, extensions: [...] }`; запись — `id`
  (строго `publisher.name`), `publisher`, `name`, `displayName`, `description`,
  `kind` (`proxy-openvsx` | `native`), `categories?`, `latest: { version, engines }`
  (чтобы список показывал версию и совместимость без ленивых фетчей).
- `meta/<id>.json`: идентичность + `repository?`/`license?`/`homepage?`/`readme?`
  (inline markdown — контент страницы расширения в табе) + `versions[]`; версия —
  `{ version, engines, artifact, sha256, size?, publishedAt? }`. `engines` обязан
  нести хотя бы одно из `diode`/`vscode`; `sha256` обязателен (hex lowercase).
- Артефакт — union: `{ type: "url", url, origin?: "openvsx" | "github-release" }`
  (origin — provenance, поведение не меняет) или `{ type: "path", path }`
  (POSIX-relative внутри корня; для файлового source).
- Эволюция: `schemaVersion > поддерживаемого` → ошибка «обнови Diode»; опциональные
  поля добавляются без bump'а. Битая запись пропускается с диагностикой, битый файл —
  ошибка (философия `scanExtensions`).

Точные типы и валидация — `registryFormat.ts`; этот раздел — конспект, не копия.

## Статус: шаг 2 (наполнение и публикация) — сделан

Реестр живёт в репозитории сайта [`diode-editor.github.io`](https://github.com/diode-editor/diode-editor.github.io),
отдельный `diode-registry` не заводился: сайт уже есть, Pages раздаёт его из корня
`main`, и это убирает кросс-репозиторную доставку целиком.

```
extensions/<publisher>.<name>.json  источник правды — PR-ы сюда
artifacts/<id>-<version>.vsix       байты ТОЛЬКО наших расширений
registry/v1/index.json              публикуемый вид, собирает CI
registry/v1/meta/<id>.json
```

- Публичные адреса: `https://diode-editor.github.io/registry/v1/index.json` и
  `…/registry/v1/meta/<id>.json`. Префикс `v1` = `REGISTRY_SCHEMA_VERSION`: ломающая
  смена формата встанет рядом как `v2`, выпущенные клиенты продолжат читать `v1`.
- Раскладка публикуемого вида **совпадает с той, что читает `FileExtensionRegistrySource`** —
  HTTP-источник и оказался заменой `fs` на `fetch`, без смены формата.
- Исходный файл тождественен по форме публикуемой мете; `index.json` полностью
  производный, `latest` = максимум по semver той же политикой, что в
  `resolveCompatibleVersion.ts` (расхождение политик между индексом и тем, что реально
  поставится, хуже, чем prerelease в списке). `generatedAt` не пишем — он сделал бы
  каждую сборку диффом и убил бы `build --check`.
- **Валидатор и сборщик — `scripts/registry.mjs` в репозитории сайта**, обычный ESM на
  встроенных модулях плюс `semver`. Наши TS-парсеры туда сознательно НЕ доставляются:
  бандл, релиз-тег и воркфлоу публикации инструмента — непропорционально для реестра
  такого размера. Плата — упрощённое эхо проверок в двух местах; расхождение ловится
  прогоном опубликованного через `parseRegistryIndex`/`parseRegistryMeta` — с шага 3 это
  не разовая приёмка, а `e2e/marketplace/` на каждом прогоне.
- Проверки строже клиентских, и это намеренно: клиент обязан пережить битую запись
  (реестр может обогнать выпущенный редактор), реестр обязан её не опубликовать.
  Фатальны неизвестные ключи (иначе `licence` вместо `license` теряется молча),
  невалидные semver-диапазоны, не-`https`/чужой хост, `path`-артефакты и правка либо
  удаление опубликованной версии (`--allow-removals` — аварийный флаг мейнтейнера).
- `--fetch` качает артефакт и сверяет `sha256`/`size`; хосты по списку, и он же
  проверяется на **конечном** адресе после редиректов (open-vsx уводит на
  `openvsx.eclipsecontent.org`). Свои артефакты сверяются по файлу в репозитории, а не
  по сети: в PR они ещё не опубликованы. Воркфлоу — `pull_request`, не
  `pull_request_target`: URL приходят из недоверенного PR.
- В реестре два примера: `EditorConfig.EditorConfig` (прокси на сток из open-vsx, пин
  подтверждён — sha256 скачанного совпал с нашей e2e-фикстурой) и `test.tab-setter`
  (образец `native` до появления настоящего расширения Diode; ставит `tabSize=7` при
  активации — за это цепляется тест полного цикла).

Открытые вопросы: `categories` есть в `IRegistryIndexEntry`, но не в
`IRegistryExtensionMeta` — вывести их сборке неоткуда, поле пока не заполняем
(аддитивно чинится в `registryFormat.ts`); отзыв версии (`yanked`) — иммутабельность
запрещает удаление, а скомпрометированную версию надо уметь снять.

## Статус: шаг 3 (HTTP-источник + система тестирования расширений) — сделан

Клиент читает опубликованное по сети, и `--install-extension <id>` **без флагов** ставит
расширение из публичного реестра: установка по id и есть магазин, `--registry` остаётся
для локального каталога, зеркала и тестов.

- `HttpExtensionRegistrySource` (`node/httpRegistrySource.ts`) — первый HTTP-код в `src/`.
  Форма и контракт как у файлового источника: чистый модуль, диагностики в `onProblem`,
  `sha256` проверяет вызывающий. Лимиты на размер (JSON 8 МиБ, `.vsix` 64 МиБ) считаются
  по фактическим байтам, а не по `Content-Length` — заголовок необязателен и может врать;
  таймаут 30 с; причина сетевого сбоя достаётся из `cause` (иначе `fetch` говорит только
  «fetch failed»). `404` на мете — «нет такого id» (как `ENOENT` у файлового источника),
  любой другой не-2xx — ошибка реестра.
- `http:` разрешён наравне с `https:`: целостность держится на `sha256` из меты, а не на
  транспорте; локальный реестр по http — законный сценарий.
- Выбор источника — `node/createRegistrySource.ts` (`DEFAULT_REGISTRY_URL` + различение по
  префиксу схемы). Именно по префиксу, а не разбором `new URL`: виндовый `C:\registry`
  парсится как URL с протоколом `c:` и уехал бы в HTTP-ветку.
- Система тестирования расширений — `e2e/marketplace/`. Полный цикл против **настоящего**
  опубликованного реестра: индекс и мета по сети → артефакт (наш с Pages либо чужой с
  open-vsx) → `sha256` → установка собранным бинарём → запуск редактора → проверка
  функциональности расширения (`test.tab-setter` ставит `tabSize=7`, EditorConfig
  применяет `[*.tabbed] indent_size=3` — оба через инспектор, без ввода в PTY).
  **Гейт курирования:** у каждой опубликованной записи обязан быть смоук-чек, иначе сьют
  красный; версия сверяется с `latest` из индекса, так что и обновление записи требует
  зелёного прогона. Сьют шумит по сети сознательно — детали и `DIODE_E2E_OFFLINE`
  в [docs/TESTING.md](../TESTING.md).
- **Риск шага 2 закрыт:** живой `index.json` разбирается нормативным `parseRegistryIndex`
  в e2e, а мета — настоящим клиентом при каждой установке. Расхождение упрощённых проверок
  `scripts/registry.mjs` с форматом больше не может остаться незамеченным.

Дискового кэша `index.json`/меты с TTL и оффлайн-режима сознательно нет: у CLI-установки
один выстрел, кэш ей ничего не экономит. Он нужен Extensions view (раздел ниже), который читает
индекс на каждый показ и фильтр, — там и заводится, вместе со своим потребителем.

Прогон по всему реестру перед релизом Diode (регрессии совместимости API-шима) — тот же
сьют, вопрос только в расписании CI.

## Прокси-расширения (`kind: "proxy-openvsx"`)

Протестированный нами сток из openvsx: запись пинит конкретную версию URL + `sha256`.
Критерии добавления: расширение реально работает в Diode (заводится через extension
host, смоук-чек проходит в `e2e/marketplace/`). Обновление версии =
PR с новой записью в `versions[]` после зелёного прогона на новой версии. Стоковое
расширение может быть заменено нашим форком/патчем позже — это смена артефакта в
новой версии записи, схему не трогает.

## Extensions view (позже)

Как в VS Code, но без иконок; страница расширения открывается в табе:

- Список: `index.json` через источник, поиск — `searchRegistryIndex`, бейдж
  «несовместимо» по `latest.engines`; установленные — `listInstalledExtensions`.
- Страница расширения (таб): рендер `meta.readme` + метаданные + кнопки
  install/uninstall/версии.
- Опора на готовый `ViewsService` (`registerContainer`/`registerView`/`setViewBody`,
  образец — `explorerComponent.ts`); см. [Extensions.md](Extensions.md) Phase 8b.
- Здесь появляется workbench-сервис с DI-токеном (выбор источника из настроек,
  события установки для view) — обёртка над `IExtensionRegistrySource` +
  `installFromRegistry`.

## Безопасность и оговорки

- `sha256` в записи — защита от подмены артефакта по URL (иммутабельность GitHub
  Releases/openvsx неполная); проверка до `installVsix`, mismatch — отказ.
- Защита от id-mismatch: манифест установленного `.vsix` сверяется с запрошенным id,
  расхождение — откат (реестр мог указать чужой артефакт).
- Доверие сосредоточено в курируемом реестре (кто мержит PR — тот и гарант);
  верификация publisher'ов — вопрос настоящих реестров, на нашем масштабе не нужна.
- Момент миграции на openvsx как источник discovery — открыт; формат и
  `IExtensionRegistrySource` делают это сменой источника, не схемы.
