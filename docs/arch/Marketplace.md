# Магазин расширений: реестр, формат, клиент

Курируемый магазин: пользователь находит и ставит рабочие расширения, а мы держим канал
публикации под контролем — всё, что лежит в реестре, проверено в Diode. Рантайм расширений и
установка `.vsix` — [Extensions.md](Extensions.md); UI магазина (вьюлет и страница расширения) —
[workbench/ExtensionsView.md](workbench/ExtensionsView.md); заметки по конкретным записям —
[StockExtensions.md](StockExtensions.md#записи-магазина); открытые задачи —
[TODO/Extensions.md](../TODO/Extensions.md#магазин).

## Три репозитория

Правка формата задевает все три:

- **diode** — формат и клиент: `src/vs/platform/extensionManagement/common/registryFormat.ts`
  (source of truth: точные типы и валидация; раздел «Формат» ниже — конспект, не копия), источники,
  резолв версии, установка;
- **[`diode-editor.github.io`](https://github.com/diode-editor/diode-editor.github.io)** — реестр и
  его валидатор `scripts/registry.mjs`;
- **[`diode-editor/marketplace`](https://github.com/diode-editor/marketplace)** — веб-витрина. Её
  легко забыть, а человек смотрит обычно туда. Так заводилась пометка `support` (#355 + сайт#7 +
  marketplace#4). Курация языков витрины живёт в самой витрине (`src/curation.ts`).

## Принципы

- **Курируемость.** В реестр попадает только то, что мы проверили в Diode. Проверка живёт на стороне
  магазина и тестом в diode не гейтится: `e2e/marketplace/` не решает, что публиковать, — он
  показывает, работает ли опубликованное на текущем коде.
- **Чужие байты не хостим.** Запись пинит конкретную версию артефакта по URL + `sha256`; чужие
  `.vsix` живут у авторов (open-vsx, GitHub Releases). Свои расширения раздаём из `artifacts/`
  репозитория сайта. Сток, которого нет на Open VSX, перевыкладывается немодифицированным
  (`kind: "proxy-hosted"`, лицензия должна разрешать редистрибуцию) — это другой тип источника
  артефакта, а не смена схемы.
- **Иммутабельность версий.** Опубликованная версия не переписывается — только новая версия рядом.
  Подмену артефакта на том же URL ловит `sha256`.
- **Только релизы.** Клиент берёт максимум по semver и pre-release не фильтрует — поставил бы его
  всем; гарантия на стороне реестра. По номеру pre-release часто не отличить: у `redhat.java` это
  `1.57.2026092608` — валидный релизный semver больше `1.56.0` (так он однажды и попал в магазин).
  Поэтому валидатор отвергает semver-суффикс по номеру, а с `--fetch` открывает сам `.vsix` и
  отвергает флаг `Microsoft.VisualStudio.Code.PreRelease` в `extension.vsixmanifest` (заодно сверяет
  id, версию и таргет артефакта с записью). Снятие просочившегося pre-release — единственное
  удаление версии, которое CI реестра пропускает без `--allow-removals`, проверив флаг по байтам.
- **Формат переживает транспорт.** Файловый источник, HTTP-источник и CI реестра читают и пишут один
  формат; миграция на open-vsx как источник discovery — смена источника, а не схемы.

## Формат (schemaVersion 1)

```
<registry-root>/
  index.json                   — компактный список для поиска и Extensions view
  meta/<publisher>.<name>.json — полная мета расширения, читается лениво
  artifacts/**                 — .vsix для path-артефактов (файловый источник, тесты)
```

- **`index.json`**: `{ schemaVersion, generatedAt?, extensions: [...] }`; запись — `id` (строго
  `publisher.name`), `publisher`, `name`, `displayName`, `description`, `kind`
  (`proxy-openvsx` | `proxy-hosted` | `native`), `categories?`, `support?`,
  `latest: { version, engines }` — чтобы список показывал версию и совместимость без ленивых фетчей.
- **`support?`** — курационная пометка, насколько расширение работает у нас:
  `{ level: "full" | "partial", works?: string[], limits?: string[] }`. Лежит и в индексе, и в мете:
  бейдж `Partial` в строке списка обязан быть виден ДО установки, а страница расширения разворачивает
  пометку в «Works in Diode» и «Does not work». `partial` без непустого `limits` реестр не публикует
  (предупреждение, которое не говорит, чего лишишься, бесполезно); клиент битую пометку молча
  игнорирует — косметика не повод потерять запись. Типичный повод для `partial` — webview: языковая
  часть работает, чат-панель не открывается.
- **`meta/<id>.json`**: идентичность + `repository?`/`license?`/`homepage?`/`readme?` (inline markdown —
  содержимое страницы расширения) + `versions[]`; версия —
  `{ version, engines, artifact, sha256, targetPlatform?, size?, publishedAt? }`. `engines` несёт хотя
  бы одно из `diode`/`vscode`; `sha256` обязателен (hex lowercase).
- **`targetPlatform`** — таргет артефакта в словаре VS Code Marketplace / Open VSX (`linux-x64`,
  `darwin-arm64`, …); не задан — universal. Одна semver-версия может лежать несколькими записями с
  разными таргетами (у `charliermarsh.ruff` есть только платформенные). `resolveCompatibleVersion`
  берёт запись своего таргета (`currentTargetPlatform()`: `process.platform` × `process.arch`;
  alpine/musl не детектится — сборок diode под musl нет), universal совместим с любым хостом, при
  равной версии платформенная запись точнее universal. **Записи с `targetPlatform` обязаны гейтиться
  `engines.diode: ">=0.4.0"`**: клиенты ≤0.3.0 поля не знают, считают платформенные записи дубликатами
  одной версии и поставили бы артефакт произвольной платформы.
- **Артефакт** — union: `{ type: "url", url, origin?: "openvsx" | "github-release" }` (origin —
  provenance, поведение не меняет) или `{ type: "path", path }` (POSIX-relative внутри корня, только
  для файлового источника).
- **Эволюция**: `schemaVersion` больше поддерживаемого — ошибка «обнови Diode»; опциональные поля
  добавляются без bump'а. Битая запись пропускается с диагностикой, битый файл — ошибка (философия
  `scanExtensions`).
- **Диапазоны `engines`** матчит стоковый `semver`: `engines` прокси-расширений пишем не мы, там
  встречаются `||`, `1.2.x` и дефисные диапазоны, а prerelease по семантике node-semver в диапазон без
  явного запроса не попадает. `engines.diode` сверяется с `DIODE_VERSION`, `engines.vscode` — с
  `VSCODE_SHIM_VERSION` (лок-степ с `extensions/VSCODE_VERSION`); dev-версия diode не блокирует.

## Реестр в репозитории сайта

Отдельный `diode-registry` не заводился: Pages уже раздаёт сайт из корня `main`, и это убирает
кросс-репозиторную доставку целиком.

```
extensions/<publisher>.<name>.json  источник правды — PR-ы сюда
artifacts/<id>-<version>.vsix       байты ТОЛЬКО наших (и перевыложенных) расширений
registry/v1/index.json              публикуемый вид, собирает CI
registry/v1/meta/<id>.json
```

- Публичные адреса — `https://diode-editor.github.io/registry/v1/index.json` и `…/meta/<id>.json`.
  Префикс `v1` = `REGISTRY_SCHEMA_VERSION`: ломающая смена формата встанет рядом как `v2`, выпущенные
  клиенты продолжат читать `v1`.
- Раскладка публикуемого вида совпадает с той, что читает `FileExtensionRegistrySource`, — поэтому
  HTTP-источник оказался заменой `fs` на `fetch` без смены формата.
- Исходный файл тождественен по форме публикуемой мете; `index.json` полностью производный, `latest` —
  максимум по semver той же политикой, что в `resolveCompatibleVersion.ts` (расхождение политик между
  индексом и тем, что реально поставится, хуже, чем prerelease в списке). `generatedAt` не пишем — он
  сделал бы каждую сборку диффом и убил бы `build --check`.
- **Валидатор и сборщик** — `scripts/registry.mjs` сайта, обычный ESM на встроенных модулях плюс
  `semver`. Наши TS-парсеры туда сознательно не доставляются (бандл, релиз-тег и воркфлоу публикации
  инструмента непропорциональны реестру такого размера). Плата — упрощённое эхо проверок в двух
  местах; расхождение ловит `e2e/marketplace/`, разбирая живой индекс нормативным `parseRegistryIndex`.
- **Проверки строже клиентских, и это намеренно**: клиент обязан пережить битую запись (реестр может
  обогнать выпущенный редактор), реестр обязан её не опубликовать. Фатальны неизвестные ключи (иначе
  `licence` вместо `license` теряется молча), невалидные semver-диапазоны, не-`https` или чужой хост,
  `path`-артефакты, правка либо удаление опубликованной версии (`--allow-removals` — аварийный флаг
  мейнтейнера). Размер артефакта реестр режет своим `MAX_ARTIFACT_BYTES` — клиентского лимита мало.
- `--fetch` качает артефакт и сверяет `sha256`/`size`; список хостов проверяется на **конечном** адресе
  после редиректов (open-vsx уводит на `openvsx.eclipsecontent.org`). Свои артефакты сверяются по файлу
  в репозитории, а не по сети: в PR они ещё не опубликованы. Воркфлоу — `pull_request`, не
  `pull_request_target`: URL приходят из недоверенного PR.
- Синтетические `native`-записи (`test.tab-setter` — рантайм-расширение, `test.sample-lang` —
  декларативное) живут до появления настоящего расширения Diode; их исходники и детерминированный
  упаковщик — в diode (`e2e/marketplace/sample-extension`, `scripts/pack-vsix.mjs`), так что
  пересборка даёт те же байты и пин по `sha256` проверяется сверкой, а не на веру.

## Клиент: источники и установка

`--install-extension <id>` без флагов ставит из публичного реестра — установка по id и есть магазин;
`--registry <путь|URL>` — локальный каталог, зеркало, тесты. Аргумент с суффиксом `.vsix` — путь к
файлу, всё прочее — id (различение как у VS Code, без обращения к ФС: файл с именем вида id не должен
перехватывать установку).

- **Шов источника** — `IExtensionRegistrySource` (`getIndex`/`getMeta`/`fetchArtifact`):
  `FileExtensionRegistrySource` (каталог, только `path`-артефакты) и `HttpExtensionRegistrySource`.
  Выбирает `createRegistrySource` (`DEFAULT_REGISTRY_URL` + различение **по префиксу схемы**, а не
  разбором `new URL`: виндовый `C:\registry` парсится как URL с протоколом `c:` и уехал бы в HTTP).
- **HTTP-источник**: форма и контракт как у файлового — чистый модуль, диагностики в `onProblem`,
  `sha256` проверяет вызывающий. Лимиты (JSON 8 МиБ, `.vsix` 256 МиБ) считаются по фактическим байтам,
  а не по `Content-Length` — заголовок необязателен и может врать; таймаут 30 с; причина сетевого сбоя
  достаётся из `cause` (иначе `fetch` говорит только «fetch failed»). `404` на мете — «нет такого id»
  (как `ENOENT` у файлового), любой другой не-2xx — ошибка реестра. `http:` разрешён наравне с
  `https:`: целостность держится на `sha256` из меты, а не на транспорте.
- **Артефакт качается потоком в файл**, а не буферизуется: платформенные `.vsix` со вшитым рантаймом
  (redhat.java с JRE 21 — ~133 МиБ, Claude Code — до 138 МБ) держать в резиденте незачем. Лимит
  остаётся лимитом **скачивания** — поток рвётся на превышении, а не проверяется постфактум;
  недокачанный `artifact.vsix` убирается, чтобы не остаться под видом валидного.
- **Установка** — `installFromRegistry`: мета → совместимая версия → артефакт → `sha256` →
  `installVsix`; `extensionDependencies` ставятся следом ([Extensions.md](Extensions.md)). Обновление —
  та же установка: новая версия ложится рядом, профиль переключается на неё, прежняя помечается в
  `extensions/.obsolete` и удаляется на следующем старте редактора. Каталог той же версии, целый и с
  совпадающим манифестом, переиспользуется без скачивания (эталон `extractUserExtension(removeIfExists=false)`).
- CLI-команды расширений выставляют `process.exitCode` вместо `process.exit()`: обрыв процесса посреди
  закрытия http-сокетов роняет libuv на Windows (`UV_HANDLE_CLOSING`) — после успешной установки был
  ассерт в stderr и мусорный код возврата (поймано windows-джобой e2e).
- **Дискового кэша** индекса и меты с TTL и оффлайн-режима нет сознательно: у CLI-установки один
  выстрел, кэш ей ничего не экономит; Extensions view держит каталог в памяти на сессию.

## Прогон магазина

`e2e/marketplace/` идёт в общем `npm run test:e2e`, то есть на каждом PR и пуше в `main`: ставит
последнюю версию каждой опубликованной записи собранным бинарём и проверяет, что она работает. Кейсы
порождаются из живого каталога — новая запись попадает под прогон сама. Отдельного прогона перед
релизом поэтому нет: регрессия совместимости API-шима видна сразу, а не в релизном окне. Устройство
сьюта, шум сети и `DIODE_E2E_OFFLINE` — [TESTING.md](../TESTING.md#расширения-из-магазина-сетевой-сьют).

## Как добавить расширение

Релиз для этого не нужен, ждать его не надо.

1. Проверить расширение из `.vsix` в живом редакторе (`drive --install <файл>`) и написать смоук в
   `e2e/marketplace/checks.ts`.
2. Поставить гейт `engines.diode` — первую версию, в которой есть всё нужное. Нужный коммит уже в
   теге — этот тег; ещё не в теге — версия из `package.json` на `main` плюс патч. Минорному релизу
   такой диапазон тоже подойдёт.
3. PR с записью в репозиторий сайта (`node scripts/registry.mjs validate --fetch`), влить, дождаться
   Pages: `curl -f https://diode-editor.github.io/registry/v1/meta/<id>.json`.
4. PR в diode со смоуком и правками, влить. Кейсы берутся из опубликованного каталога, поэтому запись
   идёт первой: иначе CI этого PR карточку не запустит.

Запись на ещё не вышедшую версию ничего не ломает:

- e2e собирает бинарь с версией `nightly-e2e`, а сборки без настоящей версии (dev и nightly) гейт
  `engines.diode` проходят (`resolveCompatibleVersion.ts`);
- на `main` без карточки для записи проверяется только установка, так что порядок шагов 3 и 4 не
  красит чужие прогоны;
- пользователь релиза до выхода версии видит расширение с пометкой `Incompatible` и неактивной
  кнопкой Install, на сломанную версию он не попадёт.

Обратная сторона: e2e обходит гейт и поэтому не проверяет его число. Ошибочный гейт тесты не заметят.

## Безопасность

- `sha256` в записи — защита от подмены артефакта по URL (иммутабельность GitHub Releases и open-vsx
  неполная); проверка до `installVsix`, расхождение — отказ.
- Манифест установленного `.vsix` сверяется с запрошенным id, расхождение — откат: реестр мог указать
  чужой артефакт.
- Доверие сосредоточено в курируемом реестре (кто мержит PR — тот и гарант); верификация
  publisher'ов — вопрос настоящих реестров, на нашем масштабе не нужна.
