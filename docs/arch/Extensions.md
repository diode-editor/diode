# Extensions/

Часть архитектуры Diode — обзорная карта в [../ARCHITECTURE.md](../ARCHITECTURE.md).

Загрузка VS Code-совместимых расширений. Сейчас поддержаны `contributes.languages`, `contributes.grammars` и `contributes.themes` для builtin (`extensions/` — 48 языковых паков из microsoft/vscode, импорт verbatim скриптом с пином тега) и user-расширений (`<userData>/extensions/<publisher>.<name>-<version>/`). Остальные contribution points — отдельные фазы (см. [../TODO/Extensions.md](../TODO/Extensions.md)).

Контракты/швы:
- **`IExtension`** — `{ id, manifest, location, isBuiltin }`. `ExtensionScanner` парсит `package.json` через `IAssetAccess`; `mergeExtensions` разруливает конфликты id (builtin побеждает user).
- **NLS манифеста (`extensionNls.ts`)** — любая строка `package.json` расширения может быть ключом `"%java.clean%"`, а текст лежит в `package.nls[.<locale>].json`. Резолв делает `ExtensionScanner` сразу за парсингом — **одним проходом по всему дереву манифеста**, как `localizeManifest` эталона, а не точечно у команд: те же ключи сидят в `displayName`/`description`, в `label` тем, в заголовках и описаниях настроек. Поэтому у потребителей (`ExtensionThemeContributor`, `collectCommandMeta` в `extensionRegistration.ts`, `packageJSON` в `vscode.extensions`) манифест уже локализованный, и своего резолва им не нужно. Бандл читается тем же `IAssetAccess`, что и манифест, — у builtin'а файла на диске нет, он внутри SEA-бандла. Выбор файла — `nlsFileCandidates(locale)`: `package.nls.<locale>.json` → базовый язык (`pt-br` → `pt`) → `package.nls.json`; локаль одна на редактор — `UI_LOCALE` (`platform/environment/common/uiLocale.ts`), оттуда же берётся `vscode.env.language`. Краевые случаи эталонные и **не роняют загрузку**: нет ключа — строка остаётся ключом плюс одна строка в лог на расширение (молча подставленная пустота не отлаживается), нет/битый бандл — расширение грузится с нерезолвленными строками, нестроковые значения не трогаются. `ExtensionInstaller.listInstalledExtensions` локализует себе `displayName`/`description` сам: он работает с физическими каталогами, мимо `IAssetAccess`.
- **`LanguageRegistry implements ILanguageService`** — собирает `contributes.languages`, резолвит language по пути файла. Неочевидное правило разрешения: приоритет `filenames` → `filenamePatterns` (мини-glob) → `extensions`; при конфликте одного `.ext` побеждает **зарегистрированный позже** (user поверх builtin, как в VS Code). Seed'ит core-язык `plaintext` как fallback.
- **`ExtensionThemeContributor`** — регистрирует цветовые темы из `contributes.themes` в `ThemeRegistry`. В отличие от грамматик — **eager**: `await apply()` в `main.ts` идёт после сканирования и ДО выбора активной темы и первого кадра (файлы тем — килобайты, а пикеру нужен синхронный `resolve`, и тема из `workbench.colorTheme` обязана быть в первом кадре). Ключ — `label` манифеста, `uiTheme` → тип, JSONC и `include` — см. [Theme.md](Theme.md). Битая тема (нет файла, битый JSON, цикл `include`) — ошибка в лог с id расширения и label, пропуск; расширение и старт не падают. `dispose()` снимает регистрации.
- **`ExtensionTokenizationContributor`** — регистрирует грамматики из всех `contributes.grammars` в `TokenizationRegistry`. `apply()` синхронный и без I/O: кладёт **ленивые фабрики** (`registerLazy`), а `.tmLanguage.json` парсится при первом `TokenizationRegistry.load(languageId)` — его дёргает `EditorComponent.ensureTokenizerForLanguage`, когда язык реально понадобился документу (наш аналог `onLanguage`; к activation-events extension host'а отношения не имеет — языковые паки декларативные, без `main`). Пока грамматика едет, документ работает на `PlainTextTokenizer`, а подъехавший support пересаживается через `onDidChange`. Мотив: 77 builtin-грамматик — 6.6 MB JSON, ~420 мс на полную загрузку; раньше всё это лежало на пути к первому кадру с содержимым файла.

Две вещи прикрывают ленивость, чтобы пользователь не видел неподсвеченный текст:
- **Стартовые файлы** — `main.ts` через `preloadGrammarsForFiles` ждёт грамматики именно тех файлов, что сейчас откроются (обычно один язык, ~2 мс), **до** `openFile`. Ждать после поздно: `await` отдаёт event loop, и отложенный рендер успевает нарисовать кадр на fallback'е. Пути берутся из CLI либо из `WorkbenchComponent.getOpenEditorsToRestore()` — тот же список, что откроет `restoreOpenEditors()`, чтобы знание о восстанавливаемой сессии не расползалось по бутстрапу.
- **Остальные грамматики** — фоновый `preloadAll()` (`setImmediate` после первого кадра), чтобы переключение вкладки на другой язык не ждало парсинга.
- **`ExtensionInstaller`** — установка/удаление/список из `.vsix` (CLI `--install-extension` и т.п., до подъёма TUI): распаковка с защитой от zip-slip + атомарный `rename` в каталог, который ждёт `ExtensionScanner`.
- **Установка по id из реестра** (`platform/extensionManagement/`) — `installFromRegistry` поверх того же `installVsix`: мета → совместимая версия (`engines` ↔ `DIODE_VERSION`/`VSCODE_SHIM_VERSION`; платформенные записи — по `targetPlatform` ↔ `currentTargetPlatform()`, universal — фолбэк) → артефакт → `sha256` → установка. Источник за швом `IExtensionRegistrySource`: каталог (`FileExtensionRegistrySource`) или сеть (`HttpExtensionRegistrySource`); выбирает `createRegistrySource` по значению `--registry`, без флага — публичный реестр. Формат и политика наполнения — [docs/TODO/Marketplace.md](../TODO/Marketplace.md).
  - **`extensionDependencies` ставятся вместе с расширением** — без вопросов, как VS Code (`getAllDepsAndPackExtensions`), и из CLI, и кнопкой Install на странице. Сначала всё **готовится** (версия, артефакт, `sha256`, манифест прямо из `.vsix` — `readVsixManifest`, сверка id), и только потом ставится — зависимости раньше, расширение последним. Поэтому отказ ничего не трогает на диске, а прежняя версия расширения при сбое остаётся. Транзитивно, без дублей; уже установленная зависимость (любой версии, id без учёта регистра) не трогается; цикл не зацикливает. Зависимость **найдена, но поставить нельзя** (нет совместимой версии, `sha256`, чужой артефакт) — отказ всей установки с причиной, как у эталона. Зависимости **нет в реестре** — расширение всё равно ставится (у эталона галерея её просто не вернёт), а отказ случится на активации тостом «depends on unknown extension». Зависимость на встроенное расширение VS Code (`vscode.*`) в магазине не ищется и пропавшей не считается — то же отступление, что на активации. Поставленные зависимости получают в Extensions view тот же бейдж Reload. CLI печатает строку на каждую зависимость и предупреждение о пропавших — отступление: эталонный CLI о зависимостях молчит. `--install-extension foo.vsix` тоже тянет зависимости из реестра; сбой — предупреждение, само расширение остаётся (как у эталона для VSIX). `extensionPack` пока не ставится.

## Extensions/Host/ — extension host (real subprocess)
Изоляция кода расширений от ядра. Host форкает **один subprocess** (тот же бинарь / `main.ts` с env `DIODE_EXTENSION_HOST=1`) и общается с ним через **RPC поверх Node IPC**. Швы:
- **`IMessageChannel`** — транспортно-агностичный двунаправленный канал. Реализации: `IpcMessageChannel` (Node IPC) и `createInProcessChannelPair()` (unit-тесты).
- **`RpcEndpoint`** — request/response/notification поверх канала, **симметричный** (запросы шлют обе стороны).
- **Сторона ядра — фасад и customers** (`services/extensions/node/`, как `mainThread*` эталона). `ExtensionHost` — фасад с прежним публичным API: держит реестр и активацию (таблица фаз `ExtensionPhases` — все регистрации, ожидающие активации, активные; журнал событий и активации в полёте), оркестрацию спавна и делегаторы. Процесс — `ExtensionHostProcess` (spawn, stdio, ready, выключение host.shutdown → SIGTERM → SIGKILL). Каждая поверхность API — customer в `customers/` (`secrets`, `env`, `window`, `decorations`, `fileSystem`, `commands`, `editor`, `configuration`, `documents`, `languageFeatures`, `terminal`, `tasks`) с контрактом `IExtensionHostCustomer.attach(ctx): IDisposable` (`common/extensionHostCustomer.ts`): объект customer'а живёт столько же, сколько хост, а всё состояние одного спавна — обработчики RPC, подписки на ядро, handle'ы — заводится в `attach` и снимается возвращённым disposable вместе со `spawnStore`. Набор customers — явный массив, который хост собирает в конструкторе из опций. Семена handshake (настройки → полоса групп и активный редактор → тема → каталог → открытые документы) хост шлёт сам в этом порядке, зовя `pushInitialState` нужных customers. Стоки окна (`DiagnosticsSink`, `IProgressSink` и соседи) — порты в `api/common/iExtensionWindowSinks.ts`, приёмник document sync — `IDocumentSyncTarget`: адаптеры `api/browser` слой node не импортируют.
- **Загрузка точки входа:** CJS или ESM, решает `isEsmEntry` правилом эталона (`_isESM` в `abstractExtHostExtensionService`): `.mjs` — всегда модуль, `.cjs` — всегда CJS, иначе — `"type"` из `package.json` расширения (хост отдаёт его в `host.activateExtension` как `moduleType`). CJS грузится `createRequire(mainPath)`, ESM — `importModule` (`base/node/importModule.ts`): `import()` из синтетического CJS-модуля, скомпилированного в памяти, потому что прямой `import()` из вшитого SEA-main перехватывается embedder-хуком и умеет только builtin'ы. Тот же приём и у `runAsNode`. ESM-расширения не экзотика: `esbenp.prettier-vscode` с 12.x — `"type": "module"`.
- **vscode-стаб:** subprocess патчит `Module._cache["vscode"]` + `Module._resolveFilename` (`installVscodeStub`), поэтому `require("vscode")` расширения отдаёт нашу поверхность. Для ESM тот же `installVscodeStub` ставит `module.registerHooks` (`resolve` + `load`): CJS-кэш ESM-loader'у не виден, и `import … from "vscode"` без хука падает на `ERR_MODULE_NOT_FOUND`. Хук отдаёт сгенерированный модуль с именованным export'ом на каждый член namespace'а (`buildVscodeEsmShim`), значения он читает из `globalThis` — замыканием их в исходник не передать; эталон держит эти два механизма рядом по той же причине. Сама поверхность собрана в `Extensions/Host/Vscode/` — тонкий ассемблер `buildVscodeNamespace(rpc)` над общим контекстом (`window`/`workspace`/`languages`/`commands` + value-типы `Position`/`Range`/`Uri`/enum'ы). Документы держат **стабильную идентичность** (`DocumentRegistry`: один объект на `fileName`, обновления мутируют его на месте — нужно для `activeTextEditor.document === doc`).
- **Идентичность расширения (G7, трекер — [ExtensionIdentity](../TODO/ExtensionIdentity.md)):** `vscode` раздаётся ПО ИМПОРТЁРУ. Субпроцесс держит индекс корней расширений (`api/common/extensionPaths.ts`: самый длинный корень-предок по сегментам пути, корень за симлинком — под обоими именами), наполняемый из каталога `extensions.catalog` и в `host.activateExtension` до загрузки модуля. CJS-патч `_resolveFilename` отдаёт `vscode:<id>` по `parent.filename` и лениво кладёт под этот ключ API расширения; ESM-хук `resolve` — `diode-vscode:api/<id>` по `context.parentURL` (на Node с `registerHooks` этот же хук видит и `require`). Builtin, скомпилированный в памяти, опознаётся по синтетическому `filename`. API расширения — **тонкий оверлей** поверх общего namespace (`api/common/extensionApiFactory.ts`), а не своя копия неймспейсов: собственные свойства — дескрипторы общего (геттеры вроде `window.activeTextEditor` живые, value-типы общие: `api1.Position === api2.Position`), перекрыты лишь `window`/`languages`/`commands`, где явный список синхронных «создающих» членов (`createOutputChannel`, `createStatusBarItem`, активные `register*Provider`, `createDiagnosticCollection`, `registerCommand`, …) обёрнут в `ExtensionOwner.runAs(id, …)` — «окружающего владельца» из общего контекста (`IVscodeHostContext.owner`). Импортёр вне известных корней получает общий namespace и одно предупреждение в stderr. Полную фабрику API на расширение (как `createApiFactoryAndRegisterActors` эталона) не делаем: обработчики RPC живут внутри фабрик неймспейсов, и копия на расширение их бы размножила.
- **Языковые провайдеры — реестр ядра (G2, как upstream `MainThreadLanguageFeatures`/`ExtHostLanguageFeatures`):** селекторы и скоринг живут в ядре — `editor/common/languageSelector.ts` (`score`: 10 точное совпадение, 5 — `*`, у массива максимум; `RelativePattern`, `exclusive`), `editor/common/languageFeatureRegistry.ts` (`register/has/ordered/onDidChange`: по убыванию score, при равном — более поздняя регистрация первой, `onDidChange` на КАЖДУЮ регистрацию и снятие), `editor/common/services/languageFeatures.ts` (`ILanguageFeaturesService` — реестр на фичу: hover, definition, references, signatureHelp, completion, documentFormatting/documentRangeFormatting, codeAction, foldingRange, inlineCompletions; биндинг в `tokenizationModule`). Субпроцесс на каждый `register*Provider` выдаёт handle и шлёт `languages.register {handle, kind, selector, …metadata}` (селектор — DTO `toWireLanguageFilters`: строка → `{language}`, `RelativePattern` → `{base: fsPath, pattern}`; метаданные — триггер-символы completion/signatureHelp, `providedCodeActionKinds`), dispose — `languages.unregister {handle}`. Хост держит регистрации (`getLanguageProviders`/`onLanguageProvidersChanged`) и снимает их все на смерти/остановке субпроцесса; `api/browser/languageFeaturesAdapter.ts` (порт `IExtensionLanguageFeaturesBridge`) регистрирует в реестрах прокси `{provideX: (req) => host.provideX(handle, req)}` — подключён один раз в `extensionHostModule.ts` и `ExtensionTestHarness`. Запрос `languages.provideX` несёт handle — субпроцесс зовёт ровно этого провайдера. Агрегация — у потребителя, по upstream: hover/definition/references — параллельно и склейка в порядке `ordered` (`contrib/hover/getHover.ts`, `gotoDefinition/goToSymbol.ts`, `references/getReferences.ts`), signatureHelp — по очереди до первого ответа (`parameterHints/provideSignatureHelp.ts`), formatting — документный форматтер по score, за ним range-провайдер на полный диапазон (`editor/contrib/format/format.ts`; `null` = «нет форматтера» решается по реестру, без RPC), code actions — с отсевом по `providedCodeActionKinds` (`editor/contrib/codeAction/codeAction.ts`). Документ без подошедших провайдеров RPC не будит вовсе. **Пачка:** пока запросы несут полный текст документа (до document sync дельтами — G3), фичи «на каждый символ» (completion, folding, inline) зовут прокси одним объектом запроса, и хост склеивает их в один RPC `{handles, …}` (`services/extensions/common/providerRequestBatcher.ts`), ответ — массив, выровненный по handles. Новая языковая фича = вид в `WIRE_LANGUAGE_FEATURE_KINDS` + реестр в `ILanguageFeaturesService` + фабрика прокси в адаптере + `provideX(handle, …)` хоста + обработчик по handle в субпроцессе; полей-швов на `EditorService` и флагов подписки больше нет.
- **Save-participant / completion seams:** `TextFileModel.save()` асинхронный — участники сохранения `await`-ятся до записи (правки клампятся к границам, уходят одним undoable-батчем). Пайплайн — `TextFileSaveParticipant` (`services/textfile/common/textFileSaveParticipant.ts`, аналог upstream): один экземпляр на все модели держит `TextFileModelService`, модель зовёт его перед записью и в `save`, и в `saveAs`; состав берётся у провайдеров в момент save (живые настройки) — `EditorService` регистрирует их через `TextFileModelService.addSaveParticipant` в порядке VS Code: участник `editor.codeActionsOnSave` → участник `editor.formatOnSave` (оба — `services/editor/browser/onSaveParticipants.ts` поверх реестров `ILanguageFeaturesService`; участник входит в пайплайн, только если для ЭТОГО документа есть подходящий провайдер) → will-save расширений (`EditorService.saveParticipant` ← host `onWillSaveTextDocument`). Каждый участник получает свежий снапшот (предыдущий мог править буфер), ограничен таймаутом 5000 мс (зависший — пропуск, сохраняем как есть), сбойный пропускается. С дефолтами (настройки выключены) пайплайн = один will-save участник — поведение прежнее; без host'а список пуст. Сама запись — через `IFileService.writeFile` (атомарно, с гардом по etag), поэтому `save()` асинхронный и без участников. Инъекция seam'ов — в `Workbench/Modules/ExtensionHostModule.ts`; **ядро (`TextFileModel`/`EditorService`) про extension-слой не знает.**
- **Folding-провайдер seam (#194):** `languages.registerFoldingRangeProvider` — путь host↔subprocess по образцу completion (`languages.provideFoldingRanges` RPC). Реестр — `ILanguageFeaturesService.foldingRangeProvider` (тип `editor/common/languages/iFoldingSource.ts`), `EditorService` отдаёт его каждому `EditorComponent`; тот при пересчёте фолдов запрашивает области подошедших провайдеров (пачкой) и **мержит их поверх indentation-фолдов** (union: provider ∪ indentation, provider выигрывает по общей `startLine`), перенося `isCollapsed` по `startLine`. Пересчёт идёт и на `onDidChange` реестра — на каждую регистрацию/снятие, так что провайдер, появившийся после открытия файла (в том числе второй), подхватывается сразу. Стоковый `maptz.regionfolder` заводится этим путём (тест `extensionHost.maptzRegionfolder.test.ts`).
- **Editor-write seam (#194):** `TextEditor.edit(cb)` (с `TextEditorEdit` insert/replace/delete), `editor.selection(s)` геттер/сеттер, `window.visibleTextEditors`, value-тип `Selection`. Правки/выделения субпроцесса едут хосту (`editor.applyEdit` / `editor.setSelection`) и применяются к активному редактору порта `IEditorOptionsService` (правки — одним undoable-батчем через `applyExternalEdits`, с клампом к границам; guard по совпадению uri).
- **Workspace-edit seam (#196):** `workspace.applyEdit(WorkspaceEdit)` — обобщение editor-write на несколько ресурсов: субпроцесс сериализует текстовые правки per-uri (`IWireApplyWorkspaceEditParams`) и шлёт RPC `workspace.applyEdit`; хост применяет через `IEditorOptionsService.applyWorkspaceEdit` (документ ищется в ЛЮБОЙ вкладке, каждый — своим undoable-батчем; all-or-nothing по валидации: закрытый или read-only ресурс — честный `false` без применения чего-либо). Файловые операции `WorkspaceEdit` не поддержаны — субпроцесс отвечает `false` сам, без RPC; сниппет-правки (`SnippetTextEdit` — класс-ловушка конвертера клиента) применяются текстом со стрипом плейсхолдеров. Люфты — docs/TODO/LSP.md.
- **Document sync (LSP) — зеркало документа в субпроцессе (G3, как `$acceptModelChanged` эталона):** `editor.didOpen` — полный снапшот (`IWireDocumentSyncSnapshot`: uri, languageId, `version` = `versionId` модели, text), дальше `editor.didChange` — правки батча модели (`IWireDocumentChangedEvent`: `{range, text}[]` в порядке применения, `version` после батча, isDirty) из `ITextDocument.onDidChangeModelContent`; замена содержимого целиком (flush, перечитка с диска) едет снапшотом в том же `didChange`. Продюсер — `bindDocumentSync` (`api/browser/documentSyncAdapter.ts`, проводка в module/харнессе) через порт `IDocumentSyncTarget`. Каждый батч уходит **синхронно, без коалесинга и без гейта подпиской**: запрос провайдера, ушедший следом, едет по тому же каналу после правки, а пропуск любой правки испортил бы зеркало. Хост (`DocumentsCustomer`) шлёт правки только документам, которые субпроцессу открыл (`synced` спавна; семя открытых документов на handshake тоже открывает); порог синхронизации — 50 Mi символов (опция `maxSyncedDocumentChars`, как `_MODEL_SYNC_LIMIT` эталона) решается на открытии: документ сверх него для расширений не существует, а flush, переросший порог, его закрывает. Синхронизируются документы вкладок и сторон дифф-вкладок (`IEditorService.getTextSurfaces`), но не панели Output: строка лога канала RPC, уехав правкой, порождала бы новую. Субпроцесс (`DocumentSyncTracker`): `open` — снапшот (новый ресурс → `onDidOpenTextDocument`, изменившийся текст → одна full-range правка), `change` — правки применяются к строкам зеркала по одной (`ExtHostTextDocument.acceptChanges`, `rangeOffset`/`rangeLength` по строкам до каждой правки), `onDidChangeTextDocument` несёт настоящие `contentChanges` и `document.version` = версия модели; правки неоткрытого документа отбрасываются с предупреждением. **Запросы текста не везут:** `languages.provide*` и will-save несут `version` (`versionId` модели на момент запроса, в ядре — поле `versionId` seam-запросов `editor/common/languages/i*Source.ts`); хост по несинхронизированному документу отвечает пусто без RPC (`isSynced`), субпроцесс берёт документ из зеркала (`DocumentSyncTracker.resolve`) и отвечает пусто, если он не открыт или запрос устарел (версия запроса позади зеркала); версия впереди зеркала — нарушенный порядок, предупреждение. Как у эталона, корректность держит порядок сообщений в одном канале, а не текст в запросе. Активный документ пушится на `host.ready` ДО активации (стоковый `vscode-languageclient` читает `workspace.textDocuments` на `start()`).

- **Транспорт отмены RPC:** `RpcEndpoint.request(method, params, { token?, timeoutMs? })` — сработавший токен вызывающего уходит второй стороне зарезервированной нотификацией `$/cancelRequest {id}` (аналог LSP), а принимающая сторона гасит токен, который выдаёт обработчику вторым аргументом (`IRequestHandler = (params, token) => unknown`). Транспорт общий для всех методов; подключение провайдера к отмене — это проводка токена, а не новый протокол. Ядро проводит свой токен у всех pull-запросов языковых фич: `*Provider.provide*(request, token)` → прокси `LanguageFeaturesAdapter` → `ExtensionHost.provide*` → `LanguageFeaturesCustomer.request(…, { token })`; источник токена — билет `LatestRequest` потребителя (у Format — `EditorStateCancellationTokenSource`), без токена — resolve пункта автодополнения, `applyCodeAction`, разовые команды code actions и save-участники (см. docs/TODO/Cancellation.md). Тихие края: отмена, пришедшая ПОСЛЕ ответа, не шлётся вовсе (подписка на токен снимается вместе с ответом), а отмена, обогнавшая свой запрос на переупорядоченном транспорте, запоминается (последние 64 id) и выдаётся обработчику уже отменённым токеном; `dispose` endpoint'а отменяет всё, что ещё считается. В субпроцессе каждый провайдер языковых фич и провайдер содержимого (`TextDocumentContentProvider`) получает настоящий `vscode.CancellationToken` поверх транспортного (`api/common/vscodeCancellation.ts`, подписка снимается по завершении вызова), а обход цепочки провайдеров (completion, folding, inline) на отмене прерывается. Сбой провайдера, кроме `CancellationError`, — строка в stderr с методом и стеком (`reportProviderFailure`): `[ext-host] [<id>] <method> failed: …`, где `<id>` — расширение, зарегистрировавшее провайдера (регистрация запоминает окружающего владельца G7 в момент `register*`; регистрация мимо оверлея — строка без `[<id>]`). Упавшая команда code action (`applyCodeAction command "<команда>"`) — туда же, а не молчаливым `false`; предупреждение `registerTextEditorCommand` без активного редактора тоже несёт id владельца; `RpcEndpoint` субпроцесса пишет свои warn туда же (`createStderrLogger`), host зеркалит stderr в канал `extensions.host.stderr`.
- **Срок ответа = отмена (G4):** `timeoutMs` в `request` — истёкший срок отменяет запрос тем же `$/cancelRequest` (провайдер видит токен, language server — свою отмену) и отклоняет промис `TimeoutError`, не дожидаясь опоздавшего ответа. Сроки pull-запросов хоста — одна таблица по методу провода `DEFAULT_REQUEST_TIMEOUTS` (`services/extensions/node/requestPolicy.ts`; тесты укорачивают опцией `requestTimeouts`), вместо опций `*TimeoutMs` на каждый провайдер; исключения — inline completions, срок которых едет в самом запросе, и `languages.provideCompletionItems`, у которого срока нет вовсе (как в upstream: по «пустому» ответу ядро открыло бы попап словами из буфера вместо пунктов медленного language server'а; ожидание ограничивает токен `CompletionService` — перезапрос, уход каретки из слова, закрытие). Хост шлёт через `loggingRequest`: истёкший срок — debug, отказ — warn с методом и ошибкой (стек доезжает целиком); результат в обоих случаях пустой, UI не ждёт.
- **Ошибки через RPC (G4):** отказ обработчика едет `SerializedError` (`base/common/errorSerialization.ts`, извлечение из upstream `errors.ts` без `noTelemetry`): `name`, `message`, `stack`, `code` и цепочка `cause` восстанавливаются у вызывающего (`transformErrorFromSerialization`) — `FileSystemError` расширения, `CancellationError` (узнаётся `isCancellationError` и после границы процесса) и стек провайдера не теряются. Бросили не `Error` — значение едет текстом сообщения.
- **Карта протокола (G4):** `api/common/extHostProtocol.ts` (калька upstream `extHost.protocol.ts`, только типы) — `IHostToSubprocess`/`ISubprocessToHost`: запросы `метод → [параметры, результат]` и нотификации `метод → параметры` каждого направления. `RpcEndpoint<TOut, TIn>` типизирует по ним `request`/`notify` (что шлёт сторона) и `handleRequest`/`handleNotification` (что принимает и обязана вернуть); алиасы `HostRpc` (хост, `IExtensionHostContext.rpc`) и `SubprocessRpc` (`IVscodeHostContext.rpc`) задают направление — хост не пошлёт метод, обработчик которого живёт на хосте. `RequestFn` (`services/extensions/node/hostRequests.ts`) берёт из той же карты и параметры запроса хоста, и тип ответа. Параметры в карте — то, что шлёт отправитель; принимающая сторона сужает доверие локально аннотацией (`const p: ЛокальныйВид = params`, поля необязательны). Ответ языковых запросов (`languages.*`, will-save) хост не перепроверяет (G5): форму провода гарантирует сериализатор субпроцесса (`api/common/extHostTypeConverters.ts`, калька upstream; G5 D1) — единственное место утиной проверки объекта расширения: конечность координат диапазонов, кламп `activeSignature`, конечный `kind`, непустые строки. Диапазон на проводе — везде core `IRange` (`{start, end}`, 0-based; G5 C1/C2): языковые запросы и ответы, правки (`IWireEditorEdit` = core `ITextEdit` — `TextEditor.edit`, workspace edit, formatting, правки-спутники resolve; will-save `WireTextEdit` = `ITextEdit` | смена EOL), дельты document sync, маркеры диагностик (`WireMarker.range`), декорации; плоской формы `startLine/…` в проводе нет (выделения `IWireSelection` — anchor/active, это не диапазон). Субпроцесс собирает любой диапазон «API → провод» одним `rangeFrom` (`extHostTypeConverters.ts`; утиный — подходит и `Range` чужого бандла, `Number.isFinite`, перевёрнутый разворачивает в `start <= end`): языковые ответы, правки (`TextEditor.edit`, workspace edit, will-save), маркеры, декорации. Битый диапазон выпадает вместе со своим элементом, а не роняет вызов расширения; если выпали все правки `TextEditor.edit` или текстовой операции workspace edit — ответ `false`, как дал бы разбор хоста. Там же сериализаторы ответов провайдеров (`serialize*`), опций декораций, `WorkspaceEdit` и обратные переводы провод → API (`toVscodeRange`, `toVscodeSelection`, `toVscodeSignatureHelp` — эхо `activeSignatureHelp` провайдер получает экземплярами API-классов), и ответы completion (с resolve), inline, definition, hover, references, formatting в карте — `ICore*`/`ITextEdit`: хост отдаёт их ядру как есть. Где хост — единственный валидатор (нотификации и запросы субпроцесса: `editor.applyEdit`, `workspace.applyEdit`, `diagnostics.publish`, декорации; у субпроцесса — `editor.didChange`), диапазон разбирает один `parseRange` в `wireTypes.ts`. В форму ядра хост переводит только то, что с ней ещё расходится: folding (`wireToCoreFoldingRegions`: floor/кламп/вырожденные — инвариант модели) и prepare rename. Все `provide*` хоста идут одним хелпером `LanguageFeaturesCustomer.request(method, params, empty)`: гарды «спавна нет» и «документ не синхронизирован» и исход сбоя (истёк срок, отказ RPC — `empty`; у rename — отказ с сообщением о причине) живут в одном месте. Прочие ответы субпроцесса (`workspace.fs.readFile`, `workspace.provideTextDocumentContent`, `window.inputBox.validate`) и нотификации субпроцесса по-прежнему проходят `parseWire*`. Код провода разделён по сторонам (G5 D2): в `api/common/wireTypes.ts` — общие типы провода (их держит карта `extHostProtocol.ts`) и разбор того, что читает субпроцесс (`parseWireDocumentChangedEvent`, `parseWireEditorLayout`, ответы хоста), плюс общие помощники `parseRange`/`isFiniteNumber`/`parseWireSelections`; host-only код — в `services/extensions/node/`: `hostWireParsers.ts` (разбор хостом нотификаций и запросов субпроцесса `parseWire*`, перевод в ядро `wireToCore*`, `themeColorIdOf`, `parseDecorationRanges`) и `hostRequests.ts` (`RequestFn`, `requestWillSaveEdits` с переводом в `ISaveEdit` save-участников `services/textfile`). `api/common` значений из `services/*` не берёт. Исключения по месту потребителя: `selectionChangeKindOf` зовёт `api/browser/editorOptionsServiceAdapter.ts` (browser не импортирует node), `reviveWireUri` — `contrib/diff`; они остались в `wireTypes.ts`. У языковых запросов (`languages.provide*`, rename) параметры объявлены один раз (G5): база `IWireDocumentParams {uri, languageId, version}` / `IWirePositionParams` (+ `line`, `character`), адресация провайдера `{handle}` или пачкой `{handles}`; субпроцесс читает тот же тип через `Received<T>` (`Pick<T, "uri"> & Partial<T>`) — своих копий у него нет, и разъехаться сторонам негде. Каналы спавна у customer'ов хоста — тоже `HostRpc` (а не голый `RpcEndpoint`), иначе их `notify`/`request` идут мимо карты. Карта полна: в ней все методы провода обоих направлений — `languages.*`, `workspace.*`, `editor.*`, `diagnostics.*`, `window.*`, `commands.*` (`commands.executeCommand` — запрос в обе стороны), `secrets.*`, `env.*`, `output.*`, `extensions.*`, `host.*`, `memento.*`, `terminal.*`, `tasks.*`; вне карты только служебный `$/cancelRequest`, его ведёт сам `RpcEndpoint`. Метод вне карты не компилируется (нетипизированный `IUntypedProtocol` — только дефолт голого `RpcEndpoint` для тестов транспорта). В рантайме те же расхождения сторон видны: нотификация без обработчика — warn раз на метод, повторный `handleRequest` того же метода бросает `BugIndicatingError` (у запроса один ответчик).
- **Файловые watcher'ы (`workspace.createFileSystemWatcher`):** `RelativePattern` + `FileSystemWatcher` — настоящие. Субпроцесс держит только id и эмиттеры (`fileWatcherNamespace.ts`), а следит за деревом ядро: notify `workspace.watcher.create {id, base, pattern, ignore*Events}` → порт `IExtensionFileWatcher` (в DI — `FileWatcherAdapter` поверх `ITreeFileWatcher` + excludes из `files.watcherExclude`) → обратный notify `workspace.watcher.events`. **Матчинг шаблона — на хосте**: субпроцессу уезжают только подошедшие события, а не весь поток по воркспейсу. Рекурсивность выводится из шаблона (`*` — только прямые дети, `**`/`/` — поддерево) — на этом держится дешёвый watcher `.git` у встроенного git.
- **Локальный диск без RPC (`workspace.fs`, `workspace.findFiles`):** обе поверхности (и `openTextDocument` по промаху реестра) работают **в субпроцессе через `node:fs`**: привязка к диску — `api/node/extHostDisk.ts` (`IExtHostDisk`, как `extHostDiskFileSystemProvider` у эталона), её отдаёт `buildVscodeNamespace` точка входа субпроцесса, а в `api/common` остаются роутер, обход и сборка документов — целевой файл живёт на той же машине и не является открытым буфером ядра, поэтому запроса к хосту не нужно (в отличие от will-save, который ходит за текстом активного документа). Это ещё и правильное место по нагрузке: рекурсивный обход дерева однажды уже голодал главный цикл (см. `files.watcherExclude` и вынос watcher'а в отдельный процесс), а стоковый `redhat.java` зовёт `findFiles` около десяти раз на одной активации. `workspace.fs` (`fileSystemNamespace.ts`) — роутер по схеме: `file` идёт на диск, прочие схемы — провайдеру расширения (`registerFileSystemProvider`), схема без провайдера получает `FileSystemError.Unavailable`; гейт схемы не декоративный — `fsPath` у `untitled:` отдаёт относительный путь, и `writeFile` без него создавал бы файл в `$CWD`. `findFiles` (`findFiles.ts`) — обход в ШИРИНУ с отделённым интерфейсом `IFindFilesScanner` (бюджет каталогов, исключения и матчинг тестируются на карте в памяти); глубина обхода выводится из шаблона (без `**` число сегментов фиксировано), бюджет — 5000 каталогов на запрос, отмена — настоящий `CancellationToken`. Три значения `exclude` из контракта различаются: `undefined` — настройка `files.exclude` (и только она, как в контракте: `search.exclude` сюда не входит), `null` — ничего, шаблон — ВМЕСТО настройки.
- **Webview как честный no-op (`webviewNoop.ts`):** четыре члена `window` (`createWebviewPanel`, `registerWebviewViewProvider`, `registerWebviewPanelSerializer`, `registerCustomEditorProvider`) существуют и ничего не делают. Webview в TUI не будет **by design**, но ОТСУТСТВИЕ члена убивало расширение целиком: панель поднимают первой строкой `activate()`, и `is not a function` уносил заодно команды и провайдеры. Вызов возвращает инертный объект и пишет в Output одну строку про неподдерживаемый webview; декларации в `vscode.d.ts` остаются закомментированными — статус ⛔ рантайм-заглушка не меняет.
- **Деревья как заглушка (`treeViewNoop.ts`):** `window.registerTreeDataProvider`/`createTreeView` существуют, но дерево не рисуется (Phase 8b в [docs/TODO/Extensions.md](../TODO/Extensions.md)). В отличие от webview это не потолок, а временная ступень: декларации деревьев подняты в `vscode.d.ts` целиком (кроме `TreeViewOptions.dragAndDropController`), значения `TreeItem`/`TreeItemCollapsibleState`/`TreeItemCheckboxState`/`ThemeIcon` — эталонные (`vscodeTypes.ts`; поля `TreeItem` — `declare`, чтобы не затенять геттеры подкласса). Без них расширение с деревом умирало дважды: модуль с `class X extends vscode.TreeItem` не грузился вовсе, а `registerTreeDataProvider` в `activate()` давал `is not a function`. Форма — эталонная (`registerTreeDataProvider` = `createTreeView` + dispose, без `treeDataProvider` — бросок); `TreeView` инертный, человеку — одна warn-строка в Output на `viewId` за жизнь субпроцесса (отступление: эталон незаконтрибьюченный view встречает тостом-ошибкой, а у нас view законтрибьючен, просто не рисуется). Честная проводка заменит заглушку без смены поверхности.
- **Сток диагностик (LSP):** `languages.createDiagnosticCollection` (наивная: хранит оригинальные `Diagnostic`, честные get/has/forEach/итератор; `dispose` снимает её и из контекста code actions) → notify `diagnostics.publish` с owner — ключом `MarkerService`, уникальным на коллекцию: `ext:<id>:<имя>` (без владельца — `ext:<имя>`, без имени — `diagnostics`), повтор базы получает `#N`, как уникализирует эталон, — одноимённые коллекции не затирают маркеры друг друга; → опция `ExtensionHost.diagnosticsSink` → мост в `MarkerService.changeOne` (module); потребители (squiggle, панель Problems) слушают `onDidChangeMarkers` и правок не требуют.
- **Прогресс (LSP):** настоящий `window.withProgress` — notify `window.progress.{start,report,end}` → опция `ExtensionHost.progressSink` → `ProgressStatusBarAdapter` (запись статус-бара с анимированным спиннером; report обновляет message/проценты, end снимает; на смерть subprocess'а host гасит живые handle'ы). Отмена не поддержана — токен не стреляет.
- **Пункты статус-бара:** настоящий `window.createStatusBarItem` — notify `window.statusBarItem.update`/`.dispose` → опция `ExtensionHost.statusBarItemSink` → `ExtensionStatusBarAdapter` (запись `StatusBarService` на каждый ПОКАЗАННЫЙ пункт; клик исполняет команду расширения через `ICommandService`). Состояние живёт в субпроцессе, `update` несёт ПОЛНОЕ состояние (у хоста своей копии пункта нет), а непоказанный пункт в проводе не появляется вовсе. Id записи — `extensions.<id пункта>`, где id пункта — `<id расширения>.<свой id>` (как `asStatusBarItemIdentifier` эталона; владелец фиксируется при создании пункта, имя может прийти позже): пространства имён разделены, расширение не может ни перебить, ни скрыть встроенный сегмент (`status.editor.encoding`). Id пункта без явного — slug его `name` (чтобы «скрыл через меню видимости» пережило перезапуск: скрытые id хранит `StatusBarService`), иначе `item-<счётчик>`. Вызов мимо оверлея (общий namespace, владельца нет) даёт id без префикса расширения. Значки `$(name)` в тексте подменяются глифами codicon-шрифта (см. «Значки `$(name)` в тексте расширений» ниже) ДО обрезки по 24 символам — иначе разметка съела бы смысл подписи. Стабы — `tooltip`/`color`/`backgroundColor`/`accessibilityInformation` (принимаются, ни на что не влияют).
- **Значки `$(name)` в тексте расширений:** подменщик — `renderCodicons` (`base/common/codicons.ts` над генерируемой таблицей `codicons.generated.ts`: `scripts/import-codicons.mjs`, пин в лок-степе с `vscode.d.ts`). Политика: известное имя → глиф, **неизвестное выбрасывается** (литерал `$(foo)` хуже, чем ничего), модификатор `~spin` игнорируется, `\$(имя)` — литерал со снятым слэшем. Подмена стоит **в раковине** — в адаптере, который превращает просьбу расширения в нашу модель интерфейса, — а НЕ на границе RPC: подменять можно далеко не всё, что пишет расширение (содержимое канала Output, тела диагностик/ховеров/дополнений, `InputBox.value`, который человек правит и который уезжает обратно, обязаны остаться дословными — `$(…)` там бывает настоящей шелл-подстановкой). Перечень раковин с политикой и обоснованием по каждому полю — `workbench/api/browser/extensionTextSinks.test.ts`; у перечня два гейта: типовой (новое текстовое поле wire-типа без записи краснит `typecheck`) и поведенческий (поле без кейса, гоняющего текст через настоящую раковину, краснит тест).
- **Output-каналы (LSP):** настоящий `window.createOutputChannel` — notify `output.append`/`output.show` → опция `ExtensionHost.outputSink` → `ExtensionOutputAdapter` (ленивая регистрация канала `extensions.<id расширения>.<slug(name)>` в `OutputChannelRegistry` — канал принадлежит расширению, как в эталоне, и не сталкивается с логгерами хоста вроде `extensions.host`; без владельца — `extensions.<slug(name)>`, строки — логгером `ILogService`, `show` — команда `workbench.action.output.show.<id>`). `append` буферизуется в subprocess до `\n` (панель строчная).
- **Сообщения человеку:** `window.show{Information,Warning,Error}Message` — **запрос** `window.showMessage` (не notify: перегрузка с кнопками обязана вернуть выбранное) → опция `ExtensionHost.notificationSink` → `NotificationExtensionAdapter` → `NotificationService` (поверхность — стек тостов над статус-баром, у модального сообщения окно по центру; см. docs/arch/Workbench.md). Разбор четырёх перегрузок (`MessageOptions` первым аргументом, кнопки строками или `MessageItem`-ами) живёт в `api/common/messageNamespace.ts`, ответ приходит ИНДЕКСОМ в присланном массиве — расширение обязано получить обратно свой объект. Адреса показа на проводе нет: отменять показ расширение не умеет (у `show*Message` нет токена), а «погасить при смерти субпроцесса» решается handle'ом, который минтит сам хост. Сообщение вдобавок дублируется в лог расширений — тост гаснет, а прочитать сказанное надо и потом. Исключение стока НЕ отклоняет запрос (`index: null` + строка в лог): отказ доехал бы до `await show*Message(...)` расширения, а необработанный reject валит весь субпроцесс.
- **`env.clipboard` / `env.openExternal`:** запросы `env.clipboard.{readText,writeText}` → опция `ExtensionHost.clipboard` (тот же `IClipboard`, которым пользуются copy/paste ядра: OSC 52 + внутренний регистр) и `env.openExternal` → опция `ExtensionHost.externalOpener`. Uri уезжает по проводу как `toString(true)` (skipEncoding) — как в эталоне, где ссылка отдаётся системному обработчику именно в этой форме; обычный `toString()` percent-кодирует `=`/`&` в query, и системе досталось бы `?token%3D42`.

Рантайм «как VS Code»: JS-энтрипоинты запускаются `process.execPath` субпроцесса (dev/self-extract — настоящий node; SEA — diode-бинарь в node-режиме `DIODE_RUN_AS_NODE=1` — ранний branch `runAsNode.ts`, калька `ELECTRON_RUN_AS_NODE`; env сервера всегда снимает `DIODE_EXTENSION_HOST`). Наивные стабы поверхности languageclient (no-op провайдеры, naive-события, env, `version` в лок-степе с `extensions/VSCODE_VERSION`) — статусы и шаги закрытия в docs/TODO/LSP.md.
- **Проекция выделения host → subprocess (#194):** первичное выделение едет в `IActiveEditorMeta` на смене активного редактора, а **каждое движение каретки** — отдельной нотификацией `editor.selectionChanged` (`IActiveEditorSelections`: uri + все выделения). Продюсер — `EditorService.onDidChangeActiveEditorSelection` (подписка живёт на группе и сама переезжает на новый активный редактор) → `IEditorOptionsService.onActiveEditorSelectionChanged` (коалесинг в пределах тика + эхо-гард: выделение, поставленное самим субпроцессом через `editor.setSelection`, назад не уезжает). Отдельное сообщение, а не повторный `activeEditorChanged`, потому что последний дёргает `onDidChangeActiveTextEditor` — встроенный git пересчитывал бы статус на каждое нажатие стрелки. **Без этой проекции любая команда расширения, читающая `activeTextEditor.selection`, видит состояние момента открытия файла** (обычно `(0,0)`) и молча ничего не делает — так ломались все команды `maptz.regionfolder`.
- **Событие выделения (`window.onDidChangeTextEditorSelection`):** производит его САМ субпроцесс из нотификации `editor.selectionChanged` (нового сообщения в проводе нет — добавилось поле `kind`), уже после обновления своих кэшей: слушатель читает `event.textEditor.selection` и обязан увидеть новое. Эхо-гард остаётся на хосте, поэтому выделение, которое расширение поставило само (`TextEditor.selection =`), события не даёт — осознанное отличие от upstream в пользу «расширение не будит само себя». **`kind` (`TextEditorSelectionChangeKind`) едет от ЖЕСТА**, а не угадывается: источник объявляется областью `withCursorChangeSource` (`editor/common/core/cursorChangeSource.ts`) вокруг обработчика — ввод и мышь в `EditorElement`, диспетчер кейбиндов (`keyboard`: стрелки у нас исполняются командами, но для расширения это Keyboard, как в VS Code), обработчик `commands.executeCommand` от расширения (`command`). Снимается источник СИНХРОННО в `EditorOptionsServiceAdapter` (в отложенном флаше коалесинга область жеста уже закрыта), вложенная область не перебивает внешнюю. Неразмеченный жест (undo/redo, find, фолдинг, программная правка) едет без поля — `kind: undefined` upstream объявляет явно. Плоского «протащить причину через пять сигнатур» не делаем: у потребителя один, и ambient-область дешевле.
- **Активная тема (`window.activeColorTheme` + `onDidChangeActiveColorTheme`):** notify `window.themeChanged {kind}` (host → subprocess) через тот же порт `IThemeColorResolver`, что резолвит `ThemeColor` — второго порта к теме не заводим, событие смены у обоих потребителей одно. `ThemeColorResolverAdapter.kind()` переводит `WorkbenchTheme.type` в `vscode.ColorThemeKind`. Сообщение уходит **семенем на handshake, ДО первой активации** (расширение читает тему уже в `activate()`, чтобы выбрать иконки/цвета) и на каждую настоящую смену темы; субпроцесс стреляет событием на каждое пришедшее сообщение, включая переход между двумя тёмными темами — upstream формулирует событие как «changed **or has changes**». До первого сообщения тема — `Dark` (дефолт VS Code), а не `undefined`: `activeColorTheme.kind` читают без проверок.
- **Уборка расширения в субпроцессе** (`services/extensions/node/extensionDeactivation.ts`): `deactivate()`, затем `context.subscriptions` в обратном порядке; сбой любого шага — warn `[ext-host] [<id>] deactivate failed` / `subscription dispose failed` в stderr, уборка доходит до конца и наружу не бросает (и в `host.deactivateExtension`, и при выключении).
- **Изоляция сбоев субпроцесса:** `runExtensionHostSubprocess` ставит `process.on("unhandledRejection")` — расширение, не поймавшее свой промис (исторический пример: стоковый maptz после `wrapWithRegion` fire-and-forget звал `editor.action.formatDocument`, до #196 отсутствовавшую), логируется в stderr и **не уносит с собой host** со всеми остальными расширениями. Причина печатается со **стеком** (`describeRejection`): `String(err)` даёт только «Error: message», по которой не найти ни виноватое расширение, ни строку.
- **`localhost` в субпроцессе — IPv4 первым:** `runExtensionHostSubprocess` ставит `dns.setDefaultResultOrder("ipv4first")` — то же, что `--dns-result-order=ipv4first` в execArgv extension host'а VS Code (`localProcessExtensionHost.ts`, issue #189805). С дефолтным `verbatim` Node вешает `net.listen(port, "localhost")` на `::1` там, где `/etc/hosts` ставит его выше, а клиент на Java (`Socket("localhost", port)`, JVM предпочитает IPv4) стучится в 127.0.0.1 и получает «Connection refused» — так bazel-java терял лог синхронизации. Функцией, а не флагом: под SEA execArgv бинаря не наш (прецедент эталона — `cliProcessMain.ts`). Отступление: дети субпроцесса (`cp.fork` из расширения) порядок не наследуют — в VS Code он уезжает вместе с execArgv. Тест — `extensionHost.localhost.test.ts` на синтетическом расширении.
- **Каталоги хранения (`ExtensionContext.globalStorageUri` / `storageUri` / `logUri` + депрекейтнутые строковые близнецы):** корни даёт ХОСТ — раскладку user-data знает приложение, и субпроцессу её не выдумывать. Опция `ExtensionHost.storageHomes` — **ленивый** провайдер (`() => IExtensionStorageHomes`): папка воркспейса выставляется позже создания хоста, а `storageUri` зависит именно от неё, поэтому корни читаются на каждой активации. Сами корни собирает `extensionStorageHomes` (чистая, из путей user-data и текущей папки), пути одного расширения — `resolveExtensionStoragePaths`; и то и другое уезжает в `host.activateExtension`, а субпроцесс только оборачивает их в `Uri.file`. Регистр id повторяет эталон дословно, включая асимметрию: `globalStorage` — по **lowercase** id, `workspaceStorage`/`logs` — по id как есть. Разделение ответственности за каталоги — из контракта `vscode.d.ts`: **родителя** создаёт хост (`ensureExtensionStorageParents`, best effort — недоступный на запись user-data не рубит активацию), **свой** каталог создаёт расширение. Папка не открыта ⇒ `storageUri` = `undefined`, как в VS Code. Без опции — `fallbackExtensionStorageHomes()` (каталог во временных файлах ОС): `globalStorageUri` по API необязательным не бывает, а расширение падает на нём в первой же строке `activate()`.
- **`ExtensionContext.extension`** — запись самого расширения из каталога `vscode.extensions` (телеметрии читают по ней `packageJSON.name`/`version` первой строкой `activate()`). Эталон строит в `_loadExtensionContext` отдельный `Extension` из описания расширения; у нас объект уже лежит в каталоге, который хост шлёт семенем до первой активации и на каждой регистрации, поэтому субпроцесс берёт `getExtension(id)` общего namespace (оверлей владельца `extensions` не перекрывает). Записи нет — нарушен контракт хоста, активация падает с именем расширения, а не TypeError'ом внутри него. Идентичность с `getExtension(id)` не обещается (эталон тоже отдаёт отдельные экземпляры): новый каталог пересобирает объекты, но `isActive`/`exports` у старой записи остаются живыми.
- **Memento (`ExtensionContext.globalState` / `workspaceState`):** хранилище держит ХОСТ (`IExtensionStateStore`, опция `ExtensionHost.extensionState`; в проводке — `createExtensionStateStore` поверх общего `IStateService`, ключ `extensionState/<id>`, `globalState` — scope `global`, `workspaceState` — `workspace`, то есть стор открытого проекта или пустого окна), поэтому memento переживает перезапуск, как и состояние workbench'а. Субпроцесс держит словарь у себя (`get`/`keys` синхронные), начальный приезжает в параметрах `host.activateExtension` (без отдельного round-trip), а `update` отдаёт хосту словарь целиком запросом `memento.update` и резолвится по ответу; опустевший словарь удаляет запись (`IStateService.remove`). Запись `workspaceState` из воркспейса, отличного от того, где расширение активировано, хост отбрасывает с предупреждением: словарь A не протечёт в стор B (честное лечение — перезапуск хоста при смене папки). `setKeysForSync` — осознанный no-op (Settings Sync нет). Без проводки (тесты, харнессы) — `createTransientExtensionStateStore`: memento живёт в памяти субпроцесса.
- **Секреты (`ExtensionContext.secrets`):** хранилище держит ХОСТ (`IExtensionSecretStore`, опция `ExtensionHost.secrets`), субпроцесс только ходит в него запросами `secrets.get`/`store`/`delete`/`keys` — причина та же, что у каталогов хранения: раскладку user-data знает приложение. Секреты переживают перезапуск (в них лежит токен сервиса, который расширение спрашивает у человека один раз) — отдельный файл `<profileDir>/secrets.json` (0600, синхронная запись), `createFileExtensionSecretStore`. Лоток у каждого расширения свой: ключ хранения составной (id расширения + ключ секрета), причём id подставляет субпроцесс, а не сам вызов — чужой лоток расширению не адресовать. `onDidChange` приходит уведомлением `secrets.changed` от хоста и на СВОИ записи тоже (в эталоне событие описывает факт изменения, а не его источника); один диспетчер на субпроцесс разводит его по id. **Шифрования нет** — связки ключей ОС у нас нет, значения лежат открытым текстом под правами `0600`; замалчивать это нельзя, поэтому оно написано и здесь, и в [матрице](../public/API-COVERAGE.md). Отсюда же правило: значения секретов не логируются нигде, и сообщения об отказе хендлеров `secrets.*` не содержат параметров запроса (в соседнем поле того же объекта едет значение).
- **Каталог расширений (`vscode.extensions`):** состав знает только хост (он держит регистрации), поэтому каталог едет уведомлением `extensions.catalog` — **семенем на handshake, ДО первой активации** (`getExtension` зовут прямо в `activate()`, детектя соседей: в бандле Supermaven таких вызовов четыре) и на каждую смену состава. Активность доводится отдельным точечным `extensions.activated {id}`: манифесты тяжёлые (у языковых серверов `package.json` со схемой настроек — сотни килобайт), а меняется один флаг. Источник состава — `ExtensionPhases.all()` (все регистрации в порядке появления, отдельно от фаз «ждёт активации» и «активно»), `packageJSON` — манифест регистрации целиком. `exports` (публичный API расширения) по проводу не ездят вовсе: все расширения живут в ОДНОМ субпроцессе, и значение берётся из карты `IVscodeHost.extensionExports`, куда точка входа кладёт результат `activate()`. **Расхождение с эталоном:** декларативные расширения (языковые паки без `main`) в extension host не регистрируются и в `all` не попадают. `Extension.activate()` у активного расширения отдаёт его `exports`, у неактивного — честно отклоняется: активацией распоряжается хост, и «субпроцесс просит хост поднять соседа» — отдельная задача со своим RPC. `extensionKind` — константа стороны субпроцесса (`ExtensionKind.UI`): upstream предписывает именно её, когда удалённого extension host'а нет.
- **Команда `setContext`:** встроенная команда VS Code, которой расширения публикуют собственные when-ключи (`commands.executeCommand("setContext", "supermaven.isProUser", true)`). Регистрирует `SetContextCommandContribution` (`workbench/browser/`) — без title, в палитре её быть не должно. Имя ключа регистрировать не нужно: when-вычислитель (парсер грамматики VS Code) читает любое имя целиком, в том числе **точечное** (`publisher.thing`); массив и объект хранятся как есть под оператор `in` — см. [Workbench.md](Workbench.md#система-команд).
- **`contributes.menus` / `contributes.submenus`:** декларативный contributor `extensionMenuContributor.ts` (не через host, как keybindings) переводит строковые id точек VS Code в наши `MenuId` и кладёт пункты в `MenuRegistry.appendMenuItem`. Правила разбора и список поддержанных точек — в [Workbench.md](Workbench.md#menuregistry-srcvsplatformactionscommon); неизвестная точка, пункт без команды и ссылка на необъявленное подменю — строка в лог и пропуск пункта, а не падение расширения. Пункты смотрят на upstream-имена контекст-ключей (`editorLangId`, `editorTextFocus`), поэтому они выставляются рядом с нашими.
- **`contributes.keybindings` (#194):** декларативный contributor `extensionKeybindingContributor.ts` (не через host) собирает манифестные биндинги всех расширений в слой extension `KeybindingRegistry` (`setExtensionKeybindings`): бинд расширения сильнее встроенного на той же комбинации, пользовательский из `keybindings.json` — сильнее бинда расширения, независимо от порядка шагов старта; `key`/`mac`/`linux`/`win`, `-command` — снятие из слоёв default и extension (user-бинды не трогает).
- **`IExtensionRegistration`** несёт `commandTitles`, `commandCategories` и `activationEvents`. `commandTitles` нужны, чтобы рантайм-`registerCommand` расширения **показался в палитре** (host заводит прокси в `CommandRegistry` с этим title; иначе команда исполнима, но невидима). `commandCategories` — `category` из того же вклада (`"Java"`): палитра рисует её **префиксом подписи** («Java: Switch to Standard Mode», `commandPaletteLabel`), но в сам `title` она не входит — иначе протекла бы в меню и в статус-бар, где эталон её не показывает. `activationEvents` — см. «Активация» ниже.
- **Lifecycle:** `ExtensionHost.dispose()` — graceful `host.shutdown` → `SIGTERM` → `SIGKILL`; `shutdown()` — то же, но отдаёт промис прощания; `disposeNow()` — синхронно добивает сигналом субпроцесс, который ещё не вышел (перезагрузка окна: дальше идёт `spawnSync` нового процесса, и он остался бы сиротой). Оба подключены к прощанию `LifecycleService` в `extensionHostModule`: `shutdown()` — в асинхронной фазе `onWillShutdown`, `disposeNow()` — в синхронной `onShutdownSync`, так что выход, перезагрузка и выход по инспектору снимают host одинаково. В DI — `ExtensionHostDIToken`. `main.ts` содержит ранний branch на env-флаг: subprocess уходит в `runExtensionHostSubprocess()`, обычный запуск — в `runEditor()`.
- **Смерть субпроцесса:** расширение может уронить свой процесс (краш нативного модуля, OOM, `process.exit`). `exit` ребёнка → `handleSubprocessDeath` → общий с вежливым выключением `endSpawn()`: `spawnStore` снимается целиком, и каждый customer отдаёт то, что держал мертвец (спиннеры прогресса, пункты статус-бара, декорации, прокси-команды, watcher'ы, схемы провайдеров ФС и содержимого, языковые провайдеры, флаги подписок, подписки на события ядра — `editorLayout`, `editorOptions`, `configuration`); хост забывает `rpc` и процесс. Ручного списка сброса нет: новое состояние спавна заводится в `attach` и уходит само, респавн не копит слушателей. Канал мертвеца закрывается (`rpc.dispose()`): запросы в полёте получают отказ, и активация, оборванная смертью, возвращается в `pending` вместе с остальными, а не теряется (если расширение за это время не сняли). Активные расширения при этом возвращаются в `pending`, а **любое** следующее событие активации сперва проигрывает **журнал запрошенных событий** (`requestedEvents`, как `_allRequestedActivateEvents` эталона; `ensureSubprocess` спавнит новый субпроцесс) и проход `workspaceContains:` (его повод в журнал не пишется — заново по ФС): их собственное событие (`*`, `onStartupFinished`, `onLanguage:<уже открытый язык>`) давно отгорело и второй раз не наступит. Оживление ленивое, на следующем событии, а не сразу при смерти — краш-петлю не устраиваем. Тот же журнал поднимает расширение, зарегистрированное **после** своего события (`_activateAddedExtensionIfNeeded` эталона): оно встаёт на самой регистрации. `activateByEvent` дожидается и расширений, которые уже поднимает другой вызов (активации «в полёте»), — его промис значит «расширения события активны». Заглушки-активаторы команд при этом возвращаются на место снятых прокси — см. «Активация» ниже.

### Активация (activationEvents)
Расширения активируются **лениво** по `manifest.activationEvents` — до триггера код расширения не грузится и subprocess под него не поднимается. Механика целиком на родительской стороне `ExtensionHost`; ядро про activation-events не знает.
- **Владелец цикла — `ExtensionService`** (`services/extensions/node/extensionService.ts`, интерфейс `IExtensionService` и токен — `services/extensions/common/extensions.ts`; аналог vscode `IExtensionService`, узкий срез). Политика «что и когда активировать» — у сервиса, механика (RPC, субпроцесс) — у `ExtensionHost` (сервис видит его через узкий `IExtensionActivationHost`). `start()` (зовёт старт окна в фазе `restored`, хук `afterRestored` у `workbenchStartup.ts`): регистрирует набор (`ctx.extensions` модуля — пользовательские, затем встроенные) через `toExtensionRegistration` (веха `main:extensions-registered`), затем, как `_handleEagerExtensions` эталона, **параллельно** `*` (за ним — события, запрошенные до регистрации, и **барьер** `whenInstalledExtensionsRegistered`) и проход `workspaceContains:`; `onStartupFinished` — после них, но не позже `STARTUP_FINISHED_TIMEOUT_MS` (10 с, `timeout(10000)` эталона), и веха `exthost:activated`. Старт окна `start()` не ждёт: фаза `eventually` (фоновый прогрев, `main:startup-complete`) от активации не зависит, трасса выгружается, когда есть обе вехи. Сбой host'а на одном стартовом событии — лог `extension host activation failed (<событие>)`, остальные события всё равно идут. **Память событий** (как `_allRequestedActivateEvents` эталона): `activateByEvent` до барьера запоминает событие (без повторов, в порядке прихода) и резолвится на барьере, после — идёт в host сразу. Поэтому файл, открытый на старте раньше регистрации, свой `onLanguage:` не теряет, и ручной `onLanguage:` активного редактора из `main.ts` больше не нужен. Сбой регистрации одного расширения — лог с id, сбой host'а — лог `extension host activation failed`; барьер открывается в любом случае. Набор статичен на жизнь окна (установка — через перезагрузку), событий состава нет.
- **Сборка регистрации — одна функция:** `toExtensionRegistration(ext, env)` (`services/extensions/node/extensionRegistration.ts`) из записи скана: манифест целиком, заголовки/категории команд (`collectCommandMeta`), события активации; пользовательское — `mainPath`/`extensionPath` с диска, встроенное — `source`/`filename` из ассетов; без `main` — `null`. Ей же собирают регистрацию стоковые фикстуры тестов (`TestUtils/installedExtensionRegistration.ts`), так что в сьютах регистрация ровно прод-овая.
- **Настройки расширений — в общем реестре.** `contributes.configuration` всех расширений (включая декларативные и ещё не активированные) регистрирует в `ConfigurationRegistry` главного процесса `ExtensionConfigurationContributor` (`services/extensions/common/`, аналог `configurationExtPoint` vscode) — на bootstrap, до загрузки настроек, поэтому скан расширений в `main.ts` идёт раньше `loadConfiguration`. Дубль ключа — warn в лог `extensions` и пропуск; `scope` без значения — `window`. Инъекции хоста (курируемые дефолты сторонних — `curatedConfigInjection`, пути вшитого tsserver — `builtinConfigInjection`) ложатся переопределениями дефолтов (`registerDefaultConfigurations`). Следствия: ядро видит дефолты `git.*`, валидатор settings.json не помечает ключи расширений «unknown», а субпроцесс своего defaults-слоя не держит — хост шлёт ему слои `{ defaults, user, workspace }` (`IConfigurationService.getConfigurationData()`; `workspace` — `.diode/settings.json` открытой папки, уже отфильтрованный по `scope`), `WorkspaceConfigStore` сливает их той же `ConfigurationModel` (как `ExtHostConfigProvider` vscode). `configDefaults` в регистрации и в `host.activateExtension` больше нет. Значения ключей расширений по схеме не валидируются (схема расширения — полный JSON-schema). Тестовый харнесс собирает дефолты тем же контрибьютором из манифестов своих регистраций (`manifestWithDefaults` — описать настройки фикстуры в её манифесте).
- **Регистрация ≠ активация.** `registerExtension(reg)` — синхронный bookkeeping: кладёт reg в `pending`, регистрирует `commandTitles` и заглушки-активаторы команд (палитра видит команды до активации), возвращает disposable. Subprocess **не** поднимается.
- **Разбор событий — один на всех:** `services/extensions/common/activationEvents.ts`. Точное сравнение строк закрывает только виды без аргумента (`*`, `onStartupFinished`) и те, где аргумент приносит вызывающий (`onLanguage:<id>`, `onCommand:<id>`); `workspaceContains:<паттерн>` так не закрывается — его аргумент надо сверять с ФС.
- **`activateByEvent(event)`** — идемпотентно активирует `pending`-расширения, чьи события активации содержат событие: `ensureSubprocess()` → `host.activateExtension` RPC → перенос в реестр активных. Набор одного события активируется **параллельно** (`Promise.all`, как `_activateExtensions` эталона) с изоляцией сбоя каждого: стоковый LSP-клиент, поднимающий сервер секундами прямо в `activate()`, соседей не держит. Ошибки spawn/`parseActivateParams` (в т.ч. конфликт `source`/`mainPath`) всплывают здесь, а не на регистрации.
- **Дефолт `*` — осознанное отклонение от эталона:** манифест без событий (пусто или нет поля) считается eager — у vscode пусто значит пусто, но в нашем магазине опубликованы расширения, которые на этот дефолт полагаются (`test.tab-setter`), и эталонный дефолт молча выключил бы их у пользователей. Считает дефолт сборка регистрации (`computeActivationEvents`), хост его не додумывает: регистрация с пустым набором не поднимается. Тестовым регистрациям в обход сборки eager-дефолт даёт харнесс (`testRegistration`, `extensionFixture`).
- **Неявные события — явный список генераторов** `IMPLICIT_ACTIVATION_EVENT_GENERATORS` (`activationEvents.ts`, как `activationEventsGenerator` у дескрипторов точек эталона): `contributes.commands` ⇒ `onCommand:<id>` (иначе видимая в палитре команда не-eager расширения была бы вечным no-op'ом), `contributes.languages` ⇒ `onLanguage:<id>`, `contributes.taskDefinitions` ⇒ `onTaskType:<type>`. Полный набор (`computeActivationEvents`: объявленные + неявные) считается **один раз при сборке регистрации** (`toExtensionRegistration`) и лежит в `IExtensionRegistration.activationEvents`; хост только сравнивает строки и про `contributes` не знает. Генераторы для поверхностей, которых у нас нет (`onView`, `onUri`, …), появятся вместе с поверхностью.
- **Поддержанные события:** `onTaskType:<type>` (фаерит сервис задач перед тем, как спросить провайдеров, — см. «Задачи расширений»), `*` и `onStartupFinished` (фаерит `ExtensionService.start()` после регистрации, когда файлы открыты), `onLanguage:<id>`, `onCommand:<id>`, `workspaceContains:<паттерн>`. `onLanguage:<id>` — владелец сигнала сервис языков (как `requestRichLanguageFeatures` эталона): `TextFileModel` зовёт `ILanguageService.requestLanguageFeatures(id)`, когда у документа появляется язык (новая модель, открытый файл, синтетический документ) или меняется (Change Language Mode, Save As); `LanguageRegistry` фаерит `onDidRequestLanguageFeatures` один раз на язык, и `extensionHostModule.ts` переводит его в `ExtensionService.activateByEvent("onLanguage:"+id)` плюс голое `onLanguage`. Так расширение встаёт для любой модели — фоновой вкладки, диффа, `jdt:`-документа, — а не только для активного редактора; стартовые (модели открылись до регистрации) сервис запоминает и проигрывает за `*`.
- **`onCommand:<id>` — заглушка-активатор, а не только событие.** Пофаерить событие мало: настоящий прокси команды заводит сам субпроцесс в `commands.registerCommand`, то есть уже ПОСЛЕ `activate()`, и команда до активации попросту не нашлась бы. Поэтому `registerExtension` кладёт в `CommandRegistry` заглушку под каждый `onCommand:<id>` (с `commandTitles`-заголовком — значит команда видна в палитре): её исполнение сперва `await activateByEvent`, потом вызов уже живого прокси. Заглушка не затирает живой прокси, снимается на `commands.registerCommand`, и **возвращается на место после смерти субпроцесса** — иначе команда исчезла бы из палитры вместе с единственным ручным способом оживить расширение. Провал хоста и «расширение поднялось, но команду не завело» гасятся логом: вызывающие (палитра, бинд) результат не ждут, и reject ушёл бы в `unhandledRejection` главного процесса.
- **`workspaceContains:<паттерн>` — повод считается по ФС**, поэтому у него свой вход `activateByWorkspaceContains()` и своя единица: не «событие на всех», а **расширение** (паттерн — аргумент события, и подошёл он конкретному манифесту; так же устроен `checkActivateWorkspaceContainsExtension` эталона). Причина подъёма — подошедший паттерн — уходит в лог хоста. У префикса **две семантики**, и сводить их к одной нельзя: паттерн **без** glob-символов — простая проверка существования пути относительно каждой папки воркспейса (истинна и для каталога, `workspaceContains:.vscode`), паттерн **с** ними — поиск ФАЙЛА по дереву. Обход — `node/workspaceContainsActivation.ts` за сеамом `IWorkspaceScanner` (в проде — настоящая ФС): в ширину, с глубиной по самому щедрому паттерну (`*.py` читает только корень, `*/pom.xml` — корень и первый уровень, `**` снимает ограничение), мимо `.git`/`node_modules`, с бюджетом каталогов и тайм-аутом 7000 мс как в эталоне. Тайм-аут — гонка, а не только флаг отмены: повисший `readdir` флагом не сдвинуть. Оборванный обход виден в логе — молча усечённый читался бы как «ничего не подошло».
  - **Расхождение с эталоном:** глобы матчатся нашим `base/common/glob.ts` — якорно по относительному пути, `*` не переходит `/`. У эталона за `workspaceContains:` стоит поиск на ripgrep, где паттерн без `/` ищется на любой глубине: `workspaceContains:*.py` там поднимет расширение и на `src/main.py`, у нас — только на `main.py` в корне. Второй диалект глобов ради этого не заводим; рекурсивные паттерны (`**/pyproject.toml`) работают одинаково.
  - **Лениво.** Папка воркспейса может открыться позже регистрации расширений, поэтому стартовый проход делает `ExtensionService.start()` (последним из стартовых событий — обход дерева единственный из них ходит на диск), а смену набора папок ловит `IWorkspaceContextService.onDidChangeWorkspaceFolders` → `ExtensionService.activateByWorkspaceContains()` в `extensionHostModule.ts` (до барьера проход ждёт стартовый). Повторный проход дешёвый: активное расширение ушло из `pending`, кандидатов нет — ФС не трогается вовсе.
- **`extensionDependencies` — зависимости активируются раньше зависимого** (`activateAfterDependencies` в `ExtensionHost`, как `_handleActivationRequest` эталона): расширение в `activate()` вправе читать `exports` соседа через `extensions.getExtension(dep)`, поэтому зависимость поднимается, даже если её собственные события не наступали (стоковый форк bazel-java зовёт команды `redhat.java`, а у того в Bazel-воркспейсе своих событий нет). Причина в логе — `dependency of <id>, <событие>`. Ожидающая зависимость активируется, поднимающаяся — дожидается, активная — годится сразу; id сравниваются без учёта регистра, разбор манифеста и поиск цикла — `platform/extensions/common/extensionDependencies.ts` (общий с установкой из магазина). Не вышло — зависимое **не активируется** (эталонный `FailedExtension`), оживляет его только перезагрузка окна:
  - зависимости нет среди установленных — ошибка в лог и **тост** «Cannot activate the '<имя>' extension because it depends on unknown extension '<id>'» (текст `unknownDep` эталона; кнопок «Install/Enable and Reload» эталона нет — минимальный вариант). Тост хост шлёт тем же стоком `notificationSink`, что и `window.show*Message`, под отрицательными адресами: свои показы субпроцесса растут от 1 и гасятся на его смерти, тост хоста к ней отношения не имеет;
  - зависимость упала в `activate()` (сейчас или раньше) — только лог, как у эталона в собранной версии;
  - цикл (`a → b → a`) — только лог с цепочкой; каждый участник узнаёт о цикле на своей активации (у эталона они выпадают из реестра целиком — наблюдаемо то же);
  - **встроенного расширения VS Code** (`vscode.*`) у Diode нет — **отступление**: зависимое поднимается без него, с предупреждением в лог (`isBuiltinVSCodeExtension`). У эталона они часть продукта и есть всегда, а у нас многих нет (`git` — это `diode.git`), и поставить их неоткуда: строгий вариант молча выключил стоковый Supermaven (`extensionDependencies: ["vscode.git"]`). Встроенные `vscode.*`, которые у нас есть (`vscode.git-base`), зарегистрированы и поднимаются обычным порядком;
  - расширение **без кода** (декларативный языковой пак, тема) регистрации в хосте не имеет, но зависимость на него удовлетворена: `ExtensionService.start()` сообщает хосту такие id (`registerDeclarativeExtension`), как `_isResolvedExtension` эталона;
  - субпроцесс умер, пока поднималась зависимость, — зависимое не считается упавшим и возвращается к оживлению вместе с ней.
- **Тест-хелпер:** `registerAndActivate(host, reg)` (`TestUtils/ExtensionTestHarness.ts`) = `registerExtension` + `activateByEvent("*")`; харнесс фаерит `activateEvents` (дефолт `["*"]`) после регистрации.

### Пример: builtin `diode-settings` (автодополнение настроек)
`Extensions/builtin/diode-settings/` — code-расширение, активируется **только** по `onLanguage:json`/`onLanguage:jsonc` (доказательство лениости: пока не открыт JSON — не грузится). В `activate()` регистрирует `registerCompletionItemProvider` с селектором `pattern:"**/settings.json"` → в `settings.json` подсказывает известные ключи настроек. Каталог ключей **вшит на этапе сборки**: `scripts/generate-settings-schema.mjs` (запускается из `build-extensions.mjs` перед esbuild) собирает ключи из app-дефолтов (`Configuration/defaults.ts`) + `contributes.configuration` всех builtin и пишет `settings-schema.generated.ts`, который бандлится в `out/extension.cjs`. Никакого рантайм-API за схемой расширение не ходит.

## Правило роста `vscode.d.ts` (важно)
`src/vscode-dts/vscode.d.ts` — стадийная копия upstream `microsoft/vscode:src/vscode-dts/vscode.d.ts`, всё line-commented кроме активной поверхности. Это дословная копия реального API, а не стаб под реализацию. Инвариант: **файл меняется ТОЛЬКО снятием `// `**.

Структура файла:
1. **Шапка** — провенанс (upstream tag + commit SHA + permalink) и ссылка сюда.
2. **Активный `declare module "vscode"`** — дословно раскомментированные строки upstream. Единственный human-owned блок. Framing-строки (сам `declare module "vscode" {`, его `}`, глобальный `Thenable`) — единственное не-upstream в этой части.
3. **Строка-сентинел** `//@diode:begin-upstream-verbatim …`.
4. **Дормант** — вся upstream-копия, каждая строка с `// `. Генерируется, вручную не редактируется.

**Пиннинг.** Тег зафиксирован в шапке и согласован с `extensions/VSCODE_VERSION` (сейчас `1.127.0`) — держи их в лок-степе. Пин нужен, чтобы обновление upstream шло **ручным трёхсторонним merge**: base = `vscode.d.ts` запинненной версии, theirs = новый upstream, ours = наш файл с раскомментированными блоками.

**Как добавить API.** Найди нужный блок в дормантной части и подними **дословно** (сняв `// `) в активный модуль — не сужать / не переписывать / не переоформлять (комментарии тоже upstream). Если блок тянет ещё не раскомментированный тип (dependency closure) — раскомментируй и его. Runtime-значение может опережать типовую декларацию: неймспейсы и корень проверяются против активного модуля присваиваемостью (`implementsApi<typeof vscode.X>()(ns)` из `api/common/apiSurface.ts`) — недостающий член или сигнатура не той формы ловится компилятором, а лишние члены рантайма разрешены. Поднял поверхность или поменял статус стаба — **в том же PR обнови публичную матрицу** [docs/public/API-COVERAGE.md](../public/API-COVERAGE.md): она ведётся руками и держится актуальной именно этой дисциплиной; генератор для неё не заводим (решение человека: дисциплина, а не автоматика).

**Bounded member-level uncommenting.** Для «тяжёлого по closure» блока (namespace/интерфейс/класс, чьё полное upstream-тело тянет непрактичное дерево зависимостей) можно раскомментировать **подмножество членов**, оставив прочие в дормантной части. Каждая раскомментированная строка обязана быть **байт-в-байт** равна upstream. Так сделаны, например, `window`/`workspace`/`languages` (только реализованные функции), `TextEditor` (`document`/`selection`/`selections`/`options`/`edit`), `ExtensionContext` (`subscriptions`, каталоги хранения, `secrets`), `FileStat`/`CompletionItem` (подмножество полей). `TextDocument` поднят целиком, и класс документа субпроцесса `implements vscode.TextDocument` — недостающий член ловит компилятор.

**Инструмент.** `scripts/import-vscode-dts.mjs`:
- (без флагов) — регенерировать дормант из запинненного тега + обновить провенанс в шапке (активный модуль не трогает);
- `--check` — сверить, что дормант байт-в-байт равен upstream тега (drift guard, нужна сеть);
- `--verify-active` — offline-проверка инварианта: каждая кодовая строка активного модуля дословно присутствует в дормантной копии. Прогоняй после ручного раскомментирования.

**Раскомментирование скриптом.** Если блоков много и правишь файл одноразовым скриптом: все вырезки из дормантной копии делай из **исходного** текста до первой подстановки — офсеты плывут после каждой вставки в активную часть, и поиск «следующего маркера» попадает в соседний блок (так вместо `FileSystem` дважды вырезался `FileSystemProvider`). Якорь в активной части ищи с ведущим `\n`: строка `\texport enum X {` — подстрока закомментированной `// \texport enum X {`, и проверка «нашлось ровно одно» проходит, вставляя блок в середину дормантной копии. Итог сверяй `--verify-active`, а скрипт с несколькими заменами — по каждой замене.

**Какие API нужны стоковому расширению** — дешевле снять с его бандла, чем гонять UI: `grep -oE "\b(window|workspace|languages|commands|env)\.[A-Za-z]+" out/main.js | sort | uniq -c` (из магазина — `meta/<id>.json` → `artifact.url` → `unzip`). Быстрый спайк без редактора — `createExtensionTestHarness({ extensions: [registration], activateEvents: [], logger })`, где `registration` — настоящий vsix (`fetchStockVsix` → `installVsix` → `registrationFromInstalled`, по образцу `src/TestUtils/ruffFixture.ts`), со своими стоками (`outputSink`, `statusBarItemSink`, `quickInputSink`, …) и ручным `host.activateByEvent(...)`: ошибку активации без `logger` не видно.

**Семантические отклонения Diode** (тип совпадает с upstream, отличается только смысл/JSDoc-намерение):
| Символ | Отклонение |
| --- | --- |
| `version` | Возвращает версию **Diode**, а не VS Code (upstream JSDoc говорит «editor»). |
| `Event<T>` | Слушатель `(e) => any` (upstream); хост оборачивает подписки через `EventEmitterImpl` в `Vscode/VscodeTypes.ts`. |
| `TextEditorOptions.indentSize` | Хост алиасит его к `tabSize` (Diode пока не различает); editorconfig шлёт `indent_size` так. |
| Namespaces / value-типы | Рантайм может опережать типы (лишние члены разрешены); отставание ловит компилятор — поверхность собирается в `api/common/*Namespace.ts` и проверяется `implementsApi<typeof vscode.*>()`. Где отставание осознанное (новый функционал не сделан), стоит точечный каст с комментарием-причиной. |

**Кодировки (#106).** `workspace.openTextDocument(…, { encoding })` реально декодирует не-utf8 файлы осью encoding ядра (`src/vs/editor/common/model/encoding.ts`): explicit-кодировка побеждает BOM-сниф, неизвестный id молча откатывается к дефолту (контракт vscode.d.ts); эфемерный документ детектит и `encoding`, и `eol`. `ExtHostTextDocument.encoding`/`.eol` — живые: обновляются метой `editor.activeEditorChanged` и снапшотом will-save (`IWireWillSaveParams.encoding`). Дормантные `workspace.decode`/`encode` не раскомментированы (не понадобились).

**Зависимости:** Extensions → Editor (через `ILanguageService`, `TextMateGrammarLoader`, `TokenizationRegistry`), Common. Подмодуль **`Extensions/Host` дополнительно → Workbench** (адаптеры над `EditorService`; мост файловых декораций типизирован портом `IFileDecorationsTarget`, в DI его реализует `ExplorerService`) и **→ Theme** (`ThemeColorResolverAdapter` над `ThemeService`) — единственное место, где Extensions поднимается выше Editor.

**Терминалы расширений (`window.createTerminal`, `terminals`, `activeTerminal`, события).** Устроено как `ExtHostTerminalService` ↔ `MainThreadTerminalService` эталона. Состояние `vscode.Terminal` живёт в субпроцессе (`api/common/terminalNamespace.ts`), инстансом владеет хост: `TerminalCustomer` (`services/extensions/node/customers/`) переводит нотификации `terminal.create/show/hide/sendText/dispose` в сток `IExtensionTerminalSink`, а его реализация `ExtensionTerminalAdapter` (`contrib/terminal/browser/` — в фиче, потому что ядро workbench фич не знает) водит `TerminalService`. Обратно хост пересказывает жизнь ВСЕХ инстансов встроенного терминала, включая шеллы человека: `terminal.opened` (с pid и `launch` — из него `creationOptions` чужого терминала), `terminal.closed` (код и причина: выход шелла — `process`, Kill — `user`, `dispose()` — `extension`), `terminal.activeChanged`. Адресация двойная: хостовый `id` минтит хост, свой терминал субпроцесс до прихода `opened` адресует собственной меткой `extHostId` (`extHostTerminalId` эталона) — поэтому `createTerminal` + `sendText` в одном тике доходят до шелла. Снимок всех инстансов уходит после `host.ready` и до первой активации (`pushInitialState`); на смерти субпроцесса метки забываются, а шеллы расширения живут дальше — новый субпроцесс видит их как чужие (у эталона так же). `hideFromUser` — фоновый инстанс `TerminalService` (`_backgroundedTerminalInstances` эталона): процесс жив, во вкладках он появляется по `show()`. Pty расширения (`ExtensionTerminalOptions`, `ExtHostPseudoterminal` эталона): на хосте — инстанс с сессией-эмулятором без процесса (`ExtensionPtySession` поверх общего с шеллом `XtermSurface`, фабрика `ExtensionPtySessionFactoryDIToken`, в сервис — готовой сессией в опции `session`, как `customPtyImplementation` эталона). Хост сразу после создания шлёт `terminal.pty.start` — субпроцесс подключает `onDidWrite`/`onDidClose` и зовёт `pty.open`; вывод склеивается окном 5 мс и едет `terminal.pty.data`, выход pty — `terminal.pty.exit`. Набор человека и `sendText` расширения идут через хост в эмулятор и обратно `terminal.pty.input` → `handleInput` — поэтому `sendText` сразу после `createTerminal` приходит уже после `open` (как в эталоне); размер виджета — `terminal.pty.resize` → `setDimensions`. Закрытие инстанса по любой причине зовёт `pty.close()`; на смерти субпроцесса его pty-терминалы закрываются.

**Задачи расширений (`vscode.tasks`).** Устроено как `ExtHostTask` ↔ `MainThreadTask` эталона; задачами владеет сервис ядра (`contrib/tasks`, см. [Workbench.md](Workbench.md#задачи-tasks)). Субпроцесс (`api/common/tasksNamespace.ts`) держит провайдеры, свои исполнения и колбэки `CustomExecution`; хост — `TasksCustomer` (`services/extensions/node/customers/`) над стоком `IExtensionTaskSink`, реализация — мост `ExtensionTaskAdapter` (`contrib/tasks/browser/`, перевод описаний — `contrib/tasks/common/taskDto.ts`). Провод `tasks.*` (типы — `api/common/taskWireTypes.ts`, разбор хостом — `hostWireParsers.ts`): субпроцесс → хост `tasks.registerProvider`/`unregisterProvider` (нотификации с handle, типом и id расширения-владельца), `tasks.fetch` и `tasks.execute` (запросы), `tasks.terminate`; хост → субпроцесс `tasks.provideTasks` (запрос по handle) и жизнь ВСЕХ задач ядра — `tasks.didStart` (исполнение, id терминала, определение с подставленными переменными), `tasks.didStartProcess`, `tasks.didEndProcess`, `tasks.didEnd`, поэтому задача, запущенная из палитры, приходит расширению событиями с `name`/`source` задачи провайдера (так bazel-java ищет свою бегущую задачу в `taskExecutions`). Идентичность — эталонная: своё исполнение `executeTask` заводит по id задачи ДО запроса, и событие, обогнавшее ответ, находит его — расширение получает свой объект `Task`; задача из ядра (`fetchTasks`) исполняется по id (`handleId`, `_id` эталона), сеттер `Task` его сбрасывает — тогда уходит описание целиком. **Отступления:** RPC в стиле Diode (customer, методы `tasks.*`) — по смыслу 1:1 с `$`-методами; нет `$createTaskId` — id задачи провайдера `${расширение}.${_key}` субпроцесс считает сам той же формулой (`api/common/taskIdentity.ts`, общая для обеих сторон; схемы `contributes.taskDefinitions` — из каталога расширений); нет `$registerSupportedExecutions`/`$registerTaskSystem`/`$jsonTasksSupported`/`$findExecutable` (исполнение одно — терминал, платформа — своя); `$customExecutionComplete` и отдельного сообщения старта `CustomExecution` нет — его колбэк зовётся на `tasks.didStart`, как у эталона в `$onDidStartTask`. **CustomExecution:** ядро заводит терминал задачи на pty расширения через тот же мост, что `window.createTerminal({ pty })` (`IExtensionPtyTerminals`, реализует `ExtensionTerminalAdapter`), субпроцесс на старте зовёт колбэк и подключает pty к терминалу по id инстанса (`ITerminalNamespace.attachPty`, `attachPtyToTerminal` эталона): размер — последний из `terminal.pty.start`/`resize`, которые хост прислал раньше подключения; при повторном запуске прежний pty отцепляется без `close()`. Нотификации задач субпроцесс обрабатывает строго по очереди — старт с колбэком не обгоняется событиями процесса. Overlay владельца оборачивает `tasks.registerTaskProvider`/`executeTask` и устаревший `workspace.registerTaskProvider`. `contributes.taskDefinitions` дают неявное `onTaskType:<type>`; перед Run Task сервис поднимает `onCommand:workbench.action.tasks.runTask` и `onTaskType:` (таймаут 5 с, как у эталона).

**Мост декораций (`vscode.window.createTextEditorDecorationType` / `registerFileDecorationProvider`).** Value-типы (`ThemeColor`/`FileDecoration`/`OverviewRulerLane`/`DecorationRangeBehavior`) живут в `Vscode/VscodeTypes.ts`; `WindowNamespace` держит тип декорации локально (монотонный числовой key) и шлёт хосту RPC-нотификации, сериализуя `ThemeColor` как `{ $themeColor: id }` (см. `WireTypes.ts`). Хост держит реестр `key → { overviewRulerColorId?, isWholeLine }` (gutter-тип = есть `overviewRulerColor`), резолвит `ThemeColor` через `IThemeColorResolver` и проталкивает: gutter change-bar'ы — в `EditorComponent.setGutterChangeDecorations` (по совпадению пути, образец — `DiagnosticsService`), файловые декорации — в `ExplorerService.setFileDecorations`. На `theme.onDidChange` все держимые декорации пере-резолвятся и пере-push'атся. **Ядро про источник декораций (git/SCM) не знает** — адаптеры отдают уже резолвнутые packed-RGB цвета.
