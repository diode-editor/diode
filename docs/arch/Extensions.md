# Extensions/

Часть архитектуры Diode — обзорная карта в [../ARCHITECTURE.md](../ARCHITECTURE.md).

Загрузка VS Code-совместимых расширений. Сейчас поддержаны `contributes.languages`, `contributes.grammars` и `contributes.themes` для builtin (`extensions/` — 48 языковых паков из microsoft/vscode, импорт verbatim скриптом с пином тега) и user-расширений (`<userData>/extensions/<publisher>.<name>-<version>/`). Остальные contribution points — отдельные фазы (см. [../TODO/Extensions.md](../TODO/Extensions.md)).

Контракты/швы:
- **`IExtension`** — `{ id, manifest, location, isBuiltin }`. `ExtensionScanner` парсит `package.json` через `IAssetAccess`; `mergeExtensions` разруливает конфликты id (builtin побеждает user).
- **NLS манифеста (`extensionNls.ts`)** — любая строка `package.json` расширения может быть ключом `"%java.clean%"`, а текст лежит в `package.nls[.<locale>].json`. Резолв делает `ExtensionScanner` сразу за парсингом — **одним проходом по всему дереву манифеста**, как `localizeManifest` эталона, а не точечно у команд: те же ключи сидят в `displayName`/`description`, в `label` тем, в заголовках и описаниях настроек. Поэтому у потребителей (`ExtensionThemeContributor`, `collectCommandMeta` в `extensionRegistration.ts`, `packageJSON` в `vscode.extensions`) манифест уже локализованный, и своего резолва им не нужно. Бандл читается тем же `IAssetAccess`, что и манифест, — у builtin'а файла на диске нет, он внутри SEA-бандла. Выбор файла — `nlsFileCandidates(locale)`: `package.nls.<locale>.json` → базовый язык (`pt-br` → `pt`) → `package.nls.json`; локаль одна на редактор — `UI_LOCALE` (`platform/environment/common/uiLocale.ts`), оттуда же берётся `vscode.env.language`. Краевые случаи эталонные и **не роняют загрузку**: нет ключа — строка остаётся ключом плюс одна строка в лог на расширение (молча подставленная пустота не отлаживается), нет/битый бандл — расширение грузится с нерезолвленными строками, нестроковые значения не трогаются. `ExtensionInstaller.listInstalledExtensions` локализует себе `displayName`/`description` сам: он работает с физическими каталогами, мимо `IAssetAccess`.
- **`LanguageRegistry implements ILanguageService`** — собирает `contributes.languages`, резолвит language по пути файла. Неочевидное правило разрешения: приоритет `filenames` → `filenamePatterns` (мини-glob) → `extensions`; при конфликте одного `.ext` побеждает **зарегистрированный позже** (user поверх builtin, как в VS Code). Seed'ит core-язык `plaintext` как fallback.
- **`ExtensionThemeContributor`** — регистрирует цветовые темы из `contributes.themes` в `ThemeRegistry`. В отличие от грамматик — **eager**: `await apply()` в `main.ts` идёт после сканирования и ДО выбора активной темы и первого кадра (файлы тем — килобайты, а пикеру нужен синхронный `resolve`, и тема из `workbench.colorTheme` обязана быть в первом кадре). Ключ — `label` манифеста, `uiTheme` → тип, JSONC и `include` — см. [Theme.md](Theme.md). Битая тема (нет файла, битый JSON, цикл `include`) — ошибка в лог с id расширения и label, пропуск; расширение и старт не падают. `dispose()` снимает регистрации.
- **`ExtensionTokenizationContributor`** — регистрирует грамматики из всех `contributes.grammars` в `TokenizationRegistry`. `apply()` синхронный и без I/O: кладёт **ленивые фабрики** (`registerLazy`), а `.tmLanguage.json` парсится при первом `TokenizationRegistry.load(languageId)` — его дёргает `EditorComponent.ensureTokenizerForLanguage`, когда язык реально понадобился документу (наш аналог `onLanguage`; к activation-events extension host'а отношения не имеет — языковые паки декларативные, без `main`). Пока грамматика едет, документ работает на `PlainTextTokenizer`, а подъехавший support пересаживается через `onDidChange`. Мотив: 77 builtin-грамматик — 6.6 MB JSON, ~420 мс на полную загрузку; раньше всё это лежало на пути к первому кадру с содержимым файла.

Две вещи прикрывают ленивость, чтобы пользователь не видел неподсвеченный текст:
- **Стартовые файлы** — `main.ts` через `preloadGrammarsForFiles` ждёт грамматики именно тех файлов, что сейчас откроются (обычно один язык, ~2 мс), **до** `openFile`. Ждать после поздно: `await` отдаёт event loop, и отложенный рендер успевает нарисовать кадр на fallback'е. Пути берутся из CLI либо из `WorkbenchComponent.getOpenEditorsToRestore()` — тот же список, что откроет `restoreOpenEditors()`, чтобы знание о восстанавливаемой сессии не расползалось по бутстрапу.
- **Остальные грамматики** — фоновый `preloadAll()` (`setImmediate` после первого кадра), чтобы переключение вкладки на другой язык не ждало парсинга.
- **`ExtensionInstaller`** — установка/удаление/список из `.vsix` (CLI `--install-extension` и т.п., до подъёма TUI): распаковка с защитой от zip-slip + атомарный `rename` в каталог, который ждёт `ExtensionScanner`.
- **Установка по id из реестра** (`platform/extensionManagement/`) — `installFromRegistry` поверх того же `installVsix`: мета → совместимая версия (`engines` ↔ `DIODE_VERSION`/`VSCODE_SHIM_VERSION`; платформенные записи — по `targetPlatform` ↔ `currentTargetPlatform()`, universal — фолбэк) → артефакт → `sha256` → установка. Источник за швом `IExtensionRegistrySource`: каталог (`FileExtensionRegistrySource`) или сеть (`HttpExtensionRegistrySource`); выбирает `createRegistrySource` по значению `--registry`, без флага — публичный реестр. Формат и политика наполнения — [docs/TODO/Marketplace.md](../TODO/Marketplace.md).

## Extensions/Host/ — extension host (real subprocess)
Изоляция кода расширений от ядра. Host форкает **один subprocess** (тот же бинарь / `main.ts` с env `DIODE_EXTENSION_HOST=1`) и общается с ним через **RPC поверх Node IPC**. Швы:
- **`IMessageChannel`** — транспортно-агностичный двунаправленный канал. Реализации: `IpcMessageChannel` (Node IPC) и `createInProcessChannelPair()` (unit-тесты).
- **`RpcEndpoint`** — request/response/notification поверх канала, **симметричный** (запросы шлют обе стороны).
- **Загрузка точки входа:** CJS или ESM, решает `isEsmEntry` правилом эталона (`_isESM` в `abstractExtHostExtensionService`): `.mjs` — всегда модуль, `.cjs` — всегда CJS, иначе — `"type"` из `package.json` расширения (хост отдаёт его в `host.activateExtension` как `moduleType`). CJS грузится `createRequire(mainPath)`, ESM — `importModule` (`base/node/importModule.ts`): `import()` из синтетического CJS-модуля, скомпилированного в памяти, потому что прямой `import()` из вшитого SEA-main перехватывается embedder-хуком и умеет только builtin'ы. Тот же приём и у `runAsNode`. ESM-расширения не экзотика: `esbenp.prettier-vscode` с 12.x — `"type": "module"`.
- **vscode-стаб:** subprocess патчит `Module._cache["vscode"]` + `Module._resolveFilename` (`installVscodeStub`), поэтому `require("vscode")` расширения отдаёт нашу поверхность. Для ESM тот же `installVscodeStub` ставит `module.registerHooks` (`resolve` + `load`): CJS-кэш ESM-loader'у не виден, и `import … from "vscode"` без хука падает на `ERR_MODULE_NOT_FOUND`. Хук отдаёт сгенерированный модуль с именованным export'ом на каждый член namespace'а (`buildVscodeEsmShim`), значения он читает из `globalThis` — замыканием их в исходник не передать; эталон держит эти два механизма рядом по той же причине. Сама поверхность собрана в `Extensions/Host/Vscode/` — тонкий ассемблер `buildVscodeNamespace(rpc)` над общим контекстом (`window`/`workspace`/`languages`/`commands` + value-типы `Position`/`Range`/`Uri`/enum'ы). Документы держат **стабильную идентичность** (`DocumentRegistry`: один объект на `fileName`, обновления мутируют его на месте — нужно для `activeTextEditor.document === doc`).
- **Языковые провайдеры — реестр ядра (G2, как upstream `MainThreadLanguageFeatures`/`ExtHostLanguageFeatures`):** селекторы и скоринг живут в ядре — `editor/common/languageSelector.ts` (`score`: 10 точное совпадение, 5 — `*`, у массива максимум; `RelativePattern`, `exclusive`), `editor/common/languageFeatureRegistry.ts` (`register/has/ordered/onDidChange`: по убыванию score, при равном — более поздняя регистрация первой, `onDidChange` на КАЖДУЮ регистрацию и снятие), `editor/common/services/languageFeatures.ts` (`ILanguageFeaturesService` — реестр на фичу: hover, definition, references, signatureHelp, completion, documentFormatting/documentRangeFormatting, codeAction, foldingRange, inlineCompletions; биндинг в `tokenizationModule`). Субпроцесс на каждый `register*Provider` выдаёт handle и шлёт `languages.register {handle, kind, selector, …metadata}` (селектор — DTO `toWireLanguageFilters`: строка → `{language}`, `RelativePattern` → `{base: fsPath, pattern}`; метаданные — триггер-символы completion/signatureHelp, `providedCodeActionKinds`), dispose — `languages.unregister {handle}`. Хост держит регистрации (`getLanguageProviders`/`onLanguageProvidersChanged`) и снимает их все на смерти/остановке субпроцесса; `api/browser/languageFeaturesAdapter.ts` (порт `IExtensionLanguageFeaturesBridge`) регистрирует в реестрах прокси `{provideX: (req) => host.provideX(handle, req)}` — подключён один раз в `extensionHostModule.ts` и `ExtensionTestHarness`. Запрос `languages.provideX` несёт handle — субпроцесс зовёт ровно этого провайдера. Агрегация — у потребителя, по upstream: hover/definition/references — параллельно и склейка в порядке `ordered` (`contrib/hover/getHover.ts`, `gotoDefinition/goToSymbol.ts`, `references/getReferences.ts`), signatureHelp — по очереди до первого ответа (`parameterHints/provideSignatureHelp.ts`), formatting — документный форматтер по score, за ним range-провайдер на полный диапазон (`editor/contrib/format/format.ts`; `null` = «нет форматтера» решается по реестру, без RPC), code actions — с отсевом по `providedCodeActionKinds` (`editor/contrib/codeAction/codeAction.ts`). Документ без подошедших провайдеров RPC не будит вовсе. **Пачка:** пока запросы несут полный текст документа (до document sync дельтами — G3), фичи «на каждый символ» (completion, folding, inline) зовут прокси одним объектом запроса, и хост склеивает их в один RPC `{handles, …}` (`services/extensions/common/providerRequestBatcher.ts`), ответ — массив, выровненный по handles. Новая языковая фича = вид в `WIRE_LANGUAGE_FEATURE_KINDS` + реестр в `ILanguageFeaturesService` + фабрика прокси в адаптере + `provideX(handle, …)` хоста + обработчик по handle в субпроцессе; полей-швов на `EditorService` и флагов подписки больше нет.
- **Save-participant / completion seams:** `TextFileModel.save()` асинхронный — участники сохранения `await`-ятся до записи (правки клампятся к границам, уходят одним undoable-батчем). Пайплайн — `TextFileSaveParticipant` (`services/textfile/common/textFileSaveParticipant.ts`, аналог upstream): один экземпляр на все модели держит `EditorService`, модель зовёт его перед записью и в `save`, и в `saveAs`; состав берётся у провайдера в момент save (живые настройки) — `EditorService.collectSaveParticipants` собирает пайплайн в порядке VS Code: участник `editor.codeActionsOnSave` → участник `editor.formatOnSave` (оба — `services/editor/browser/onSaveParticipants.ts` поверх реестров `ILanguageFeaturesService`; участник входит в пайплайн, только если для ЭТОГО документа есть подходящий провайдер) → will-save расширений (`EditorService.saveParticipant` ← host `onWillSaveTextDocument`). Каждый участник получает свежий снапшот (предыдущий мог править буфер), ограничен таймаутом 5000 мс (зависший — пропуск, сохраняем как есть), сбойный пропускается. С дефолтами (настройки выключены) пайплайн = один will-save участник — поведение прежнее; без host'а список пуст. Сама запись — через `IFileService.writeFile` (атомарно, с гардом по etag), поэтому `save()` асинхронный и без участников. Инъекция seam'ов — в `Workbench/Modules/ExtensionHostModule.ts`; **ядро (`TextFileModel`/`EditorService`) про extension-слой не знает.**
- **Folding-провайдер seam (#194):** `languages.registerFoldingRangeProvider` — путь host↔subprocess по образцу completion (`languages.provideFoldingRanges` RPC). Реестр — `ILanguageFeaturesService.foldingRangeProvider` (тип `editor/common/languages/iFoldingSource.ts`), `EditorService` отдаёт его каждому `EditorComponent`; тот при пересчёте фолдов запрашивает области подошедших провайдеров (пачкой) и **мержит их поверх indentation-фолдов** (union: provider ∪ indentation, provider выигрывает по общей `startLine`), перенося `isCollapsed` по `startLine`. Пересчёт идёт и на `onDidChange` реестра — на каждую регистрацию/снятие, так что провайдер, появившийся после открытия файла (в том числе второй), подхватывается сразу. Стоковый `maptz.regionfolder` заводится этим путём (тест `extensionHost.maptzRegionfolder.test.ts`).
- **Editor-write seam (#194):** `TextEditor.edit(cb)` (с `TextEditorEdit` insert/replace/delete), `editor.selection(s)` геттер/сеттер, `window.visibleTextEditors`, value-тип `Selection`. Правки/выделения субпроцесса едут хосту (`editor.applyEdit` / `editor.setSelection`) и применяются к активному редактору порта `IEditorOptionsService` (правки — одним undoable-батчем через `applyExternalEdits`, с клампом к границам; guard по совпадению uri).
- **Workspace-edit seam (#196):** `workspace.applyEdit(WorkspaceEdit)` — обобщение editor-write на несколько ресурсов: субпроцесс сериализует текстовые правки per-uri (`IWireApplyWorkspaceEditParams`) и шлёт RPC `workspace.applyEdit`; хост применяет через `IEditorOptionsService.applyWorkspaceEdit` (документ ищется в ЛЮБОЙ вкладке, каждый — своим undoable-батчем; all-or-nothing по валидации: закрытый или read-only ресурс — честный `false` без применения чего-либо). Файловые операции `WorkspaceEdit` не поддержаны — субпроцесс отвечает `false` сам, без RPC; сниппет-правки (`SnippetTextEdit` — класс-ловушка конвертера клиента) применяются текстом со стрипом плейсхолдеров. Люфты — docs/TODO/LSP.md.
- **Document sync seam (LSP):** наивный full-text push host → subprocess — `editor.didOpen`/`editor.didChange` (`IWireDocumentSyncSnapshot`: uri, languageId, `version` = `versionId` модели, text). Продюсер — `bindDocumentSync` (`api/browser/documentSyncAdapter.ts`, подписки в module/харнессе); субпроцесс кладёт текст в `DocumentRegistry` и фаерит `workspace.onDidOpen/onDidChangeTextDocument` (change — одна full-range правка, валидно для Full и Incremental sync LSP-сервера). Гейт по подписке (`workspace.updateSubscriptions.documentSync`, переход 0→1 доталкивает активный документ), didChange коалесируется в тик, лимит 8 МБ; активный документ пушится на `host.ready` ДО активации (стоковый `vscode-languageclient` читает `workspace.textDocuments` на `start()`). Люфты (нет didClose, только активный редактор) — docs/TODO/LSP.md.
- **Definition-провайдер seam (LSP):** `languages.registerDefinitionProvider` — калька с completion (`languages.provideDefinition` RPC, таймаут 5000 мс — холодный language server). Реестр — `ILanguageFeaturesService.definitionProvider` (тип `editor/common/languages/iDefinitionSource.ts`); UI — contrib `gotoDefinition` (`DefinitionService` + F12 `editor.action.revealDefinition`), кросс-файловая навигация паттерном Problems reveal (`openUri` + `goToPosition`). Результат провайдера `Location | Location[] | LocationLink[]` нормализуется субпроцессом (у LocationLink прицел — `targetSelectionRange ?? targetRange`).
- **Провайдер содержимого недисковых ресурсов:** `workspace.registerTextDocumentContentProvider` — дверь, которой в редактор попадают исходники, которых нет на диске (`jdt:`/`class:` у стокового `redhat.java`: класс из jar, исходник JDK, декомпиляция). Проводка — калька с провайдеров ФС: реестр субпроцесса (`SubprocessTextDocumentContentProviders`, чистая логика без RPC) объявляет хосту свои схемы нотификацией `workspace.textDocumentContentProvidersChanged`, содержимое едет обратным запросом `workspace.provideTextDocumentContent` (текстом, а не base64 — провайдер отдаёт строку, не байты), `onDidChange` провайдера — нотификацией `workspace.textDocumentContentChanged`. Core-seam — `EditorService.virtualDocumentSource` (тип `workbench/services/editor/common/iVirtualDocumentSource.ts`), инъекция в `ExtensionHostModule`/`ExtensionTestHarness`; вкладка получается синтетической моделью (`TextFileModel.openSynthetic`) с `readOnly` — контракт `TextDocumentContentProvider` про read-only документы прямо и говорит. **Реестр отдельный от `IFileSystemProviderRegistry`**, как в эталоне: одна схема может иметь и провайдера ФС, и провайдера содержимого. `workspace.openTextDocument` по такой схеме спрашивает провайдера локально, без RPC, — он живёт в том же субпроцессе. Неудача открытия (схемы никто не обслуживает, провайдер отказался или сломался) — **не исключение**: `EditorService.openUri` не отклоняется никогда, причина уезжает в лог и хук `onOpenFailed`, а человек видит её тостом (`OpenFailureNotificationContribution`). Это не гигиена: раньше не-`file:` ресурс доезжал до `TextFileModel.openFile`, тот бросал, промис команды никто не ждал — и Node закрывал редактор со всеми буферами.
- **Hover-провайдер seam (LSP):** `languages.registerHoverProvider` — калька с definition (`languages.provideHover` RPC, таймаут 5000 мс). Ядро спрашивает все подошедшие провайдеры и склеивает непустые ответы в порядке реестра (`WireHover {contents, range?}`, contents — блоки сырого markdown; `MarkedString {language, value}` сериализуется fenced-блоком). Реестр — `ILanguageFeaturesService.hoverProvider` (тип `editor/common/languages/iHoverSource.ts`); UI — contrib `hover` (пара `HoverService`/`HoverComponent` по образцу suggest: overlay-сессия у каретки без захвата фокуса, `stripMarkdown` в плоский текст, закрытие по Escape/правке/каретке/фокусу; ключ `editorHoverVisible`).
- **References-провайдер seam (LSP):** `languages.registerReferenceProvider` — та же калька (`languages.provideReferences` RPC, таймаут 5000 мс; в параметрах LSP-контекст `includeDeclaration`). Ядро спрашивает все подошедшие провайдеры и склеивает ответы в порядке реестра (`WireReference {uri, range}`, сериализатор общий с definition). Реестр — `ILanguageFeaturesService.referenceProvider` (тип `editor/common/languages/iReferenceSource.ts`); UI — contrib `references` (вьюлет сайдбара REFERENCES: `ReferencesService` спрашивает провайдеров и добирает текст строк, `ReferencesComponent` рисует список; ключи `referencesViewletVisible` / `hasReferenceResult`). Особенность против definition/hover: ответ несёт только координаты, поэтому строку кода панель читает сама — из открытой модели, иначе через `IFileSystemProviderRegistry`.
- **Signature-help seam (LSP):** `languages.registerSignatureHelpProvider` — та же калька (`languages.provideSignatureHelp` RPC, таймаут 5000 мс), но с двумя отличиями. Первое: провайдеров обходим по очереди и возвращаем ПЕРВЫЙ непустой ответ (vscode API предписывает именно это — склеивать две разные `activeParameter` нечем). Второе: в параметрах едет LSP-контекст (`triggerKind`, `triggerCharacter`, `isRetrigger`, эхо показанной подсказки `activeSignatureHelp` — по нему сервер удерживает выбранную пользователем перегрузку). Триггер- и ретриггер-символы объявляет сервер: они едут метаданными регистрации провайдера, и ядро берёт их только у подошедших документу. Реестр — `ILanguageFeaturesService.signatureHelpProvider` (тип `editor/common/languages/iSignatureHelpSource.ts`); UI — contrib `parameterHints` (`ParameterHintsService` ловит набор триггер-символа и перезапрашивает подсказку на каждую правку, `ParameterHintsComponent` держит overlay-сессию НАД строкой каретки; ключи `parameterHintsVisible` / `parameterHintsMultipleSignatures`). Стаб `vscodeTypes` пришлось дополнить value-классами `SignatureHelp`/`SignatureInformation`/`ParameterInformation` и enum'ом `SignatureHelpTriggerKind` — их конструирует и читает конвертер стокового клиента.

Ключ `inlineSuggestionRequestPending` (нашего изобретения — у upstream отмена едет из observable-графа) продлевает биндинг Escape на окно ожидания ответа, когда призрака на экране ещё нет. Настройки `editor.inlineSuggest.{enabled,delay,requestTimeout}` читаются на каждом обращении (правка settings.json применяется без перезапуска); `enabled` гейтит ТОЛЬКО автозапрос — команда-триггер (**Alt+\\**) работает и при `false`. `requestTimeout` едет полем `timeoutMs` в САМОМ запросе, а не фиксируется при создании хоста, как остальные таймауты (`req.timeoutMs ?? options.inlineCompletionTimeoutMs`) — осознанная асимметрия ради live-применения. - **Транспорт отмены RPC:** `RpcEndpoint.request(method, params, token?)` — сработавший токен вызывающего уходит второй стороне зарезервированной нотификацией `$/cancelRequest {id}` (аналог LSP), а принимающая сторона гасит токен, который выдаёт обработчику вторым аргументом (`IRequestHandler = (params, token) => unknown`). Транспорт общий для всех методов; подключение провайдера к отмене — это проводка токена, а не новый протокол. Тихие края: отмена, пришедшая ПОСЛЕ ответа, не шлётся вовсе (подписка на токен снимается вместе с ответом), а отмена, обогнавшая свой запрос на переупорядоченном транспорте, запоминается (последние 64 id) и выдаётся обработчику уже отменённым токеном; `dispose` endpoint'а отменяет всё, что ещё считается. Сегодня токеном пользуются ТОЛЬКО inline completions — остальные провайдеры получают заглушку `neverCancelledToken`.

- **Локальный диск без RPC (`workspace.fs`, `workspace.findFiles`):** обе поверхности (и `openTextDocument` по промаху реестра) работают **в субпроцессе через `node:fs`**: привязка к диску — `api/node/extHostDisk.ts` (`IExtHostDisk`, как `extHostDiskFileSystemProvider` у эталона), её отдаёт `buildVscodeNamespace` точка входа субпроцесса, а в `api/common` остаются роутер, обход и сборка документов — целевой файл живёт на той же машине и не является открытым буфером ядра, поэтому запроса к хосту не нужно (в отличие от will-save, который ходит за текстом активного документа). Это ещё и правильное место по нагрузке: рекурсивный обход дерева однажды уже голодал главный цикл (см. `files.watcherExclude` и вынос watcher'а в отдельный процесс), а стоковый `redhat.java` зовёт `findFiles` около десяти раз на одной активации. `workspace.fs` (`fileSystemNamespace.ts`) — роутер по схеме: `file` идёт на диск, прочие схемы — провайдеру расширения (`registerFileSystemProvider`), схема без провайдера получает `FileSystemError.Unavailable`; гейт схемы не декоративный — `fsPath` у `untitled:` отдаёт относительный путь, и `writeFile` без него создавал бы файл в `$CWD`. `findFiles` (`findFiles.ts`) — обход в ШИРИНУ с отделённым интерфейсом `IFindFilesScanner` (бюджет каталогов, исключения и матчинг тестируются на карте в памяти); глубина обхода выводится из шаблона (без `**` число сегментов фиксировано), бюджет — 5000 каталогов на запрос, отмена — настоящий `CancellationToken`. Три значения `exclude` из контракта различаются: `undefined` — настройка `files.exclude` (и только она, как в контракте: `search.exclude` сюда не входит), `null` — ничего, шаблон — ВМЕСТО настройки.

- **Событие выделения (`window.onDidChangeTextEditorSelection`):** производит его САМ субпроцесс из нотификации `editor.selectionChanged` (нового сообщения в проводе нет — добавилось поле `kind`), уже после обновления своих кэшей: слушатель читает `event.textEditor.selection` и обязан увидеть новое. Эхо-гард остаётся на хосте, поэтому выделение, которое расширение поставило само (`TextEditor.selection =`), события не даёт — осознанное отличие от upstream в пользу «расширение не будит само себя». **`kind` (`TextEditorSelectionChangeKind`) едет от ЖЕСТА**, а не угадывается: источник объявляется областью `withCursorChangeSource` (`editor/common/core/cursorChangeSource.ts`) вокруг обработчика — ввод и мышь в `EditorElement`, диспетчер кейбиндов (`keyboard`: стрелки у нас исполняются командами, но для расширения это Keyboard, как в VS Code), обработчик `commands.executeCommand` от расширения (`command`). Снимается источник СИНХРОННО в `EditorOptionsServiceAdapter` (в отложенном флаше коалесинга область жеста уже закрыта), вложенная область не перебивает внешнюю. Неразмеченный жест (undo/redo, find, фолдинг, программная правка) едет без поля — `kind: undefined` upstream объявляет явно. Плоского «протащить причину через пять сигнатур» не делаем: у потребителя один, и ambient-область дешевле.
- **Активная тема (`window.activeColorTheme` + `onDidChangeActiveColorTheme`):** notify `window.themeChanged {kind}` (host → subprocess) через тот же порт `IThemeColorResolver`, что резолвит `ThemeColor` — второго порта к теме не заводим, событие смены у обоих потребителей одно. `ThemeColorResolverAdapter.kind()` переводит `WorkbenchTheme.type` в `vscode.ColorThemeKind`. Сообщение уходит **семенем на handshake, ДО первой активации** (расширение читает тему уже в `activate()`, чтобы выбрать иконки/цвета) и на каждую настоящую смену темы; субпроцесс стреляет событием на каждое пришедшее сообщение, включая переход между двумя тёмными темами — upstream формулирует событие как «changed **or has changes**». До первого сообщения тема — `Dark` (дефолт VS Code), а не `undefined`: `activeColorTheme.kind` читают без проверок.
- **Изоляция сбоев субпроцесса:** `runExtensionHostSubprocess` ставит `process.on("unhandledRejection")` — расширение, не поймавшее свой промис (исторический пример: стоковый maptz после `wrapWithRegion` fire-and-forget звал `editor.action.formatDocument`, до #196 отсутствовавшую), логируется в stderr и **не уносит с собой host** со всеми остальными расширениями. Причина печатается со **стеком** (`describeRejection`): `String(err)` даёт только «Error: message», по которой не найти ни виноватое расширение, ни строку.
- **Каталоги хранения (`ExtensionContext.globalStorageUri` / `storageUri` / `logUri` + депрекейтнутые строковые близнецы):** корни даёт ХОСТ — раскладку user-data знает приложение, и субпроцессу её не выдумывать. Опция `ExtensionHost.storageHomes` — **ленивый** провайдер (`() => IExtensionStorageHomes`): папка воркспейса выставляется позже создания хоста, а `storageUri` зависит именно от неё, поэтому корни читаются на каждой активации. Сами корни собирает `extensionStorageHomes` (чистая, из путей user-data и текущей папки), пути одного расширения — `resolveExtensionStoragePaths`; и то и другое уезжает в `host.activateExtension`, а субпроцесс только оборачивает их в `Uri.file`. Регистр id повторяет эталон дословно, включая асимметрию: `globalStorage` — по **lowercase** id, `workspaceStorage`/`logs` — по id как есть. Разделение ответственности за каталоги — из контракта `vscode.d.ts`: **родителя** создаёт хост (`ensureExtensionStorageParents`, best effort — недоступный на запись user-data не рубит активацию), **свой** каталог создаёт расширение. Папка не открыта ⇒ `storageUri` = `undefined`, как в VS Code. Без опции — `fallbackExtensionStorageHomes()` (каталог во временных файлах ОС): `globalStorageUri` по API необязательным не бывает, а расширение падает на нём в первой же строке `activate()`.
- **Memento (`ExtensionContext.globalState` / `workspaceState`):** хранилище держит ХОСТ (`IExtensionStateStore`, опция `ExtensionHost.extensionState`; в проводке — `createExtensionStateStore` поверх общего `IStateService`, ключ `extensionState/<id>`, `globalState` — scope `global`, `workspaceState` — `workspace`, то есть стор открытого проекта или пустого окна), поэтому memento переживает перезапуск, как и состояние workbench'а. Субпроцесс держит словарь у себя (`get`/`keys` синхронные), начальный приезжает в параметрах `host.activateExtension` (без отдельного round-trip), а `update` отдаёт хосту словарь целиком запросом `memento.update` и резолвится по ответу; опустевший словарь удаляет запись (`IStateService.remove`). Запись `workspaceState` из воркспейса, отличного от того, где расширение активировано, хост отбрасывает с предупреждением: словарь A не протечёт в стор B (честное лечение — перезапуск хоста при смене папки). `setKeysForSync` — осознанный no-op (Settings Sync нет). Без проводки (тесты, харнессы) — `createTransientExtensionStateStore`: memento живёт в памяти субпроцесса.
- **Секреты (`ExtensionContext.secrets`):** хранилище держит ХОСТ (`IExtensionSecretStore`, опция `ExtensionHost.secrets`), субпроцесс только ходит в него запросами `secrets.get`/`store`/`delete`/`keys` — причина та же, что у каталогов хранения: раскладку user-data знает приложение. Секреты переживают перезапуск (в них лежит токен сервиса, который расширение спрашивает у человека один раз) — отдельный файл `<profileDir>/secrets.json` (0600, синхронная запись), `createFileExtensionSecretStore`. Лоток у каждого расширения свой: ключ хранения составной (id расширения + ключ секрета), причём id подставляет субпроцесс, а не сам вызов — чужой лоток расширению не адресовать. `onDidChange` приходит уведомлением `secrets.changed` от хоста и на СВОИ записи тоже (в эталоне событие описывает факт изменения, а не его источника); один диспетчер на субпроцесс разводит его по id. **Шифрования нет** — связки ключей ОС у нас нет, значения лежат открытым текстом под правами `0600`; замалчивать это нельзя, поэтому оно написано и здесь, и в [матрице](../public/API-COVERAGE.md). Отсюда же правило: значения секретов не логируются нигде, и сообщения об отказе хендлеров `secrets.*` не содержат параметров запроса (в соседнем поле того же объекта едет значение).
- **Каталог расширений (`vscode.extensions`):** состав знает только хост (он держит регистрации), поэтому каталог едет уведомлением `extensions.catalog` — **семенем на handshake, ДО первой активации** (`getExtension` зовут прямо в `activate()`, детектя соседей: в бандле Supermaven таких вызовов четыре) и на каждую смену состава. Активность доводится отдельным точечным `extensions.activated {id}`: манифесты тяжёлые (у языковых серверов `package.json` со схемой настроек — сотни килобайт), а меняется один флаг. Источник состава — `ExtensionHost.registrations` (все регистрации в порядке появления, отдельно от фазовых `pending`/`activatedRegistrations`), `packageJSON` — манифест регистрации целиком. `exports` (публичный API расширения) по проводу не ездят вовсе: все расширения живут в ОДНОМ субпроцессе, и значение берётся из карты `IVscodeHost.extensionExports`, куда точка входа кладёт результат `activate()`. **Расхождение с эталоном:** декларативные расширения (языковые паки без `main`) в extension host не регистрируются и в `all` не попадают. `Extension.activate()` у активного расширения отдаёт его `exports`, у неактивного — честно отклоняется: активацией распоряжается хост, и «субпроцесс просит хост поднять соседа» — отдельная задача со своим RPC. `extensionKind` — константа стороны субпроцесса (`ExtensionKind.UI`): upstream предписывает именно её, когда удалённого extension host'а нет.
- **Команда `setContext`:** встроенная команда VS Code, которой расширения публикуют собственные when-ключи (`commands.executeCommand("setContext", "supermaven.isProUser", true)`). Регистрирует `SetContextCommandContribution` (`workbench/browser/`) — без title, в палитре её быть не должно. Имя ключа регистрировать не нужно: when-вычислитель (парсер грамматики VS Code) читает любое имя целиком, в том числе **точечное** (`publisher.thing`); массив и объект хранятся как есть под оператор `in` — см. [Workbench.md](Workbench.md#система-команд).
- **`contributes.keybindings` (#194):** декларативный contributor `extensionKeybindingContributor.ts` (не через host) собирает манифестные биндинги всех расширений в слой extension `KeybindingRegistry` (`setExtensionKeybindings`): бинд расширения сильнее встроенного на той же комбинации, пользовательский из `keybindings.json` — сильнее бинда расширения, независимо от порядка шагов старта; `key`/`mac`/`linux`/`win`, `-command` — снятие из слоёв default и extension (user-бинды не трогает).
- **`IExtensionRegistration`** несёт `commandTitles`, `commandCategories` и `activationEvents`. `commandTitles` нужны, чтобы рантайм-`registerCommand` расширения **показался в палитре** (host заводит прокси в `CommandRegistry` с этим title; иначе команда исполнима, но невидима). `commandCategories` — `category` из того же вклада (`"Java"`): палитра рисует её **префиксом подписи** («Java: Switch to Standard Mode», `commandPaletteLabel`), но в сам `title` она не входит — иначе протекла бы в меню и в статус-бар, где эталон её не показывает. `activationEvents` — см. «Активация» ниже.
- **Lifecycle:** `ExtensionHost.dispose()` — graceful `host.shutdown` → `SIGTERM` → `SIGKILL`; `shutdown()` — то же, но отдаёт промис прощания; `disposeNow()` — синхронно добивает сигналом субпроцесс, который ещё не вышел (перезагрузка окна: дальше идёт `spawnSync` нового процесса, и он остался бы сиротой). Оба подключены к прощанию `LifecycleService` в `extensionHostModule`: `shutdown()` — в асинхронной фазе `onWillShutdown`, `disposeNow()` — в синхронной `onShutdownSync`, так что выход, перезагрузка и выход по инспектору снимают host одинаково. В DI — `ExtensionHostDIToken`. `main.ts` содержит ранний branch на env-флаг: subprocess уходит в `runExtensionHostSubprocess()`, обычный запуск — в `runEditor()`.
- **Смерть субпроцесса:** расширение может уронить свой процесс (краш нативного модуля, OOM, `process.exit`). `exit` ребёнка → `handleSubprocessDeath` → общий с вежливым выключением `resetSubprocessState()`: снимаются поверхности, которые держал мертвец (спиннеры прогресса, пункты статус-бара, декорации, прокси-команды, watcher'ы), обнуляются `rpc`/`channel`/флаги подписок, а подписки спавна на события ядра (`editorLayout`, `editorOptions`, `configuration` — шлют нотификации ЭТОМУ субпроцессу) живут в `spawnStore` и снимаются целиком: респавн не копит слушателей. Канал мертвеца закрывается (`rpc.dispose()`): запросы в полёте получают отказ, и активация, оборванная смертью, возвращается в `pending` вместе с остальными, а не теряется (если расширение за это время не сняли). Активные расширения при этом возвращаются в `pending`, а **любое** следующее событие активации сперва проигрывает **журнал запрошенных событий** (`requestedEvents`, как `_allRequestedActivateEvents` эталона; `ensureSubprocess` спавнит новый субпроцесс) и проход `workspaceContains:` (его повод в журнал не пишется — заново по ФС): их собственное событие (`*`, `onStartupFinished`, `onLanguage:<уже открытый язык>`) давно отгорело и второй раз не наступит. Оживление ленивое, на следующем событии, а не сразу при смерти — краш-петлю не устраиваем. Тот же журнал поднимает расширение, зарегистрированное **после** своего события (`_activateAddedExtensionIfNeeded` эталона): оно встаёт на самой регистрации. `activateByEvent` дожидается и расширений, которые уже поднимает другой вызов (активации «в полёте»), — его промис значит «расширения события активны». Заглушки-активаторы команд при этом возвращаются на место снятых прокси — см. «Активация» ниже.

### Активация (activationEvents)
Расширения активируются **лениво** по `manifest.activationEvents` — до триггера код расширения не грузится и subprocess под него не поднимается. Механика целиком на родительской стороне `ExtensionHost`; ядро про activation-events не знает.
- **Владелец цикла — `ExtensionService`** (`services/extensions/node/extensionService.ts`, интерфейс `IExtensionService` и токен — `services/extensions/common/extensions.ts`; аналог vscode `IExtensionService`, узкий срез). Политика «что и когда активировать» — у сервиса, механика (RPC, субпроцесс) — у `ExtensionHost` (сервис видит его через узкий `IExtensionActivationHost`). `start()` (зовёт старт окна в фазе `restored`, хук `afterRestored` у `workbenchStartup.ts`): регистрирует набор (`ctx.extensions` модуля — пользовательские, затем встроенные) через `toExtensionRegistration` (веха `main:extensions-registered`), затем, как `_handleEagerExtensions` эталона, **параллельно** `*` (за ним — события, запрошенные до регистрации, и **барьер** `whenInstalledExtensionsRegistered`) и проход `workspaceContains:`; `onStartupFinished` — после них, но не позже `STARTUP_FINISHED_TIMEOUT_MS` (10 с, `timeout(10000)` эталона), и веха `exthost:activated`. Старт окна `start()` не ждёт: фаза `eventually` (фоновый прогрев, `main:startup-complete`) от активации не зависит, трасса выгружается, когда есть обе вехи. Сбой host'а на одном стартовом событии — лог `extension host activation failed (<событие>)`, остальные события всё равно идут. **Память событий** (как `_allRequestedActivateEvents` эталона): `activateByEvent` до барьера запоминает событие (без повторов, в порядке прихода) и резолвится на барьере, после — идёт в host сразу. Поэтому файл, открытый на старте раньше регистрации, свой `onLanguage:` не теряет, и ручной `onLanguage:` активного редактора из `main.ts` больше не нужен. Сбой регистрации одного расширения — лог с id, сбой host'а — лог `extension host activation failed`; барьер открывается в любом случае. Набор статичен на жизнь окна (установка — через перезагрузку), событий состава нет.
- **Сборка регистрации — одна функция:** `toExtensionRegistration(ext, env)` (`services/extensions/node/extensionRegistration.ts`) из записи скана: манифест целиком, заголовки/категории команд (`collectCommandMeta`), события активации; пользовательское — `mainPath`/`extensionPath` с диска, встроенное — `source`/`filename` из ассетов; без `main` — `null`. Ей же собирают регистрацию стоковые фикстуры тестов (`TestUtils/installedExtensionRegistration.ts`), так что в сьютах регистрация ровно прод-овая.
- **Настройки расширений — в общем реестре.** `contributes.configuration` всех расширений (включая декларативные и ещё не активированные) регистрирует в `ConfigurationRegistry` главного процесса `ExtensionConfigurationContributor` (`services/extensions/common/`, аналог `configurationExtPoint` vscode) — на bootstrap, до загрузки настроек, поэтому скан расширений в `main.ts` идёт раньше `loadConfiguration`. Дубль ключа — warn в лог `extensions` и пропуск; `scope` без значения — `window`. Инъекции хоста (курируемые дефолты сторонних — `curatedConfigInjection`, пути вшитого tsserver — `builtinConfigInjection`) ложатся переопределениями дефолтов (`registerDefaultConfigurations`). Следствия: ядро видит дефолты `git.*`, валидатор settings.json не помечает ключи расширений «unknown», а субпроцесс своего defaults-слоя не держит — хост шлёт ему слои `{ defaults, user }` (`IConfigurationService.getConfigurationData()`), `WorkspaceConfigStore` сливает их той же `ConfigurationModel` (как `ExtHostConfigProvider` vscode). `configDefaults` в регистрации и в `host.activateExtension` больше нет. Значения ключей расширений по схеме не валидируются (схема расширения — полный JSON-schema). Тестовый харнесс собирает дефолты тем же контрибьютором из манифестов своих регистраций (`manifestWithDefaults` — описать настройки фикстуры в её манифесте).
- **Регистрация ≠ активация.** `registerExtension(reg)` — синхронный bookkeeping: кладёт reg в `pending`, регистрирует `commandTitles` и заглушки-активаторы команд (палитра видит команды до активации), возвращает disposable. Subprocess **не** поднимается.
- **Разбор событий — один на всех:** `services/extensions/common/activationEvents.ts`. Точное сравнение строк закрывает только виды без аргумента (`*`, `onStartupFinished`) и те, где аргумент приносит вызывающий (`onLanguage:<id>`, `onCommand:<id>`); `workspaceContains:<паттерн>` так не закрывается — его аргумент надо сверять с ФС.
- **`activateByEvent(event)`** — идемпотентно активирует `pending`-расширения, чьи события активации содержат событие: `ensureSubprocess()` → `host.activateExtension` RPC → перенос в реестр активных. Набор одного события активируется **параллельно** (`Promise.all`, как `_activateExtensions` эталона) с изоляцией сбоя каждого: стоковый LSP-клиент, поднимающий сервер секундами прямо в `activate()`, соседей не держит. Ошибки spawn/`parseActivateParams` (в т.ч. конфликт `source`/`mainPath`) всплывают здесь, а не на регистрации.
- **Дефолт `*` — осознанное отклонение от эталона:** манифест без событий (пусто или нет поля) считается eager — у vscode пусто значит пусто, но в нашем магазине опубликованы расширения, которые на этот дефолт полагаются (`test.tab-setter`), и эталонный дефолт молча выключил бы их у пользователей. Считает дефолт сборка регистрации (`computeActivationEvents`), хост его не додумывает: регистрация с пустым набором не поднимается. Тестовым регистрациям в обход сборки eager-дефолт даёт харнесс (`testRegistration`, `extensionFixture`).
- **Неявные события — явный список генераторов** `IMPLICIT_ACTIVATION_EVENT_GENERATORS` (`activationEvents.ts`, как `activationEventsGenerator` у дескрипторов точек эталона): `contributes.commands` ⇒ `onCommand:<id>` (иначе видимая в палитре команда не-eager расширения была бы вечным no-op'ом), `contributes.languages` ⇒ `onLanguage:<id>`. Полный набор (`computeActivationEvents`: объявленные + неявные) считается **один раз при сборке регистрации** (`toExtensionRegistration`) и лежит в `IExtensionRegistration.activationEvents`; хост только сравнивает строки и про `contributes` не знает. Генераторы для поверхностей, которых у нас нет (`onView`, `onUri`, …), появятся вместе с поверхностью.
- **Поддержанные события:** `*` и `onStartupFinished` (фаерит `ExtensionService.start()` после регистрации, когда файлы открыты), `onLanguage:<id>`, `onCommand:<id>`, `workspaceContains:<паттерн>`. `onLanguage:<id>` — владелец сигнала сервис языков (как `requestRichLanguageFeatures` эталона): `TextFileModel` зовёт `ILanguageService.requestLanguageFeatures(id)`, когда у документа появляется язык (новая модель, открытый файл, синтетический документ) или меняется (Change Language Mode, Save As); `LanguageRegistry` фаерит `onDidRequestLanguageFeatures` один раз на язык, и `extensionHostModule.ts` переводит его в `ExtensionService.activateByEvent("onLanguage:"+id)` плюс голое `onLanguage`. Так расширение встаёт для любой модели — фоновой вкладки, диффа, `jdt:`-документа, — а не только для активного редактора; стартовые (модели открылись до регистрации) сервис запоминает и проигрывает за `*`.
- **`onCommand:<id>` — заглушка-активатор, а не только событие.** Пофаерить событие мало: настоящий прокси команды заводит сам субпроцесс в `commands.registerCommand`, то есть уже ПОСЛЕ `activate()`, и команда до активации попросту не нашлась бы. Поэтому `registerExtension` кладёт в `CommandRegistry` заглушку под каждый `onCommand:<id>` (с `commandTitles`-заголовком — значит команда видна в палитре): её исполнение сперва `await activateByEvent`, потом вызов уже живого прокси. Заглушка не затирает живой прокси, снимается на `commands.registerCommand`, и **возвращается на место после смерти субпроцесса** — иначе команда исчезла бы из палитры вместе с единственным ручным способом оживить расширение. Провал хоста и «расширение поднялось, но команду не завело» гасятся логом: вызывающие (палитра, бинд) результат не ждут, и reject ушёл бы в `unhandledRejection` главного процесса.
- **`workspaceContains:<паттерн>` — повод считается по ФС**, поэтому у него свой вход `activateByWorkspaceContains()` и своя единица: не «событие на всех», а **расширение** (паттерн — аргумент события, и подошёл он конкретному манифесту; так же устроен `checkActivateWorkspaceContainsExtension` эталона). Причина подъёма — подошедший паттерн — уходит в лог хоста. У префикса **две семантики**, и сводить их к одной нельзя: паттерн **без** glob-символов — простая проверка существования пути относительно каждой папки воркспейса (истинна и для каталога, `workspaceContains:.vscode`), паттерн **с** ними — поиск ФАЙЛА по дереву. Обход — `node/workspaceContainsActivation.ts` за сеамом `IWorkspaceScanner` (в проде — настоящая ФС): в ширину, с глубиной по самому щедрому паттерну (`*.py` читает только корень, `*/pom.xml` — корень и первый уровень, `**` снимает ограничение), мимо `.git`/`node_modules`, с бюджетом каталогов и тайм-аутом 7000 мс как в эталоне. Тайм-аут — гонка, а не только флаг отмены: повисший `readdir` флагом не сдвинуть. Оборванный обход виден в логе — молча усечённый читался бы как «ничего не подошло».
  - **Расхождение с эталоном:** глобы матчатся нашим `base/common/glob.ts` — якорно по относительному пути, `*` не переходит `/`. У эталона за `workspaceContains:` стоит поиск на ripgrep, где паттерн без `/` ищется на любой глубине: `workspaceContains:*.py` там поднимет расширение и на `src/main.py`, у нас — только на `main.py` в корне. Второй диалект глобов ради этого не заводим; рекурсивные паттерны (`**/pyproject.toml`) работают одинаково.
  - **Лениво.** Папка воркспейса может открыться позже регистрации расширений, поэтому стартовый проход делает `ExtensionService.start()` (последним из стартовых событий — обход дерева единственный из них ходит на диск), а смену набора папок ловит `IWorkspaceContextService.onDidChangeWorkspaceFolders` → `ExtensionService.activateByWorkspaceContains()` в `extensionHostModule.ts` (до барьера проход ждёт стартовый). Повторный проход дешёвый: активное расширение ушло из `pending`, кандидатов нет — ФС не трогается вовсе.
- **Тест-хелпер:** `registerAndActivate(host, reg)` (`TestUtils/ExtensionTestHarness.ts`) = `registerExtension` + `activateByEvent("*")`; харнесс фаерит `activateEvents` (дефолт `["*"]`) после регистрации.

### Пример: builtin `diode-settings` (автодополнение настроек)
`Extensions/builtin/diode-settings/` — code-расширение, активируется **только** по `onLanguage:json`/`onLanguage:jsonc` (доказательство лениости: пока не открыт JSON — не грузится). В `activate()` регистрирует `registerCompletionItemProvider` с селектором `pattern:"**/settings.json"` → в `settings.json` подсказывает известные ключи настроек. Каталог ключей **вшит на этапе сборки**: `scripts/generate-settings-schema.mjs` (запускается из `build-extensions.mjs` перед esbuild) собирает ключи из app-дефолтов (`Configuration/defaults.ts`) + `contributes.configuration` всех builtin и пишет `settings-schema.generated.ts`, который бандлится в `out/extension.cjs`. Никакого рантайм-API за схемой расширение не ходит.

## Правило роста `vscode.d.ts` (важно)
`src/vscode-dts/vscode.d.ts` — стадийная копия upstream `microsoft/vscode:src/vscode-dts/vscode.d.ts`, всё line-commented кроме активной поверхности. Это дословная копия реального API, а не стаб под реализацию. Инвариант: **файл меняется ТОЛЬКО снятием `// `**.

Структура файла:
1. **Шапка** — провенанс (upstream tag + commit SHA + permalink) и ссылка сюда.
2. **Активный `declare module "vscode"`** — дословно раскомментированные строки upstream. Единственный human-owned блок. Framing-строки (сам `declare module "vscode" {`, его `}`, глобальный `Thenable`) — единственное не-upstream в этой части.
3. **Строка-сентинел** `//@diode:begin-upstream-verbatim …`.
4. **Дормант** — вся upstream-копия, каждая строка с `// `. Генерируется, вручную не редактируется.

**Пиннинг.** Тег зафиксирован в шапке и согласован с `extensions/VSCODE_VERSION` (сейчас `1.127.0`) — держи их в лок-степе. Пин нужен, чтобы обновление upstream шло **ручным трёхсторонним merge**: base = `vscode.d.ts` запинненной версии, theirs = новый upstream, ours = наш файл с раскомментированными блоками.

**Как добавить API.** Найди нужный блок в дормантной части и подними **дословно** (сняв `// `) в активный модуль — не сужать / не переписывать / не переоформлять (комментарии тоже upstream). Если блок тянет ещё не раскомментированный тип (dependency closure) — раскомментируй и его. Runtime-значение может опережать типовую декларацию (namespace отдаётся через `as unknown as typeof vscode`). Поднял поверхность или поменял статус стаба — **в том же PR обнови публичную матрицу** [docs/public/API-COVERAGE.md](../public/API-COVERAGE.md): она ведётся руками и держится актуальной именно этой дисциплиной.

**Bounded member-level uncommenting.** Для «тяжёлого по closure» блока (namespace/интерфейс/класс, чьё полное upstream-тело тянет непрактичное дерево зависимостей) можно раскомментировать **подмножество членов**, оставив прочие в дормантной части. Каждая раскомментированная строка обязана быть **байт-в-байт** равна upstream. Так сделаны, например, `window`/`workspace`/`languages` (только реализованные функции), `TextEditor` (`document`/`selection`/`selections`/`options`/`edit`), `ExtensionContext` (`subscriptions`, каталоги хранения, `secrets`), `TextDocument`/`FileStat`/`CompletionItem` (подмножество полей).

**Инструмент.** `scripts/import-vscode-dts.mjs`:
- (без флагов) — регенерировать дормант из запинненного тега + обновить провенанс в шапке (активный модуль не трогает);
- `--check` — сверить, что дормант байт-в-байт равен upstream тега (drift guard, нужна сеть);
- `--verify-active` — offline-проверка инварианта: каждая кодовая строка активного модуля дословно присутствует в дормантной копии. Прогоняй после ручного раскомментирования.

**Семантические отклонения Diode** (тип совпадает с upstream, отличается только смысл/JSDoc-намерение):
| Символ | Отклонение |
| --- | --- |
| `version` | Возвращает версию **Diode**, а не VS Code (upstream JSDoc говорит «editor»). |
| `Event<T>` | Слушатель `(e) => any` (upstream); хост оборачивает подписки через `EventEmitterImpl` в `Vscode/VscodeTypes.ts`. |
| `TextEditorOptions.indentSize` | Хост алиасит его к `tabSize` (Diode пока не различает); editorconfig шлёт `indent_size` так. |
| Namespaces / value-типы | Рантайм может опережать/отставать от типов; поверхность собирается в `Vscode/*` и отдаётся как `as unknown as typeof vscode.*`. |

**Кодировки (#106).** `workspace.openTextDocument(…, { encoding })` реально декодирует не-utf8 файлы осью encoding ядра (`src/vs/editor/common/model/encoding.ts`): explicit-кодировка побеждает BOM-сниф, неизвестный id молча откатывается к дефолту (контракт vscode.d.ts); эфемерный документ детектит и `encoding`, и `eol`. `ExtHostTextDocument.encoding`/`.eol` — живые: обновляются метой `editor.activeEditorChanged` и снапшотом will-save (`IWireWillSaveParams.encoding`). Дормантные `workspace.decode`/`encode` не раскомментированы (не понадобились).

**Зависимости:** Extensions → Editor (через `ILanguageService`, `TextMateGrammarLoader`, `TokenizationRegistry`), Common. Подмодуль **`Extensions/Host` дополнительно → Workbench** (адаптеры над `EditorService`; мост файловых декораций типизирован портом `IFileDecorationsTarget`, в DI его реализует `ExplorerService`) и **→ Theme** (`ThemeColorResolverAdapter` над `ThemeService`) — единственное место, где Extensions поднимается выше Editor.

**Мост декораций (`vscode.window.createTextEditorDecorationType` / `registerFileDecorationProvider`).** Value-типы (`ThemeColor`/`FileDecoration`/`OverviewRulerLane`/`DecorationRangeBehavior`) живут в `Vscode/VscodeTypes.ts`; `WindowNamespace` держит тип декорации локально (монотонный числовой key) и шлёт хосту RPC-нотификации, сериализуя `ThemeColor` как `{ $themeColor: id }` (см. `WireTypes.ts`). Хост держит реестр `key → { overviewRulerColorId?, isWholeLine }` (gutter-тип = есть `overviewRulerColor`), резолвит `ThemeColor` через `IThemeColorResolver` и проталкивает: gutter change-bar'ы — в `EditorComponent.setGutterChangeDecorations` (по совпадению пути, образец — `DiagnosticsService`), файловые декорации — в `ExplorerService.setFileDecorations`. На `theme.onDidChange` все держимые декорации пере-резолвятся и пере-push'атся. **Ядро про источник декораций (git/SCM) не знает** — адаптеры отдают уже резолвнутые packed-RGB цвета.
