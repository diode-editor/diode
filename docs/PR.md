# Что обязано быть в PR

## Демо-сценарий для видимых фич

Любая фича с видимой/внешней составляющей (новый виджет, оверлей, изменение layout, темизации, статус-бара,
дерева файлов и т.п.) обязана принести **сценарий-демо**:

1. Добавь или обнови сценарий в `e2e/scenarios/` (`*.scenario.ts`) — код, который поднимает настоящий
   редактор headless, шлёт нужные команды и снимает кадр(ы). Формат — `defineScenario({ name, open, run })`;
   за образец возьми `e2e/scenarios/quickOpen.scenario.ts`.
2. Прогони `npm run screenshots` — сгенерит PNG в `screenshots/` (каталог в `.gitignore`) +
   `screenshots/INDEX.md`. Посмотри на кадры **сам**: в #194 пропущенный сценарий стоил бага, который
   виден на первом же кадре.
3. В теле PR опиши, что на этих кадрах происходит, и как то же самое пройти руками.

Сценарий — это гейт, а не украшение: он остаётся в репозитории и ловит регрессии дальше.

## Секция `## Removed`

Тело PR обязано содержать раздел `## Removed`: что удалено или заменено — код, тесты, настройки,
команды, которые работа вывела из употребления. `Nothing` допустимо, но пишется явно: вопрос «что
ушло» задаётся на каждом PR, потому что без него код только растёт (удалений к добавлениям в `src/`
— 0.1 в обычный месяц, и почти все удаления — чистка комментариев). Тестировщик лупа (скилл `tester`)
сверяет раздел с ветвью: заявленное удалённым действительно убрано, замена не оставила старый путь
рядом с новым.

## Зелёный CI и влитие

Прикладывать PNG к телу PR не требуется. Работу принимают по **зелёному CI** (`ci.yml`: типы и линт,
юниты с покрытием, мутационный гейт, e2e на ubuntu и windows) и по **запуску редактора из ветки**: человек
собирает его сам (`npm start` или `npm run build:sea`), а как воспроизвести поведение, ему говорит тело PR.
Бинарников на PR CI не собирает: workflow `PR Build` снят — его артефактами никто не пользовался, а сборку
под все платформы делают `nightly.yml` и `release.yml`. Что сборка не сломана, проверяет e2e: он собирает
SEA-бинарь сам.

**Влить PR — работа агента:** по зелёному CI свой PR вливаешь сам, squash'ем
(`gh pr merge <N> --squash`), если человек не сказал «покажи сначала» или задача явно не про
внешнюю поверхность (чужие репозитории: `microsoft/winget-pkgs`, сайт — их показываешь человеку до
отправки). Красный CI — это «не готово», даже если тесты локально зелёные: доводи до зелёного, потом влей.

**Флак, не задетый диффом** (упал тест, которого PR не касается, а на соседних прогонах он зелёный):
`gh run rerun <run id> --failed`, не чинить в своей ветке. Юнит-тест заносится в `test-flakes.json`
(`action: "retry"`), и с этого момента он повторяется сам, а не стоит следующим PR перезапуска;
строка с симптомом и раном — в [список флаков](TODO/TestFlakes.md#флаки). Обе правки — прямо в
`main`, PR не нужен; порядок — [TODO/TestFlakes.md](TODO/TestFlakes.md). Особый случай — мутационный
гейт упал в Stryker'овском «initial test run»: это не вердикт по мутантам, а флак dry run'а —
занеси тест в список и перезапусти ран целиком.

**Красный CI на чужом.** Сначала `gh run list --branch main` — если `main` красный на том же
месте, это не твой PR. `static` красный на файлах вне `git diff origin/main...HEAD` — тоже чужое:
семантический конфликт двух соседних мержей, чинится отдельным PR, а не в своей ветке.
Упавший тест вне диффа на зелёном `main` — флак (абзац выше).

**CONFLICTING** (`node scripts/git/pr-status.mjs`): CI на таком PR не запускается вовсе, а уже идущий
прогон бежит против старой базы, ждать проверок бесполезно — сначала merge или rebase на свежий
`origin/main`. Поэтому CI ждём `node scripts/git/pr-status.mjs <PR> --watch` (выходит с кодом 13, едва
PR стал конфликтующим), а не `gh pr checks --watch`. Чаще всего конфликтуют общие доки, которые
параллельные сессии правят разом (`docs/TODO/*.md`, `docs/public/API-COVERAGE.md`): правь их точечно,
своими строками, не переписывай чужие абзацы.

Тяжёлые гейты до PR гоняются тем же `ci.yml` на своей ветке: `npm run ci:run -- <gate>` —
скилл [`heavy-run`](../.claude/skills/heavy-run/SKILL.md#гейт-в-ci-без-pr).

## Git: стек, rebase, push, worktree

Помощники `scripts/git/*`, стек PR после squash родителя, сдача на быстром `main` (база, схлопывание,
пробное слияние), уборка worktree и картинка в теле PR через orphan-ветку — [GIT.md](GIT.md).
